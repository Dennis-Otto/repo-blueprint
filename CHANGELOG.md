## [1.3.0](https://github.com/Dennis-Otto/repo-blueprint/compare/v1.2.2...v1.3.0) (2026-11-01)

### Features

- **A project can add its own assets to a release, attested like the rest:** a `scripts/release-assets.sh` of the project builds what no registry builds, such as the zip of a browser extension. The build of the release runs `bash scripts/release-assets.sh FOLDER VERSION` at the commit of the release, in a job of its own that may write nothing and holds no secret, with Node.js and `npm ci --ignore-scripts` first where a `package.json` is, then attests each file with the package, the SBOMs and the notices and attaches it to the draft before it is published. Where `PUBLISH_TO` is `none`, the SBOMs describe the zips and tarballs of the script, and the verification of the release fails for an asset without its signed provenance. `SECURITY.md` shows how to verify such an asset. A name that the release or its registry keeps for its own files stops the build. A project without the script releases as before (decision 0084).

### Bug fixes

- The website of a project no longer hangs at random in the CI until its step ends after five minutes: a preview card that needed a layer which another card was just starting waited without end, in the social plugin of Material. The hooks of the website now let it wait for the job itself, and a build still running after four minutes prints where each of its threads stands.
- **The recording of a copy in the README and on the website renews itself again:** the Docs pictures workflow failed after every release since the question about the markers of test logs, which the recording left unanswered. It now answers each question, a test keeps it that way for every new question, and its dry run of `create` ends on the commands that make the repository and not on the marks of its preflight.
- Jobs that block every host they don't need no longer fail on a host they may reach, or hang until their time limit after their last step, as they did at random on GitHub's runners in `westus2`: the workflows move to Harden-Runner v2.22.3, each such job first waits until Harden-Runner lets its hosts through, and a job that still runs out of time runs once more, in a required check such as the title of a pull request and in a bot alike. A workflow of your project's own that blocks takes the same step: copy *Wait until Harden-Runner lets the hosts through* from `.github/workflows/welcome.yml` right after Harden-Runner, with `HOSTS` equal to its `allowed-endpoints`; a Chrome extension can add the clause to `docs/releases.md`.
- **Biome 2.6 stays out of the Markdown and YAML of a Node package:** since version 2.6 Biome also formats Markdown and YAML, so `biome ci` in the step *Lint and format* of a Node package or Chrome extension failed on files the blueprint renders, such as `AGENTS.md` and `mkdocs.yml`. `biome.jsonc` now leaves these files out, markdownlint still checks the Markdown, and Biome checks the code and the JSON, as before. The new lock takes Biome 2.6.3 and the other updates of this lock file maintenance.
- **The dependency review accepts the new license of `wcwidth`:** the current release of this tool of the blueprint bot declares `HPND-Markus-Kuhn AND MIT`, a permissive license that the review did not know, so it stopped every refresh of the lock files. A new project accepts it from the start. An existing project owns its `.github/dependency-review.yml`, so add `pkg:pypi/wcwidth` under `allow-dependencies-licenses` there.
- Delivering a Python package to PyPI no longer runs an action with a known vulnerability: the Release workflow moves to `pypa/gh-action-pypi-publish` v1.14.3, which no longer trusts the revoked root certificate of [GHSA-5xjx-3w67-w9x9](https://github.com/advisories/GHSA-5xjx-3w67-w9x9). With the update of the blueprint, the alert of zizmor that this advisory opened on `release.yml` closes, and the Findings workflow passes again, in every repository. The PR coach now also says how to fix such an alert: move the pin to the release that the advisory names as fixed.

### Performance

- **The mutation tests collect mutmut's stats once, not in every part:** mutmut first runs the whole suite with trampolines that record which tests reach each function, which takes about ten times as long as the tests, and each part of the Mutation workflow did that on its own: in issue-assistant, six parts spent 13 to 21 minutes each. Now the job *mutation stats* runs them once and hands `mutants/mutmut-stats.json` to every part, which loads it and runs only its mutants, with the same configuration of mutmut (decision 0090). When a test fails without any mutant, no part starts: the run costs one job, and its summary and annotation name the test, also when pytest prints only a traceback. A pull request that changes how the mutants run collects the stats and tries a sample of about 200 mutants in one part, the same functions each time, for at most 12 minutes, in place of every part.

## [1.1.0](https://github.com/Dennis-Otto/repo-blueprint/compare/v1.0.8...v1.1.0) (2026-10-25)

### Features

- **`create` checks what it needs before its first step:** its preflight asks for Python 3.12 or later, Git with the name and email address of the first commit, GitHub CLI 2.48 or later, signed in with the scopes `repo` and `workflow` (and `read:org` for an organization), an owner where that account may create the repository, and a name that GitHub doesn't have yet. A finding marked with ✘ stops `create` before anything is made and names the command that fixes it, such as `git config --global user.email "you@example.com"` or `gh auth refresh --hostname github.com --scopes workflow`. `--dry-run` shows the preflight with the commands, and `python3 .github/blueprint.py doctor` runs it alone (decision 0078).
- **`create` goes on where it stopped:** after a push or settings that failed, run it again. In a folder whose `origin` pushes to the repository on GitHub, it pushes when GitHub has no branch `main` yet and then applies the settings and shows the checklist, rather than refusing the folder. A folder that pushes to another repository is still refused. The troubleshooting explains each finding and both cases.
- **The Dependabot alerts of accepted advisories close by themselves, and open again when the acceptance ends:** Dependabot doesn't read `osv-scanner.toml`, so it kept an alert open for every advisory that the project accepts, such as the 41 of the Pillow that Home Assistant pins for the tests of an integration, and a new alert that matters hid among them. The new job *dependabot alerts* of the OSV-Scanner workflow, on `main`, every week and by hand, dismisses each open alert that an acceptance which hasn't ended covers, as a tolerable risk with a comment that starts with *Accepted in* and names the file, the end and the reason, and opens again each alert that it closed once the date has passed, the entry is gone or an update moved the version. `python3 .github/blueprint.py advisories --dependabot --dry-run` shows what it would do. The job asks the settings app, or the release app without one, for a token with *Dependabot alerts* (read and write) alone: grant that permission to the app on its settings page and accept it on its installation, as *Your own account* shows. Until then the job fails in the repositories of the blueprint's owner and leaves a notice in those of every other owner. Decision 0086 says why.
- **One list of the repositories that follow the blueprint:** `.github/fleet.toml` names each one with its kind, its place in the Rollout and whether the Variants try every pull request on its answers, and `python3 reference.py` writes from it the showcase of both READMEs, the section *A real repository* of each kind on the website, the order of the Rollout and the canaries of the Variants; a test fails while one of them differs (decision 0081). Player Switch for Autodarts, the first Node package that follows the blueprint, is in all of them now: in the showcase and on the page of the Node kind, third in the Rollout, and a canary that tries every change of the blueprint on its answers before the merge.
- **Node packages get a check with the newest Node:** the new workflow `newest-node.yml` runs the checks of `scripts/check.sh` with the newest release of Node after every change of `main` and every week, while the CI checks the Node of `.nvmrc`. It is no required check; a failure keeps one issue open, *The checks fail with the newest Node*, which names the Node that failed and which the weekly run closes once the checks pass again.
- **A private repository on GitHub Free passes its checks:** `settings apply` reads whether a private repository has GitHub Code Security and, without it, sets the new variables `CODE_SCANNING` and `DEPENDENCY_REVIEW` to `off` and drops the rule of code scanning from the ruleset of `main`. CodeQL then skips its analysis, whose terms allow it on private code only with GitHub Code Security or Advanced Security, and its check passes with a notice; zizmor fails on every finding; OSV-Scanner, the Scorecard and the taint analysis of PHP keep their findings out of code scanning; and the dependency review leaves the vulnerabilities of the lock files to OSV-Scanner. The rulesets and GitHub Pages that GitHub refuses for the plan are a notice, which fails no run, and the website of `main` is the artifact `website`. The checklist shows a private repository the step *GitHub Code Security on*, and the FAQ a table of what works on which plan (decision 0082). A public repository runs as before.
- **The pages check warns of tables whose cells hold paragraphs:** a cell of a Markdown table with more than 30 words, in a README, a CONTRIBUTING file or a page of `docs/`, is a warning at the line of its row, in the log of *Pages in one column* and as an annotation of the pull request, since the GitHub app and phones squeeze such a table into narrow columns or scroll it sideways, and a screen reader reads it cell by cell. It fails nothing yet: make the rows a list, or move the detail to a page of its own and link it.
- **The README of the blueprint reads on a phone:** it has a sixth of its words, with one line for each area of what a new repository gets, and the details are pages of their own on the website, under *Features*, in English and German. The guide of the website keeps the start, the kinds of projects and the set-up, with the anchors that other pages link to.
- **The issue of flaky tests counts how often each job and test flaked:** to see which test flakes most, you had to read every comment of the issue. Its body now keeps a table of each job and test, how often it flaked and the run in which it last did, the latest first, and each run gets a comment of its own. An issue that the bot opened before keeps its text and gets the table added, which counts from the next run on.
- **The flaky-test bot names the test that failed in the logs of tests that pytest doesn't run:** for a job of browser tests, such as a Docker E2E that timed out in Safari, the Test column stayed empty and the error was only the exit code. With `copier update --data "test_marker=Browser step:"`, the text that the log writes before the name of each test or step as it starts, the bot names the one that the log names last before the failure, in the step of the job that failed and, when workers run side by side and put their own prefix before each line, in the worker that failed, and takes the first exception after it as the error when no annotation names one.
- **Every tool of the checks shows its findings at their lines:** in the CI, a finding of ShellCheck, mypy, PHP CS Fixer, PHPUnit, pytest and the tests of Node is now an annotation at its line in the files of a pull request, as those of the text files, Ruff, Psalm, Biome and the TypeScript compiler already were, and the comment of the PR coach lists them with their files and lines instead of only the step that failed. `blueprint.py annotate` reads what each tool writes and passes it on to the log as it is, or reads the report of JUnit of the tests, and names only files of the repository, with every text escaped, so the output of a pull request from a fork can't start a command of the runner. A test that fails shows where it failed, a change of the coding standard shows the lines that PHP CS Fixer writes, and a run on your machine prints what it printed before. Decision 0071 says why.
- **A check without its explanation fails the checks:** the new step *Explanations of the checks* of `scripts/check.sh` runs `python3 .github/blueprint.py coach verify`, which fails for a required check or a step of `scripts/check.sh` that has no explanation in `.github/checks.toml` or `.github/checks.project.toml`, and for an explanation without its `autofix`. Every repository of the blueprint explains its checks already; a project that requires a check of its own explains it in `.github/checks.project.toml`.
- **The website shows the changelog fragments, and the fix bot heals their headings:** a page of the website that includes `CHANGELOG.md`, such as its changelog, now shows the entries of the fragments in `changelog.d/` under *Unreleased*, grouped as the next release groups them, so readers see what `main` brings before the release; before, it showed only the text of Unreleased until a release took the fragments in. A heading of a fragment that surely means a kind of change, such as `### Fixes` for `### Fixed`, `### bug fixes` for `### Bug fixes` or `## Features` for `### Features`, no longer waits for its author: `blueprint.py fragments --fix` renames it, and the fix bot commits the rename onto the branch of a pull request, or suggests it on one from a fork. A heading as close to one kind as to another, such as `### Change`, stays for its author. The PR coach names the fragment `changelog.d/<branch without its type>.md` as the fix of the check *changelog*, with Unreleased as the alternative.
- **A version changed by hand fixes itself:** when the step *Version* of `scripts/check.sh` finds a file with another version than `.release-please-manifest.json`, the fix bot writes the version of the release bot back at its place and commits it, and nothing else of the file changes. On your machine, `python3 .github/blueprint.py fix version` does the same.
- **A lock file that Composer or npm refuses locks itself again:** after a change of `composer.json` or `package.json` by hand, `composer install` and `npm ci` stop at the lock file that no longer agrees. The fix bot now locks it again with the least change, `composer update --minimal-changes` or `npm install --package-lock-only`, which keeps every other package at its version, and commits it; a lock file that the tool takes stays as Renovate wrote it. A Node package gets the step *Package lock*, which finds such a lock file on your machine too.
- **The label `no-bot-fixes` comes with a new repository:** it keeps the fix bot away from a pull request. An existing repository adds it to its own `.github/labels.toml`, with the group `decision`.
- **The explanation of the check *reuse* says what it really finds:** `REUSE.toml` gives every file the license of the project, so a failure is a header of a file's own, with a license whose text `LICENSES/` lacks or one that no file names, and the PR coach now says how to fix that. Decision 0069 says why no command fixes it, and which fixers follow in Dennis-Otto/repo-blueprint#429.
- **The workflows of a project add their parts to the one report of the PR coach:** a workflow such as the visual tests of a card or a check of the size of a module no longer needs a comment of its own on a pull request. It keeps the artifact `pr-report-<name>` with the file `report.md` for the head of the pull request, and the coach shows it after its own parts, under the title that `[report.<name>]` in `.github/checks.project.toml` gives it, with a link to the artifact. The coach runs nothing of the artifact and shows its Markdown only as code, a table with code in each cell, so a pull request from a fork can't post links, pictures or mentions with it; a part whose first line is `<!-- quiet -->` brings no comment while the checks pass, and `replaces` names the marker of the old comment of the workflow, which the coach deletes. The catalog belongs to the project, so an existing repository adds a table such as `[report.card-size]` with its `title` to `.github/checks.project.toml` and names the workflow in `test_workflows` of `.copier-answers.yml`; the starter of a new repository shows it as a comment.
- **The release verification checks the zip that HACS installs:** for a Home Assistant integration (`PUBLISH_TO` `hacs`), `verify-release.yml` checked the signed tag, the provenance and the SBOMs, but not the one file that HACS installs. It now checks that the release has the zip that `hacs.json` names with `zip_release`, that its `manifest.json` lies at the root of the zip, with the domain of the folder in `custom_components/` and the version of the release, and that HACS offers the release as it should: a release as the latest one to every user, a beta only as a prerelease. A beta, such as 2.1.0-beta.1, now also has its own version in the `manifest.json` of its zip, which Home Assistant shows to its testers, where it had the version of the last release. Decision 0065 says why.
- **A new repository photographs what it makes from the first run of the screenshot bot:** the `scripts/screenshots.sh` that it starts with renders the social preview and photographs the home page of the website, and by its kind the page of the integration in a Home Assistant in Docker, which runs with `custom_components/` and the integration set up through its config flow, or the app in the apps of the settings of a Nextcloud in Docker, with the app enabled. Each picture comes as `docs/images/screenshots/<name>.png` in the light theme and `<name>.dark.png` in the dark one, taken by the Chromium of the social preview's image with Playwright, which `.github/screenshots-browser-requirements.txt` pins by its hashes and Renovate moves together with the image; the server and the browser share a Docker network without a way out, the clock of the browser stands still, its window is 1280×800 and its letters have gray edges, so the same code renders the same pixels. Add the pictures of your project to the function `shoot()` of the script. The script belongs to the project, so an existing repository takes it over by hand: copy the one of a new repository of its kind, with `.github/screenshots-paths.txt`, from `copier copy` into an empty folder. The job *render* of the screenshot bot now checks out the whole history, so that a picture of the website shows the date of each page as it is published. Before an update of the image of Home Assistant or Nextcloud or of Playwright reaches a release, the Variants workflow takes these pictures with it; Renovate of a Nextcloud app offers no major version of Nextcloud for them, which must wait for the max-version of `appinfo/info.xml`. Decision 0067 says why.
- **The README shows the pages of GitHub that a repository of the blueprint gets:** an update of the blueprint with its checks, the assets of a release with its SBOMs and its provenance, and the comment of the PR coach with the coverage of the tests, each in both themes. `scripts/docs-pictures.sh` photographs them from pages that no longer change, with a clock that stands still long after them, and the Docs pictures workflow renews them when GitHub changes its pages.
- **A new alert of zizmor stops the merge, as one of CodeQL does:** the audit of the workflows (*Workflow security*) now runs in every pull request into `main`, the release pull request too, rather than only in those that change a workflow, and the rules of `main` list zizmor in their rule of code scanning. A pull request that adds a weakness to a workflow, such as an expression of the event in a script, shows the alert at its line and merges once it is fixed or accepted with its reason (`# zizmor: ignore[<audit>]` at its line), instead of turning `main` red in the Findings workflow after the merge. Every alert of zizmor counts, whatever its severity, since Findings fails on each one; a project changes that in `.github/repository.project.toml`. The PR coach tells what to do when an advisory published since the last run on `main` shows as an alert of a pull request that changes no workflow (decision 0073).
- **A pull request fails while it runs an action that the list of the allowed actions lacks, also one that an action runs in turn:** GitHub starts a workflow only when `[actions.selected]` allows every action that it runs, so an update of a composite action or a reusable workflow, such as one by Renovate, that started to run a new action passed every check and then stopped the workflows after the merge, and in the blueprint every repository after the release. ### Performance

- **Pull requests wait less for a runner:** a check now runs only where it can change a result, since an account runs about 20 jobs at once. - **The release verification bot** checks every release after its delivery and the latest one every week, as its users can: the signed provenance of every asset in GitHub and in the attached bundle, the SBOM, an immutable release with a signed commit, and the same release on PyPI, npm, GHCR, the Nextcloud App Store or the major tag of an action.
- **Prereleases:** a version such as `2.0.0-beta.1`, set with a line `Release-As: 2.0.0-beta.1` in a pull request, becomes a prerelease. It keeps the text of Unreleased for the release that follows, leaves the major tag of an action where it is, and goes to the tag `next` on npm.
- **The dashboard** of every public repository of the owner on GitHub Pages: the release of the blueprint it is on, its releases, its open pull requests and conflicts, the last runs of its main workflows and its Scorecard, every six hours.
- **Harden-Runner** records the network traffic of every job of the workflows, so that a connection that doesn't belong there shows; SECURITY.md says so.
- **The issue forms belong to the project** after the first copy, like its labels, because their areas and fields are its own. They start richer: an introduction with what happens with an issue and where vulnerabilities go, steps to reproduce, an area for feature requests too, and a checklist.
- Releases attach their signed provenance also as in-toto JSON lines (`provenance.intoto.jsonl`), the format of SLSA that OpenSSF Scorecard and other tools look for.
- **A dev container** for VS Code and GitHub Codespaces in every project: the image of its kind by digest, which Dependabot keeps current, the tools of the checks and the pre-push hook set up once it is created.
- Every project gets the `docker` label, for the Dependabot updates of the image of its social preview.
- **Nextcloud apps** check more on every change: `composer validate` and `composer audit`, `appinfo/info.xml` against the schema of the App Store, the PHP of `templates/`, and the package that krankerl builds, with the project's `scripts/check-package.sh`, which the release runs before and after signing as well. Lines of `info.xml` marked `x-release-please-version`, such as screenshot URLs at a tag, follow each release.
- The dev container has Docker for every project, for the end-to-end tests and the social preview, and Node for a Home Assistant integration or a Nextcloud app with a frontend; its Features are locked and kept current by Dependabot. The CI of a Home Assistant integration with a `package.json` sets up Node for the tests of its frontend.
- The README describes how an existing repository takes the blueprint.
- Every `.gitignore` leaves out the local settings of Claude Code, and `.gitattributes` marks the lock files as generated, so that GitHub folds them in diffs.

### Bug fixes

- **Updates reach every file of the blueprint again:** the patterns of the files that belong to a project matched at any depth, so that `.github/blueprint.py`, the Dockerfile of the dev container and that of the social preview never changed with an update.
- A release follows only from changes for users: pull requests of the type `docs` no longer make one on their own; what they wrote under Unreleased comes with the next release.
- A Nextcloud app keeps its icons in `img/`, and its package leaves out the dev container, the hooks, the link check, `screenshots/` and `LICENSES/`, whose text `LICENSE` carries. psalm's JSON mapper (OSL-3.0) passes the dependency review as a tool of the checks. Dependabot leaves the major version of `nextcloud/ocp`, which follows the min-version of the app, to the maintainer and groups the major updates of composer.
- Every `.gitignore` keeps secrets out: `.env`, keys, certificates and credential files.
- The weekly release verification waits for the next release when the latest one is older than the release workflow of the blueprint.
- The first release no longer drops the introduction of the changelog.
- The settings bot no longer fails on the bypass list of the rulesets: the token of the release app gets the rulesets without it.
- `LICENSE` ends with one line break, also for the SPDX texts that end with a blank line, such as MIT.
