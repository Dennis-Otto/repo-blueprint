**GitHub repositories that test, release, secure and update themselves — from one `copier copy`.**

Repo Blueprint is a [Copier](https://copier.readthedocs.io/) template for seven kinds of projects: Home Assistant integrations, Nextcloud apps, GitHub Actions, Python and Node packages, container images and repositories without a build. A new repository starts with more than 30 workflows, and a bot brings it up to every new release of the blueprint.

- **Tested on every change.** `scripts/check.sh` runs the same checks on your machine and in the CI, with full coverage of the code. The PR coach explains every check that fails, and the fix bot commits what a command can fix.
- **Released and signed by a bot.** Merging the release pull request publishes the release with its SBOM and the signed provenance of SLSA Build Level 3, and then verifies it as its users can.
- **Secure from the first commit.** CodeQL, OpenSSF Scorecard, a secret scan and an audit of the workflows run from the start, every action is pinned to a commit hash, and about 90 to 100 answers of OpenSSF Best Practices are filled in.
- **Up to date by itself.** Renovate updates the dependencies, the settings bot keeps the settings as code, and the blueprint bot brings every release of the blueprint as a pull request that its checks test before it merges. Five public repositories follow it today.

## Start a repository

<!-- --8<-- [start:quick-start] -->

Git, Python 3.12 or later, [uv](https://docs.astral.sh/uv/) and GitHub CLI 2.48 or later, signed in as an administrator of the account or organization that will own the repository (`gh auth login`):

```sh
uvx --from copier==9.19.0 copier copy gh:Dennis-Otto/repo-blueprint my-project
cd my-project
python3 .github/blueprint.py create
```

![copier copy in the terminal: Copier clones the blueprint and asks for the name Paperless Sync, the repository, a description, the kind of project, Python package, and the owner Dennis-Otto, takes the defaults for the rest, including the release app, writes the files and names the one command after it; the new repository has its community files, its checks and its workflows, and a dry run of python3 .github/blueprint.py create shows the commands that make it the repository on GitHub](docs/images/copier-copy.gif)

With pipx in place of uv, the first line is `pipx run --spec copier==9.19.0 copier copy gh:Dennis-Otto/repo-blueprint my-project`, and a Copier of your own, Copier 9.8 or later, runs `copier copy gh:Dennis-Otto/repo-blueprint my-project`; on Windows, `py -3` runs Python in place of `python3`. Copying runs no code of the blueprint: the template has no tasks, migrations or Jinja extensions, so Copier needs no `--trust`.

Copier asks for the name, a one-sentence description, the kind of project, the GitHub account or organization that owns it, the license (MIT, MIT-0, BSD-3-Clause, Apache-2.0, GPL-3.0-or-later or AGPL-3.0-or-later), a few details of the kind and the release app of the owner, which may stay empty until the checklist has registered it. The homepage is the website that the Docs workflow publishes on GitHub Pages, unless you name another or none, and the README, the About box, the issue forms, the manifest of an integration and `appinfo/info.xml` of an app link it; each kind starts with topics of its own, such as `home-assistant, hacs` for an integration, which HACS needs to list it. Copier refuses an answer that would break a file: a description or a name with `"""`, `*/`, `]]>` or a backslash, which would end a docstring of Python, a comment of TypeScript or the CDATA of `appinfo/info.xml`, a Nextcloud app id that the App Store doesn't take, and topics that GitHub doesn't.

`create` makes the repository of the copy, with no checkout of the blueprint: every copy brings `blueprint.py` in `.github/`. It takes the owner and the name from the answers of Copier, runs `git init --initial-branch=main`, commits the files with a sign-off, creates the repository with `gh repo create` and pushes to it, public unless you add `--private`, then applies the settings as code and prints the checklist: what is left for a person, such as the release app and the secrets, and which steps are done. `--dry-run` prints the commands and runs none. A folder that pushes to a remote already is no new copy, and `create` refuses it. Every workflow runs on `main`, so `settings check` names a repository whose default branch has another name.

## Why Repo Blueprint

<!-- --8<-- [start:why] -->

- **Rather than a template repository of GitHub:** *Use this template* copies the files once, without the settings, and nothing follows them later. The blueprint sets the rulesets, the security and the environments as code, and brings every improvement as a pull request.
- **Rather than Cookiecutter and cruft:** the hooks of a Cookiecutter template run code on your machine, and `cruft update` waits until someone runs it. Copier runs none of the blueprint's code, so it needs no `--trust`; `blueprint.py create`, which you run next, is a file of the copy that you can read first. And the bot of the blueprint updates every repository by itself.
- **Rather than another Copier template,** such as copier-uv or scientific-python/cookie, which serve Python projects well: the blueprint brings one standard to Home Assistant, Nextcloud, GitHub Actions, Node and containers too, with signed releases of SLSA Build Level 3, SBOMs and VEX, and tests each release on every kind and on the real repositories before it rolls out.
- **Rather than projen:** projen writes the files of a project from code that runs at every synthesis, above all for TypeScript, AWS CDK and jsii. The blueprint needs no code of its own in the project: it keeps its own files current and leaves those of the project to you.

[The comparison](https://dennis-otto.github.io/repo-blueprint/compare.html) puts them side by side, also where another tool fits better.

## How a repository looks after itself

<!-- --8<-- [start:loop] -->

Every change, yours or a bot's, is a pull request that merges once every check passes, and the release bot makes a signed release of what reaches `main`; three bots keep the repository current on their own. In the pictures, blue is the blueprint and its bots, orange is you and what is yours, and green is what comes out.

| **App Store** | for a Nextcloud app: the registration of its id with its certificate, once, by hand | `register-app.yml` |
| **Upstream** | for a Nextcloud app, every week: when Nextcloud has a new major version, a pull request raises `max-version` and merges itself once every check, the end-to-end tests included, passes against it; started by hand as a dry run, it shows the pull request it would open and changes nothing | `upstream.yml` |
| **Area labels** | every pull request gets the labels of the areas whose files it changes, by the paths in `.github/labeler.yml`, which belongs to the project | `area-labels.yml` |
| **Branches** | the branch bot keeps the pull requests that wait for auto-merge in a line, Renovate's too, and brings one at a time up to date with `main`, right after a merge and when auto-merge is turned on, so that each merges once its checks pass and no check runs for a pull request that can't merge next | `update-branches.yml`, `blueprint.py next-branch` |

### From a change to a release

The title of a pull request decides the next version, and merging the release pull request does the rest:

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/from-a-change-to-a-release.dark.svg">
  <img src="docs/images/diagrams/from-a-change-to-a-release.svg" alt="From a change to a release: A pull request whose title is fix, feat or feat! merges into main once every check passes. The release bot keeps a release pull request with the next version and the text of the fragments and of Unreleased. Merging it signs its tag first, in the next run of the release bot, then builds the release in isolation once the tag checks out, signs and publishes it, delivers it and verifies it, then and every week. With BETA_CHANNEL, every change for users also becomes a beta.">
</picture>

A pull request describes what it changes for users in a file of its own, a fragment in `changelog.d/`, such as `changelog.d/dark-mode.md`, below the heading of its kind of change, such as `### Features`. A new file conflicts with nothing, so pull requests that run at the same time merge one after another, without a person who merges `main` into each of them, and a release no longer conflicts with the pull requests that wait. The check of the title, *conventional title*, checks each fragment of a pull request as the release takes it in and counts only a new one as its entry, `scripts/check.sh` checks every fragment that waits on `main` as well, and the release bot moves every fragment into the section of the release and deletes it in the same commit. A line under `## Unreleased` in `CHANGELOG.md` still works.

release-please reads the title of each merged pull request, not its whole description. The squash commit carries the description, and a line of it that the strict parser of release-please takes for a footer, such as `**[(Full` of the release notes that Renovate quotes, made it skip the commit in a run that passed, so that a fix waited for another release, which didn't list it. So before release-please runs, the release bot writes the title and the lines `Release-As:` and `BREAKING CHANGE:` of each pull request since the last release that can change it into the end of its description, as an override in an HTML comment that the page doesn't show; an edit that GitHub refuses is a warning, and release-please runs anyway. The release pull request changes only when its notes change; release-please rebuilt it in every run before, and every check of it started again (decision 0060 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).

The release bot writes the section of the next release from the fragments and the text of Unreleased into CHANGELOG.md of the release pull request, and deletes the fragments in the same commit. Merging it makes that section the notes of the release.">
</picture>

Each release describes what it ships in its SBOMs, as SPDX and as CycloneDX: the package that its users install, or the files of its tag without those that only check, test and document it, under the name of the repository and the version of the release. A scanner of a user reports only the advisories of what the release ships, and applies its OpenVEX document to them (decision 0034 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)):

### When the checks run

A check runs only where it can change a result, because an account of GitHub runs about 20 jobs at once, and each job that can't fail keeps a pull request waiting for a runner:

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/when-the-checks-run.dark.svg">
  <img src="docs/images/diagrams/when-the-checks-run.svg" alt="When the checks run: Every pull request runs the required checks, and the scanners of what it changes: zizmor for a workflow, OSV-Scanner for a lock file, fuzzing for Python code and the link check for a document. The release pull request, which changes only the changelog and the version, runs the required checks without the scanners. After a merge, main runs only what keeps a baseline or publishes. Every week, main runs the scanners in full, the secret scan of the whole history, the SBOM and the newest Python.">
</picture>

- **After a merge:** `main` takes a pull request only when it is up to date with it, so the merge gives `main` the files that the checks of the pull request passed. `main` runs only the tests, whose coverage the report of every pull request compares its own with, the analyses that code scanning compares with, and what publishes, such as the website and the release. Lint runs in the pull requests, the secret scan and the fuzzing there and every week, and the SBOM every week; every release has an SBOM of its own.
- **Few jobs, each with several checks:** each job of a push waits for a runner of its own, and the quick checks waited far longer than they worked. So one job, *lint*, runs every linter, the workflows, the licenses (REUSE, from its image), the Markdown, the issue assistant, the sign-off of every commit and the hints at the prose; *conventional title* checks the title and the entry in the changelog; *codeql* analyzes every language one after the other, each under the category of its alerts; and *home-assistant* runs HACS and hassfest. Each step runs also when one before it failed, so that a check reports everything at once, and the PR coach explains each check of a job that failed, with its own fix. A pull request of the blueprint starts eight jobs fewer, one of another kind of project seven to nine (decision 0027 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)); the old jobs run for one more release, until the settings bot of every repository requires the new ones.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/the-jobs-of-a-pull-request.dark.svg">
  <img src="docs/images/diagrams/the-jobs-of-a-pull-request.svg" alt="The jobs of a pull request: Each job of a push waits for a runner of its own, and the account runs about 20 jobs at once. So the quick checks share their jobs: lint runs every linter, the title job checks the title and the entry in the changelog, codeql analyzes every language under the category of its alerts, and home-assistant runs HACS and hassfest. Each step runs also when one before it failed, and the PR coach explains each check of a job that failed.">
</picture>

- **The release pull request** changes only the changelog and the version, which can't change what a scanner finds. In the blueprint, the required check *variants* stands for the variants and updates of every kind of project: it passes when each passed, or when none had to run, as in the release pull request.
- **The newest Python**, beta included, runs the checks of a Python project after every change of `main` and every week, in a workflow of its own that keeps the CI of `main` green. A new Python breaks every pull request alike, and none waits for it. A failure keeps an issue open, which the weekly run closes once the checks pass again.
- **The runners** are named with their version, `ubuntu-24.04`, not `ubuntu-latest`: GitHub moves that label to a new image one job at a time over weeks, as to Ubuntu 26.04 from 19 October 2026, so that the runs of one workflow would land on either image at random, with another Python, ShellCheck and Docker, and fail like a flaky test. In the blueprint, the Next runner workflow runs the variants on the next runner every week, and a failure keeps an issue open; once they pass there, a release of the blueprint moves every job to it. A workflow of your own, which an update leaves alone, keeps the runner it names: with `ubuntu-latest`, it moves with GitHub's label.

### When a check fails or stops

A check that a runner, a site or GitHub fails for a moment, or that a race of two runs cancels, needs no person: the bots after the checks run it once more, and leave red only what fails for a reason.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/when-a-check-fails-or-stops.dark.svg">
  <img src="docs/images/diagrams/when-a-check-fails-or-stops.svg" alt="When a check fails or stops: When a run of the checks or of the release ends, the bots after the checks look at how. Tests that failed or ran out of time at first run their failed jobs once more, unless the same jobs broke for the commit before; a job that passes then goes into the issue of flaky tests with its step, its test and its error, and one that fails again stays red. A required check that a late run for an older commit cancelled starts again. The release of a merge that failed runs its failed jobs once more, where they stopped.">
</picture>

- **A download that hangs starts again, before a bot is needed:** each download of the website gets 10 seconds to connect and 30 for each next part of the file, also one of the social plugin, which sets no limit of its own, and starts again twice. In the Variants, a setup of uv that doesn't end within two minutes gives way to a second one from the releases of uv on GitHub, and a container whose image failed to download starts again. Only what fails every attempt fails its step (decision 0061 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **Once, not again and again:** the flaky-test bot runs the failed jobs of the first attempt of a test run once more, and so does the bot for failed releases with a release that a merge started; a release that you already run again is yours, and the bot leaves it alone; the bot for cancelled checks starts a run twice at most. A job that GitHub stops at its time limit ends cancelled, not failed, and runs once more as well. A run that you or a newer run cancelled stays cancelled, even when a job that waits for the others failed because of it.
- **A failure that repeats is real:** when the same jobs broke for the commit before on the same branch, after they ran once more, the jobs don't run again, so that a broken test doesn't keep a runner busy for nothing.
- **The issue of flaky tests** gets a table for each run that passed when it ran again: each job that failed at first, with a link to its log, the step that broke, the tests that pytest names in the log, and the first error. A name or a line of a log is written as plain code, so a pull request can't end the table or mention anybody with it, and the branch of a fork, which it names as it likes, isn't named.
- **The quick checks run once for each commit:** the title and the changelog, the dependency review, the secret scan, the area labels and the website. A late run for an older commit, such as one that an edit of the release pull request starts while release-please pushes to it, no longer cancels them for the head. The checks that take minutes, the tests, Lint, CodeQL and the variants, still cancel the run for an older commit; the bot for cancelled checks repairs a race there.
- **Other workflows of tests** that a repository has, such as visual tests, join the CI and Docker E2E with `copier update --data "test_workflows=Visual check, Screenshot bot"`.
- **The link check of a pull request** reads the documents that it changes, and every document when it changes the rules, or moves or deletes a file that a document may link to. lychee keeps the answers of the sites for a day and asks again for a link that failed, so that a site that is down for a moment fails only the pull requests that link to it.

### Pull requests that wait for auto-merge

`main` takes a pull request only when it is up to date with it, so only one of the pull requests that wait for auto-merge can merge next, and each merge leaves the others behind again. Bringing all of them up to date after every merge ran every check of each of them for the one that merged: about n²/2 runs of the checks for n pull requests, which kept the runners of the account busy and made every pull request wait longer. The branch bot keeps them in a line instead, as Kodiak and Bulldozer do, in the order in which their auto-merge was turned on, and brings only the first one up to date that can merge:

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/the-line-of-the-branch-bot.dark.svg">
  <img src="docs/images/diagrams/the-line-of-the-branch-bot.svg" alt="The line of the branch bot: A merge into main, auto-merge turned on or off, or a required check of a pull request that fails starts the branch bot. It takes the pull requests that wait for auto-merge in the order in which it was turned on. One that conflicts with main gets the label merge-conflict and one comment. While the checks of one that is up to date run, the others wait in line. Otherwise one whose required check failed waits for a fix, and the bot brings the first other one that is behind up to date, as the release app. Its checks run, and once they pass it merges, which starts the bot again for the next one.">
</picture>

- **One at a time:** while the checks of the pull request at the front run, the bot brings no other one up to date. Its merge starts the next run of the bot, which brings the next one up to date, so they still merge one after the other without a person. Each pull request had to run its checks again after the merge before it anyway, so the line delays a merge only when the pull request before it fails, by one run of the checks, and with fewer jobs at once the runners of the account take every job sooner.
- **At once:** turning auto-merge on starts the bot, so a pull request that is behind and first in the line is brought up to date within about a minute; a merge into `main`, turning auto-merge off and a required check that fails start it as well; a failed test only once it fails again, since the bots after the checks run it once more. The schedule, every six hours, is only a safety net, since GitHub runs schedules as it can, often hours late.
- **A failed check leaves its place:** a pull request whose required check failed waits for a fix, and the next one moves up; so does one that is up to date and whose checks ended, but that something else holds up, such as a conversation to resolve. One that waits for a review or has a conversation to resolve, where the rules of `main` want them resolved, isn't brought up to date either, since it couldn't merge after its checks. A check that isn't required holds up nothing. After a fix, the pull request takes its place again in the next run of the bot.
- **Conflicts and errors:** a pull request that conflicts with `main` gets the label `merge-conflict` and one comment, and the next one moves up; Renovate builds a branch of its own that conflicts anew. An update that GitHub refuses for a conflict is a conflict too, and one that someone pushed to since the list runs its checks anyway, so it is the one in flight. Any other request that GitHub refuses is a warning about that pull request, and the bot goes on with the next one; the run then fails, so that the bot-health bot hears of it. A run for auto-merge turned on or off shows as a check of that pull request, and the bot-health bot ignores such runs, so it passes with the warnings, and the next run reports them again.
- **Across changes of workflows:** bringing a pull request up to date merges `main` into its branch, and once `main` changed a workflow since, GitHub takes that merge only from a token that may change workflows. The bot's token of the release app may, as Renovate's does, so such a pull request, such as one of Renovate that updates the actions, comes up to date like any other instead of with a warning in every run.
- **The summary of every run** shows the line: which pull request the bot brought up to date or runs its checks, and why each other one waits. `blueprint.py next-branch` holds the logic, and the workflow checks out only `main` for it, also when auto-merge is turned on.

### The PR coach

A check that fails explains itself, to you and to everyone who sends a pull request, also from a fork: what it found, why that matters and how to fix it, with the commands to run.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/the-pr-coach.dark.svg">
  <img src="docs/images/diagrams/the-pr-coach.svg" alt="The PR coach: A push to a pull request, also one from a fork, runs the checks. A check that fails explains itself in its summary and as its annotation, from the explanations of .github/checks.toml and .github/checks.project.toml. After the checks, the PR coach reads the check runs and their annotations from the API, without running any code of the pull request, and keeps one comment on the pull request up to date: a section for each check that failed, with the problem, why it matters, the fix and its commands. You push the fix, and once every check passes, the comment says so.">
</picture>

- **In the check:** a job that fails ends with a step that writes the explanation of its check into the summary and as an annotation, which the list of the checks shows. `scripts/check.sh` does the same for the step that stopped it, on your machine as well, and in the CI the files of the pull request show the problems of the text files, of Ruff and of actionlint at their lines.
- **One comment, also for a fork:** the runs of a pull request from a fork can't write to it, so the coach runs after the checks, in the repository itself. It keeps one comment with a section for each check that failed, the findings of its annotations and a link to its log, and a suggested title when the title is no Conventional Commit. Once every check passes, a comment that listed failures turns into a short all-clear.
- **Safe with any pull request:** the coach reads the check runs and their annotations from the API and checks out only the explanations of the default branch; it runs no code of the pull request. Text that a pull request controls, such as a file name, a message or a title, appears only as code, cut to a short length, so it can't mention anybody, link anywhere or break the comment.
- **Every check explains itself:** the explanations are in `.github/checks.toml`, which the blueprint keeps current, and those of a project's own checks in `.github/checks.project.toml`, which belongs to the project and wins. A test of the blueprint fails for a required check or a step of `scripts/check.sh` without an explanation, and `python3 .github/blueprint.py coach verify` lists them in a repository.
- **What the pull request makes:** on a pull request of a person, the same comment says, after the checks that failed, what the merge does to the next release, such as *makes the next release 0.13.0, a minor release after 0.12.0*, from the title, a `BREAKING CHANGE:` or `Release-As:` line of the description and the release-please files of `main`; the entry that it adds to the changelog, as the release takes it in; the coverage of its tests against that of `main`, file by file; and, when it changes the website, a link to the website that the check *docs* built, kept for a week as the artifact `website`, with the address of each page that it changes. A pull request whose checks pass gets the comment only when it has something of this to say, and one of a bot only for a check that failed (decision 0030 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/the-report-of-a-pull-request.dark.svg">
  <img src="docs/images/diagrams/the-report-of-a-pull-request.svg" alt="The report of a pull request: A push to a pull request of a person runs the checks, which keep the coverage of the tests and the website that they built as artifacts. After the checks, the PR coach reads the check runs, the title and description, the files, the coverage reports of the pull request and of main and the artifact website from the API, with the release-please files and mkdocs.yml of main, and runs no code of the pull request. It keeps one comment: the checks that failed, the next version with the entry of the changelog, the coverage file by file, and the website with the pages that change. A pull request whose checks pass gets it only when it has something of this to say.">

### Pull requests fix themselves

Fix first, explain second: what a command can fix of a check that failed, the pull request fixes by itself, also a pull request of Renovate, and `main` too.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/pull-requests-fix-themselves.dark.svg">
  <img src="docs/images/diagrams/pull-requests-fix-themselves.svg" alt="Pull requests fix themselves: A check fails. Where a command fixes what it found, such as the format of the code, the whitespace of a text file or the rules of markdownlint, the job of the check runs the commands of autofix from .github/checks.toml and keeps the files that they changed. After the checks, the fix bot takes these files as data, only text files that the commit has: on a pull request from a branch of the repository, also one of Renovate, it commits them as one commit onto the branch, and the checks run again; on a pull request from a fork, it suggests them at their lines; on main, it keeps one pull request from bot/self-heal that merges itself. What no command fixes, the PR coach explains.">
</picture>

- **The check fixes:** each explanation of `.github/checks.toml` says in `autofix` which commands fix what its check finds, or why no command can; a test of the blueprint fails for one that doesn't say. When a check fails, its job runs those commands on the head of the pull request, with the tools that it installed already: the text files, the pages in one column and Ruff or php-cs-fixer for `scripts/check.sh`, markdownlint for the Markdown. It keeps the files that they changed as an artifact.
- **One commit on a branch of the repository:** once the checks of the commit that fix have ended, the fix bot commits all their fixes as one commit onto the branch, as the release app, with its sign-off, and the checks run again; the comment of the PR coach names the files. This works on the branches of Renovate and the other bots as well, so that an update of a formatter stays green and merges itself.
- **Suggestions on a fork:** no bot pushes to a fork, so the bot suggests the fixes at their lines of the pull request, ten at most in one review and none twice; **Commit suggestion** takes one. A fix that no suggestion shows, such as line endings, names its file, and the PR coach the command.
- **main heals itself:** when a check of `main` fails with fixes, one pull request from `bot/self-heal` holds them and merges itself once every check passes; the bot closes it once `main` needs none, and a failure of the bot keeps one issue open.
- **Safe with any pull request:** the bot runs nothing of a pull request with a token that can write. It takes the fixes as data, with `blueprint.py` of `main`, and lets through only text files that the commit has already, by plain paths, outside `.git` and the workflows. It commits at most twice in a row (once more for a check that ends later), never a third time, and a pull request with the label `no-bot-fixes` gets no commit.
- **On your machine:** `python3 .github/blueprint.py fix run` runs the commands of every step of `scripts/check.sh`, and `python3 .github/blueprint.py fix text` fixes the text files alone.

### Diagrams that fix themselves

The GitHub app, HACS, the Nextcloud App Store, PyPI and the e-mails of GitHub draw no Mermaid and show a `mermaid` block as code. So every diagram is a picture of its source, and the bots keep it that way without a person.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/how-the-diagrams-fix-themselves.dark.svg">
  <img src="docs/images/diagrams/how-the-diagrams-fix-themselves.svg" alt="How the diagrams fix themselves: A pull request that adds a mermaid block or changes a diagram, and Renovate with a new version of mermaid-cli, run the check diagrams, which draws the diagrams anew. - **A pull request fixes itself:** when a pull request from a branch of the repository adds a `mermaid` block or changes a source, the check *diagrams* runs `bash scripts/diagrams.sh --extract`, and the diagram bot commits the sources and pictures it made onto the branch, as the release app, with a comment that names the pages it changed. The checks of that commit pass. A pull request from a fork gets the failing check, whose summary lists the files and the command.

When something is missing, such as the blocks of a repository right after the update of the blueprint, it keeps one pull request from the branch `bot/diagrams` with the fix, which merges itself once every check passes, and closes it when `main` is fixed otherwise. A failed run opens an issue, which the weekly run closes once the bot passes again.
- **A new renderer draws anew:** Renovate keeps the image of mermaid-cli in `scripts/diagrams.sh` current; the check draws the pictures again on its branch, and the diagram bot commits them, so the update still merges on its own.
- **Nothing but diagrams:** the bot runs no code of a pull request. It commits only sources in `docs/diagrams/`, SVG pictures in `docs/images/diagrams/` and pages of Markdown, by plain paths, onto the very commit that the check drew, and only for a branch of the repository.

### Screenshots that renew themselves

The pictures of a project, in its README, on its website and in the stores, show it as it was when someone last took them. The screenshot bot takes them again whenever what they show can have changed, and changes a file only when its pixels change.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/how-the-screenshots-renew-themselves.dark.svg">
  <img src="docs/images/diagrams/how-the-screenshots-renew-themselves.svg" alt="How the screenshots renew themselves: After a change of main that touches a file of .github/screenshots-paths.txt, after every release, every week and on demand, the screenshot bot looks for scripts/screenshots.sh; without it, the bot renders nothing. The script renders the pictures without secrets, and each picture whose pixels stayed the same keeps its committed file. When pixels changed, one pull request from bot/screenshots holds the new pictures and merges itself once every check passes; when main looks as rendered, the bot closes it. So every picture shows the project as it is.">
</picture>

- **A script turns it on:** every repository has the Screenshots workflow (`screenshot-bot.yml`), which renders nothing until the project has `scripts/screenshots.sh`. The script renders the pictures in place, wherever the documentation, the stores or the social preview take them from; a new repository starts with one that renders the social preview, `.github/social-preview.png`. `.github/screenshots-paths.txt` lists the files whose change can change the pictures, as the paths of a workflow. Both belong to the project, so an update of the blueprint leaves them alone.
- **When it renders:** after a change of `main` that touches a file of the list, the script or the list, after every release, whose version a picture may show, every Friday and on demand. It runs the script without secrets, with a token that only reads, with Docker and with the tools of the website in `.venv-docs`, as `CONTRIBUTING.md` sets them up, for a script that photographs its pages.
- **Only pixels count:** `blueprint.py screenshots keep` compares each picture that the script changed with the one of `main` by its pixels, frame by frame for an animation, and gives each one that looks the same its committed file back, so a new encoder, browser or runner changes no file. A frame that repeats the one before counts once, the time that each frame shows not at all, and a fully transparent pixel has no color.
- **One pull request that merges itself:** when pixels changed, the bot keeps one pull request from `bot/screenshots`, *docs: update the screenshots*, as the release app, with a table of the pictures and the share of the pixels that changed in each. It merges itself once every check passes, the bot keeps it current with `main`, and closes it when `main` looks as rendered without it. A changed social preview gets a reminder to upload it under **Settings → General → Social preview**. Without the release app, the run warns and keeps the pictures as an artifact for three days.
- **Nothing but pictures:** the job with the release app runs nothing of the script. It takes PNG, JPEG, GIF and WebP files whose content starts as their kind does, by plain paths, outside `.git` and the workflows, and leaves out every other file that the script changed, which the description of the pull request names. A large set of pictures goes in several commits. A failed run keeps an issue of the bot-health bot open until a run passes again.
- **On your machine:** `bash scripts/screenshots.sh`, then `python3 .github/blueprint.py screenshots restore`, which gives every picture that looks the same its committed file back and lists the others. It compares the pixels with Pillow, which `python3 -m pip install --require-hashes -r .github/screenshots-requirements.txt` installs.
- **The blueprint's own pictures renew themselves too:** after a release that changed the questions, the template, the workflows or the dashboard, as `.github/docs-pictures/paths.txt` lists them, and on demand, the Docs pictures workflow runs `scripts/docs-pictures.sh`, which records `copier copy` and photographs the dashboard, and keeps one pull request from `bot/pictures`, *docs: renew the pictures*, in the same way.

### Mutation tests

The mutation tests show the lines that the tests run but don't check: every Saturday they change the code in thousands of small ways, the mutants, and run the tests that cover each one. A mutant that no test notices survives.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/how-the-mutation-tests-run.dark.svg">
  <img src="docs/images/diagrams/how-the-mutation-tests-run.svg" alt="How the mutation tests run: Every Saturday, on demand, and for a pull request that changes how they run, the Mutation workflow runs the mutants. For Python, the plan splits the code into parts of about the same number of mutants, and mutmut runs each part in a job of its own, in a copy of the repository and without the tests marked mutation_unsafe; Infection changes the PHP of a Nextcloud app, with the bootstrap of its tests. The summary shows one score and first the survivors that change the logic, with their changes, the artifact keeps them and the dashboard shows the score. When the score of the default branch drops below that of the run before, one issue opens, which closes once a run is back. A run that measured nothing fails and names the tests that failed without any mutant.">
</picture>

- **The score is the share of the mutants that a test noticed,** among those of the code that the tests run: for mutmut the killed among the killed and the survived, for Infection its *Covered Code MSI*. The dashboard shows it as *mutants caught*.
- **The survivors that change the logic come first:** the summary sorts each survivor of mutmut by its change, as `mutmut show` prints it. First come those that change the logic, an operator, a comparison, a number or a condition, which a test should notice, by function, the most first, each with its change; then a table of the functions whose survivors pass None or leave out an argument, and one of those that change only a text, such as a message, a help or a log line. The *score of the logic* counts only the survivors of the logic, and `survivors.md` of the artifact *mutation* has the change of every survivor. A line whose text no test needs to check gets `# pragma: no mutate`, and mutmut leaves it alone.
- **A large project runs in parts:** the job *plan* estimates the mutants of each function and splits the code into parts of about 3,000 mutants, at most eight: whole modules, and the functions of a module larger than a part. Each part is a job of its own that runs only its mutants, so that a project of 10,000 mutants finishes within the six hours of a job of GitHub, and the job *report* puts the parts together into one score. The variable `MUTATION_PARTS` of the repository sets the number of parts in place of the estimate.
- **A drop of the score opens one issue:** the report compares a complete run of the default branch with the run before it, from `mutation.json` of its artifact. When the score or the score of the logic falls by more than half a point, it opens the issue *Mutation score dropped*, with both scores and the functions that gained survivors of the logic, keeps it current while the score stays below, and closes it once a run is back at the score before the drop. A run that stopped at its time limit or lost a part is compared with no other.
- **A low score fails nothing,** not even below a minimum that the project's own configuration sets, but a run in which no mutant ran does: mutmut runs every test once without a mutant first, and when one fails there, the summary names it under *The tests fail without any mutant*, with the end of the output of mutmut or Infection. A broken configuration or a test that can't run in the copy shows up in the week it breaks, and the bot-health bot opens its issue.
- **A pull request that changes how the mutants run,** `mutation.yml` or the pinned mutmut, tries them, each part for 25 minutes, and shows a defect as a red check before the weekly run. The check isn't required, so a pull request that merges itself, such as an update of mutmut, doesn't wait for it: its red check is a warning to read.
- **mutmut runs the tests in a copy of the repository,** `mutants/`, with the changed code and without Git. A test that can't work there, because it reads the code as text, asks Git or starts the tool, which in the copy is the code with the mutants, gets the marker `@pytest.mark.mutation_unsafe`, and the mutation tests leave it out; the `pyproject.toml` of a new Python project registers the marker, and `MUTANT_UNDER_TEST`, which mutmut sets, tells a test that it runs there. mutmut learns which tests cover a function by running them all in one process: a test of a function with a cache of `functools`, such as `@functools.cache`, clears it with `cache_clear()`, so that it runs the code and not the result that another test left.
- **mutmut copies a whole function for each of its mutants,** so a long function with many of them, such as a parser with the options of every command, makes a module of many megabytes, which each part and every test that starts the tool in the copy compile for minutes, past their time limits. Such a function is split into smaller ones: the parser of `blueprint.py` adds each group of its commands in a function of its own, and a test of the blueprint fails when a function of its code would make more than 50,000 lines of copies.
- **A configuration of the project wins:** a `[tool.mutmut]` table in `pyproject.toml` or a `[mutmut]` section in `setup.cfg` for mutmut, an `infection.json5` for Infection. Without one, mutmut mutates `custom_components/`, `src/` or the modules and packages of the root, and Infection mutates `lib/` on PHP 8.3, with `tests/bootstrap.php`, which loads the classes of Nextcloud. The plan follows `source_paths`, `only_mutate` and `do_not_mutate` of mutmut.

### When a bot fails

GitHub mails the failure of a scheduled run only to whoever last changed its schedule, and that of another run to whoever started it, in these repositories the release app for most runs: a red bot used to show only in the Actions tab, as when Findings, Mutation and Renovate failed for days. The bot-health bot (`bot-health.yml`) makes each such failure an issue, and closes it once the bot passes again.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/what-the-bot-health-bot-does-when-a-bot-fails.dark.svg">
  <img src="docs/images/diagrams/what-the-bot-health-bot-does-when-a-bot-fails.svg" alt="What the bot-health bot does when a bot fails: When a run of a bot or a scheduled workflow ends on the default branch, the bot-health bot looks at it; runs of pull requests start nothing. A first failure that a second try can fix runs its failed jobs once more. A failure that stays opens one issue for the workflow, or updates it, with the failed jobs, their steps and their first errors. A run that passes closes the issue. Every night, the bot looks at the latest run of every workflow, in case GitHub lost an event, and starts a workflow whose schedule GitHub missed or switched off.">
</picture>

- **One issue per workflow,** titled like *Findings fails on main*, with the labels `bot-failure` and `maintenance`. It names the latest failed run, its attempt and its trigger, and a table of the failed jobs with the step that failed and the first error of each, from the annotations of the run. A later failure in the same place only updates it, without a notification; a failure in another job or step adds a comment. The next run that passes closes it with a link to that run.
- **A second try only where it can pass:** a first failure runs its failed jobs once more, as the flaky-test bot does for the tests, unless another bot already did. Findings, which fails while an alert is open, Mutation, which takes hours to measure the same again, and the property tests and the fuzzing, which failed on an input that they found, are reported at once. A run that GitHub couldn't start, because its workflow file is invalid, too.
- **Which runs count:** those of the bots and scheduled workflows that `bot-health.yml` lists, on the default branch, from a schedule, a push, a start by hand or another workflow, never from a pull request or a fork. The checks that run in pull requests, such as the CI, the website or CodeQL, and the workflows of the project count in the nightly look, which takes the latest finished run of every workflow on the default branch, so that none of their runs for a pull request starts a run of the bot. GitHub gives a run that the end of a check of a pull request starts, as it starts After the checks, the default branch too, so the nightly look counts only the other runs of such a workflow. The Diagrams workflow, Newest Python and the Next runner keep an issue of their own.
- **Missed schedules:** GitHub runs a schedule late at busy times, sometimes not at all, and switches the schedules of a repository off after 60 days without activity. Every night, a workflow whose last run is older than the latest time of its schedule, six hours ago or more, starts by hand, at most four a night so that the pull requests keep their runners; Findings, Issue lifecycle and the Issue assistant sync of the blueprint start with `dry_run` off, as their schedule runs them. A schedule that GitHub switched off is switched on again.
- **Renovate's problems:** Renovate, which runs in the blueprint for the repositories of its owner and in a repository of any other owner for that one, logs a lock file that it can't read as a warning, without failing. The Renovate workflow keeps one issue, *Renovate logs problems*, with the warnings and errors of its latest run that had any, by repository, and closes it after three runs in a row without one. A public issue names public repositories only.
- The bot reads runs, jobs and annotations and writes issues with the `GITHUB_TOKEN` of its job, and checks out only the default branch, never the code of a pull request. A repository whose `.github/labels.toml`, which belongs to the project, lacks `bot-failure` gets the label from the bot; add it to the file to keep its color and description in one place.

Every bot starts from an event, such as a merge into `main`, a pull request or the end of a check. A merge that auto-merge does with the token of a workflow starts no workflow, so Renovate, Dependabot's updates of the dev container, the release bot and the branch bot merge as the release app, and every merge into `main` is a push that starts the release bot and the branch bot at once:

- **Schedules are only a safety net:** GitHub runs them as it can, in bursts every four to seven hours, often hours late and sometimes not at all. From 7 to 12 October 2026, it ran the hourly schedule of the release bot of the blueprint 21 times instead of about 117, and the half-hourly one of the branch bot 22 times instead of about 240, and none of 279 scheduled runs of the release bot made a release. So the release bot looks once a day on its schedule and the branch bot every six hours, the bot-health bot starts a workflow whose schedule GitHub missed, no schedule starts on the full hour, when GitHub has the most to start, and no comment of a workflow promises a time (decision 0033 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).

All the schedules of a project and the runs that they start now come to about 20 a day, about 600 a month. The checks of the pull requests cost more; decisions 0009 and 0027 keep their jobs few.

## Set up a repository

What a person does once: the release app of the account and its defaults, the secrets and the delivery of each repository, and the way an existing repository takes the blueprint.

### Your own account

The blueprint works for every account and organization on GitHub, and a repository made from it names nothing of the blueprint's owner but the links to the blueprint. Each owner brings two things of their own:

- **A release app,** once for all of their repositories. The bots act as a GitHub App of the owner: its token starts the checks of the release and update pull requests, may change workflows and creates the release tags, which the token of a job can't. Only the owner of an app has its private key, so the blueprint can't lend its own. Copy the blueprint with the question of the release app left empty, and `checklist` starts with a link that registers the app on your account or organization, with its name and permissions filled in and without a webhook; set *Variables* by hand, which the link can't fill in. Create the app, generate a private key on its settings page, and name the app in the answers of the blueprint, with the name in its address and the Client ID and App ID of that page:

  ```sh
  copier update --defaults --vcs-ref=:current: --data release_app=NAME --data release_app_client_id=CLIENT_ID --data release_app_id=APP_ID
  ```

  Commit the update: `.github/repository.toml` names the app, only it may create release tags, and `settings apply` and `checklist` then ask for its private key and its installation on the repository. Until then the blueprint bot and the release bot say in their summary what is missing, rather than fail at a token.
- **Your defaults,** so that every new repository asks only what is new. Copier's [settings file](https://copier.readthedocs.io/en/stable/settings/) takes the answers that stay the same, on Windows in `%LOCALAPPDATA%\copier\settings.yml` and on macOS in `~/Library/Application Support/copier/settings.yml`:

  ```yaml
  # ~/.config/copier/settings.yml, or the file that COPIER_SETTINGS_PATH names
  defaults:
    owner: octo-org
    author: Octo Org
    release_app: octo-org-release-automation
    release_app_client_id: Iv23liExample
    release_app_id: "123456"
  ```

### Once per repository

- **The release app** of the owner opens the release and update pull requests, so that their checks run. Register it once for the account, as [your own account](#your-own-account) shows, install it on the repository, and set its private key as the secret `RELEASE_AUTOMATION_PRIVATE_KEY` of the environment `release`. The app needs the permissions *Actions*, *Administration*, *Checks*, *Commit statuses*, *Contents*, *Issues*, *Pages*, *Pull requests*, *Variables* and *Workflows* (read and write), and *Dependabot alerts*, *Environments* and *Secrets* (read): with them the settings bot applies the settings as code, Renovate updates the dependencies, and the rollout of the blueprint starts the blueprint bot of every repository after a release. Renovate gets a token without *Administration*. The release workflow creates every release tag with the app, and the ruleset *Release tag creation* lets nobody else create one; the variables `RELEASE_APP`, `RELEASE_AUTOMATION_CLIENT_ID` and `RELEASE_AUTOMATION_APP_ID` in `.github/repository.toml` name the app, from the answers `release_app`, `release_app_client_id` and `release_app_id`, and a project with another app than its answers name sets them in `.github/repository.project.toml`.
- **The issue assistant** needs `CLAUDE_CODE_OAUTH_TOKEN` in the environment `issue-assistant`, unless the answer `issue_assistant_ai` switched its AI off.
- **Delivery:** trusted publishing on PyPI or npm, the app certificate of a Nextcloud app, or the HACS submission, as the checklist says.
- **OpenSSF Best Practices:** add the project on [bestpractices.dev](https://www.bestpractices.dev/en/projects/new) with the URL of the repository. It proposes the answers of `.bestpractices.json`, about 90 to 100 of the badge and of the OSPS Baseline that the blueprint guarantees for the kind of project, each with the file that shows it; *Save (and continue) 🤖* takes them in on each level, also after an update of the file. Answer the rest, what only your software and your people can say, and add both badges to the README, as the checklist shows.

`checklist` prints the `gh secret set` commands; the value is typed into the prompt of the GitHub CLI and never appears anywhere else.

### An existing repository

An existing repository takes the blueprint on a branch, in one pull request:

1. `copier copy --overwrite --vcs-ref vX.Y.Z --data sample_code=false gh:Dennis-Otto/repo-blueprint .` with the answers that fit the repository, without the sample code and tests of a new one, such as its description, topics and homepage as they are on GitHub, so that `settings apply` changes nothing there. The files of the project (README, changelog, code, tests, manifests, labels, issue forms, icons) stay as they are.
2. Look at the diff of every file of the blueprint and put back what belongs to the project only: sections of SECURITY.md or CONTRIBUTING.md, rules of Renovate (in `.github/renovate.json5`), hosts of the issue assistant, ignore rules. `copier update` keeps these changes from then on.
3. Write the version of the latest release into `version.txt` and `.release-please-manifest.json`, start `CHANGELOG.md` with `## Unreleased`, and give `.github/labels.toml` the labels of the bots (`autorelease: pending`, `autorelease: tagged`, `merge-conflict`, `maintenance`, `bot-failure`, `docker`).
4. Put the checks of the project alone, such as its end-to-end tests, into `.github/repository.project.toml` and `scripts/check-project.sh`, with the patterns of the actions that its own workflows run, which `blueprint.py settings check` names; remove the workflows, scripts and tests that the blueprint replaces, and delete files of the template that the project doesn't need, such as a sample test. A repository without `docs/` has no website until it writes `docs/index.md`; `mkdocs.yml` shows how German pages join it.
5. Open the pull request. Once its new checks pass, `blueprint.py settings apply` switches the required checks, the variables and the labels, and the pull request can merge.

The configuration of the checks belongs to the blueprint and looks for the code where a new project of the same kind has it. Every file it names comes with the blueprint, also without the sample code:

| Kind | Code | Tests | From the blueprint |
| --- | --- | --- | --- |
| Nextcloud app | `lib/` | PHPUnit tests in `tests/Unit/` | `psalm.xml` and `phpunit.xml`, with the `tests/bootstrap.php` and `tests/stubs/` that they load |
| Node package | `src/`, built into `dist/` | `test/`, typechecked by `tsconfig.json`; the `npm test` of a new project runs `test/**/*.test.ts` | `tsconfig.json` and `tsconfig.build.json`, which need `typescript` and `@types/node` in the `package.json` of the project, and `biome.jsonc`, whose step *Lint and format* runs once `@biomejs/biome` is there too |

The other kinds set these places in files of their own, such as `pyproject.toml`. What lies in `tests/` belongs to the project: the copy and every update add only the files that are missing there, so an app with its own bootstrap keeps it.

## Settings as code

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/the-settings-as-code.dark.svg">
  <img src="docs/images/diagrams/the-settings-as-code.svg" alt="The settings as code: The settings of a repository live in .github/repository.toml, with those of the project alone and the labels. blueprint.py settings apply, run by an administrator, and the settings bot, after every change and every week, make GitHub match them; settings check shows what differs.">
</picture>

`.github/repository.toml` holds the settings of a repository; `blueprint.py settings check` compares them with GitHub and `settings apply` makes GitHub match:

- **Repository:** squash merges with the title of the pull request, auto-merge, branch updates, deleted branches, signed-off web commits, no wiki or projects.
- **Security:** immutable releases, private vulnerability reporting, Dependabot alerts with the security updates of Renovate, secret scanning with push protection and with the generic patterns of private keys, connection strings and passwords.
- **Actions:** read-only tokens by default, no approvals by workflows, actions pinned to commit hashes, only the actions of GitHub and those of the list in `[actions.selected]`, approval for the workflows of every outside contributor. `settings check` follows every action that a workflow runs, also inside a composite action or a reusable workflow, and names each one that the list lacks; until it is listed, `settings apply` only adds to the list on GitHub, so no workflow stops.
- **Rulesets:** *Protect main* (pull requests only, squashed, linear history, every required check, no new alert of CodeQL of high or critical severity, no deletion or force push), *Release tags* (`v*.*.*` never moves) and *Release tag creation* (only the release app, whose App ID `RELEASE_AUTOMATION_APP_ID` names, creates a `v*.*.*` tag, which the release workflow signs).
- **Variables and environments:** `PUBLISH_TO`, the release app (`RELEASE_APP`, `RELEASE_AUTOMATION_CLIENT_ID` and `RELEASE_AUTOMATION_APP_ID`), and environments that only `main` may use, with the secrets they need.
- **Pages:** GitHub Pages publishes the website that the Docs workflow builds.

`blueprint.py` needs Python 3.12 and GitHub CLI 2.48 or later, signed in as an administrator, and nothing else. It never reads or prints the value of a secret. Every repository has a copy in `.github/blueprint.py` and `.github/blueprint/`, and the settings bot (`settings.yml`) compares its settings with the settings as code every week, after every change of them and after every update of its own code, so that no repository drifts. A change that GitHub refuses fails the run, which names the part and the permission of the release app that it needs; after a gateway that timed out or a rate limit, a request tries once more, after the wait that GitHub asks for (decision 0036 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)). A switch of the security that GitHub doesn't offer for the repository, or that it accepts and keeps off, as it does with the generic patterns of secret scanning on a repository of a user, fails nothing: the run names it with the line of `.github/repository.project.toml` that stops asking for it, and asks again every time, so that a repository whose plan gains the switch gets it (decision 0055).

## Updates

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/how-an-update-of-the-blueprint-arrives.dark.svg">
  <img src="docs/images/diagrams/how-an-update-of-the-blueprint-arrives.svg" alt="How an update of the blueprint arrives: Right after every release of the blueprint, and every week, the blueprint bot verifies the latest published release first. The blueprint bot (`blueprint-update.yml`) runs `copier update` every week, and right after every release of the blueprint, whose Rollout workflow starts it in every repository of the release app. It takes the latest published release of the blueprint that `.copier-answers.yml` names, a fork of it perhaps, never a tag whose release is still a draft. Before it updates, it verifies the release: the release must be immutable, its tag must point at a commit of the blueprint's `main` no older than the version the repository has, and the release workflow of the blueprint must have signed the tag (gitsign, as [SECURITY.md](https://github.com/Dennis-Otto/repo-blueprint/blob/main/SECURITY.md#verify-a-release) shows). Any other release fails the run before Copier renders anything, with the reason and what to do in the summary of the run, so a tag that someone else pushed reaches no repository; when GitHub or Sigstore doesn't answer, the bot asks three times and then waits for its next run. A blueprint that isn't on GitHub can't be verified, so the bot doesn't update from one. The bot keeps one pull request on the branch `blueprint/update`: a newer release moves that pull request on, with its number and its auto-merge, instead of replacing it. Its description shows the notes of every release that it brings, the releases that it skipped too, each in a section of its own to open, the newest first, with references to the issues of the blueprint that stay links to them, a link that compares the version before with the new one, and the files that it changes; with conflicts, a checklist of the files to resolve and how; and whether it merges itself, and how `BLUEPRINT_AUTOMERGE` changes that. Without conflicts it merges itself once every check passes. Conflicts stay in it as markers for the maintainer, in the files that the update touched; they turn its auto-merge off and add the label `merge-conflict`. The repository variable `BLUEPRINT_AUTOMERGE` set to `off` makes every update wait for the maintainer. Run it by hand under *Actions → Blueprint update*, or locally with the Copier that it uses, in a virtual environment: `pip install --require-hashes -r .github/copier-requirements.txt && copier update --defaults --conflict inline`.

The Rollout workflow of the blueprint brings each release to the repositories of the release app one after the other, those with the quickest checks first: it starts the blueprint bot of a repository and gives the bot and the checks of its update pull request up to 15 minutes before it starts the next one, so that the update pull requests don't all wait for the runners of the account at once. A repository whose bot it can't start, or whose bot fails, fails the run by its name; the others still get the release. It rolls out every release that a run of the Release workflow published, whether the merge of the release pull request started that run, the daily schedule or a start by hand; a release that the run of a later merge finished, because the run of its own merge was lost, waits for a start by hand (Actions → Rollout) or the weekly run of the bots. Started by hand itself, it rolls out the latest release. Rollouts of releases that come close together overlap, but never in the same repository: there, the newer release takes the place of an older one that still waits. Every release goes out right after it is verified, and the weekly run stays as a safety net, so that a fix reaches every repository within minutes instead of a week (decisions 0052 and 0010 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).

Once you commit to the branch of the pull request, to resolve the markers for example, the bot leaves the branch to you: when a newer release is out, it says so in one comment, and after you merge or close the pull request, its next run brings the rest. A merge of `main` with the button *Update branch* doesn't count as your commit, and an auto-merge that you switch off stays off. An update that only records a new release in `.copier-answers.yml` comes as a pull request too, and the updates carry the modes of files, such as a script that becomes executable.

The blueprint owns the workflows, `scripts/check.sh` and the community files: their changes arrive with the updates. Files that belong to the project are never overwritten: the README, the changelog, the security design in `docs/security.md`, the dependency manifests and lock files (Renovate keeps them current), the code and the tests, the website's `mkdocs.yml` and pages, the issue forms, the labels and their paths, accepted findings, and the notes for coding agents. Checks of a project alone belong in `scripts/check-project.sh`, which `scripts/check.sh` runs last.

### The issue assistant

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/how-a-release-of-the-issue-assistant-reaches-every-repository.dark.svg">
  <img src="docs/images/diagrams/how-a-release-of-the-issue-assistant-reaches-every-repository.svg" alt="How a release of the issue assistant reaches every repository: Every morning, the sync bot of the blueprint takes the latest published release of the issue assistant and verifies it: the release must be immutable, GitHub's attestation of it must hold, its tag must point at a commit of the main branch of the issue assistant, and its release workflow must have signed the tag. Any other release fails the run, and nothing changes. Otherwise the bot runs install of the release in the root of the blueprint, which writes the four workflows and the firewall policy of the release and moves every pin of the action, and keeps one pull request with the result, which merges itself once every check passes. The next release of the blueprint brings it to every repository with the blueprint bot.">
</picture>

The four workflows of the [issue assistant](https://github.com/Dennis-Otto/issue-assistant) and its firewall policy are templates of its release, with which the check of the issue assistant, a step of `lint`, compares every repository, so a pin of the action that moved alone would fail that check; Renovate leaves the action alone. The sync bot of the blueprint (`sync-issue-assistant.yml`, in the blueprint alone) takes over each new release instead. Every morning it takes the latest published release of the issue assistant and verifies it as the blueprint bot verifies a release of the blueprint: the release must be immutable, GitHub's attestation of it must hold (`gh release verify`), its tag must point at a commit of the issue assistant's `main`, and its release workflow must have signed the tag. Any other release fails the run with the reason in its summary, and nothing changes; so does a release older than the one that the blueprint has, since GitHub calls a release latest by its date, not by its version. Then the bot runs `install` of exactly the verified commit in the root of the blueprint, takes over the firewall policy of the release, moves every pin of the action to it, that of the check in the Lint workflow too, and gives a workflow that is new in the release the file of the template that renders it in every repository; a release whose `install` changes anything else fails the run, and the maintainer takes it over by hand. The bot keeps one pull request on the branch `bot/issue-assistant`, `fix(deps): update the issue assistant to vX.Y.Z`, which merges itself once every check passes and moves on to a newer release; once someone else commits to its branch, the bot leaves the branch alone until the pull request is merged or closed. The next release of the blueprint, which publishes itself when it holds only updates, brings the release to every repository. Installing runs without secrets; only the job of the pull request has the release app, and it runs nothing of the release. Run it by hand under *Actions → Issue assistant sync*; with *dry_run*, it verifies and installs the latest release and shows what would change without a pull request, as it does in every pull request that changes the bot. The bot-health bot (`bot-health.yml`) keeps one issue open about a failed run, with the reason of a refusal, and closes it once a run passes.

## What belongs to a project

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="docs/images/diagrams/what-belongs-to-the-blueprint-and-what-to-the-project.dark.svg">
  <img src="docs/images/diagrams/what-belongs-to-the-blueprint-and-what-to-the-project.svg" alt="What belongs to the blueprint and what to the project: copier update brings the changes of the blueprint's files, merged line by line with the changes of the repository, and never overwrites the files of the project. A project adds checks, settings, notes for coding agents and workflows of its own beside those of the blueprint.">
</picture>

The blueprint keeps the shared parts of every repository equal; a project adds its own without forking them:

- **Changes in the blueprint's files survive updates:** `copier update` merges the changes of the blueprint with those of the repository, line by line, and marks a conflict only where both changed the same lines.
- **Settings of the project alone** go into `.github/repository.project.toml`, such as the checks of its end-to-end tests, an environment with its secrets or the patterns of the actions that only its own workflows run. `blueprint.py` and the settings bot add them to `.github/repository.toml`.
- **Checks of the project alone** go into `scripts/check-project.sh`, which `scripts/check.sh` runs last, and those of its website, such as of its `robots.txt`, into `scripts/check-site.sh`, which the check *docs* runs with the folder of the built website; **workflows of the project alone** are workflow files of their own.
- **Notes for coding agents** go into `.github/agents.project.md`, such as the architecture of the project and the commands of its own checks. `AGENTS.md`, which the blueprint keeps current, has the rules of every repository and points to them, and `CLAUDE.md` brings both to Claude Code.
- **Explanations of the checks of the project alone,** which the PR coach shows when one fails, go into `.github/checks.project.toml`; they win over those of `.github/checks.toml`.
- **Several copyright holders,** such as the authors of a fork, are the answer `copyright`, separated by semicolons; LICENSE and REUSE.toml name each of them.
- **Files under another license,** such as third-party artwork, get a `.license` file next to them, as REUSE describes.
- **The package of a Nextcloud app** is checked by `scripts/check-package.sh ARCHIVE unsigned|signed` if the project has one: `scripts/check.sh` runs it on the package that krankerl builds, the release on the package before and after signing.
- **The version in other lines of a file of the release,** such as the tag in the URL of a screenshot in `appinfo/info.xml`, follows each release when the line ends with the comment `x-release-please-version`, such as `<!-- x-release-please-version -->`.

## Tools in every repository

- `bash scripts/check.sh`: the checks of the CI, locally.
- `bash scripts/diagrams.sh`: draws every diagram of `docs/diagrams/` that a page shows as its pictures in `docs/images/diagrams/`, with Docker, and leaves the other sources alone; `--extract` first turns every `mermaid` block of the Markdown into a source and its picture and writes the `alt` of each picture from its source, and `--check` checks without Docker what `scripts/check.sh` checks.
- `bash scripts/social-preview.sh`: renders `.github/social-preview.html` into the 1280×640 image that GitHub shows for links to the repository; upload it under *Settings → Social preview*.

## Dashboard

![The dashboard: a table with every public repository of the owner, its kind, the release of the blueprint it is on, its release, its next release, its pull requests and the state of its CI, CodeQL, release, verification, website, settings, findings, links, mutation tests and Renovate with its Scorecard, and a second table with the health of each one: coverage, mutants caught, releases in 90 days, the first answer by a person and the time of the CI](docs/images/dashboard.png)

[The dashboard](https://dennis-otto.github.io/repo-blueprint/dashboard/) shows every public repository of the owner at a glance: the release of the blueprint it is on, and the pull request of the blueprint bot that updates it in the colour of its checks; its latest release and the pull request of the next one; its open pull requests and those in conflict; the last run on `main` of its main workflows, the Docs workflow, which builds the website and, outside the blueprint, publishes it, the mutation tests and, in the blueprint, Renovate among them, where a run that GitHub skipped doesn't count and the verification is the newer of its weekly run and its job in the run that made the latest release; and its OpenSSF Scorecard. A second table shows the health of each: the line coverage and the share of mutants that the tests catch, or ✘ with the run where none is known and the last run failed, the stable releases and the median time to the first answer by a person, not a bot, to an issue over 90 days, and the median time of the CI, each with an arrow when it moved since a week ago, from the history that the published dashboard keeps. The Dashboard workflow builds it with `dashboard.py` every two hours and after a change of the changelog, and publishes it on GitHub Pages, under the website of the blueprint, which is this documentation. When the history of the published dashboard can't be read, the run fails, and the website keeps its page and its trends instead of a history of one day; a report of a repository that can't be read leaves out that one value. It shows only what is public anyway, no finding of code scanning and no alert of Dependabot.

**The data of the dashboard stays at its addresses,** for the owner's website, which shows the version and the numbers of each project from it, for feed readers and for scripts of your own, also when the page changes. GitHub Pages serves them from the website of the blueprint, without a token and without a limit of GitHub's API:

- [`dashboard/`](https://dennis-otto.github.io/repo-blueprint/dashboard/), or `dashboard/index.html`: the page.
- [`dashboard/repos.json`](https://dennis-otto.github.io/repo-blueprint/dashboard/repos.json): what the page shows, as JSON: its `schema`, now `1`, which a change that takes a field away or changes its meaning raises; when it was `generated`; the `owner`; the latest release of the `blueprint`; and in `repos`, by name, each repository with its `name`, its full name `repo` (owner/name), `url`, `description`, `homepage` and `stars`, its `kind` and the release of the `blueprint` it is on, the open `update` of the blueprint bot with its `target`, `number`, `url` and the `state` of its checks, its `release`, the day it was `released` and its `release_url`, its `next_release` and the `next_url` of its release pull request, its `pulls` and `conflicts`, the file of its CI workflow `ci`, the last `runs` of its workflows by the names of the columns, each with its `state`, `url` and when it `started`, its `scorecard` and its `health`: the `coverage` and `mutation` score in percent, the number of `releases` in the last 30 days, the median `answer_hours` until a first answer to an issue and the median `ci_minutes` of its CI. A value that isn't known, or isn't there, is `null`.
- [`dashboard/history.json`](https://dennis-otto.github.io/repo-blueprint/dashboard/history.json): the `health` of each repository for each of the last 120 days, which the arrows of the page compare with.
- [`dashboard/releases.atom`](https://dennis-otto.github.io/repo-blueprint/dashboard/releases.atom): the 30 newest releases across all repositories, without prereleases, as an Atom feed, each with the first 500 characters of its notes; the page names it in its head, so a feed reader finds it from the address of the page.

The job that publishes the dashboard asks for each of the four after every deployment and fails when one is missing or holds something else.

Every Monday, the Weekly report workflow posts in the [discussions](https://github.com/Dennis-Otto/repo-blueprint/discussions) what the public repositories of the owner released, merged and fixed in the seven days before its run, to the minute, with the totals of GitHub's search: their releases, merged pull requests and the updates among them, opened and closed issues, failed runs on `main` and the median time of their CI (`weekly.py`). Like the dashboard, it reports only what is public.
