### Features

- **The taint analysis of a Nextcloud app sees what Nextcloud hides from Psalm, and proves it in every run:** CodeQL has no PHP, and Psalm's taint analysis, the only analysis that followed untrusted input through a Nextcloud app, found no input at all, because Nextcloud passes the parameters of a request to a controller as the arguments of its methods; a controller that wrote a parameter into a path or fetched it as an address passed the check. Now `.github/psalm/NextcloudTaintPlugin.php`, which `psalm.xml` loads, makes every parameter of a public method of a controller, the term of a search and the answers of other servers untrusted input, and the paths of the files and folders of a user and of the app's data, the addresses of `IClient` and of a `RedirectResponse` sinks, next to the queries and `IRequest` that `nextcloud/ocp` marks itself. The new step *Psalm taint canary* of `scripts/check.sh` analyses a controller in `.github/psalm/canary/` with a path to each kind of sink, beside the check of the types, and fails unless the analysis finds each one, so it can't go blind again unnoticed; a method of `nextcloud/ocp` that the plugin names and an update removes stops Psalm with its name. The CI shows each path that the analysis finds in code scanning, with every line that it takes, from the new job `taint report (php)`, which alone may write alerts and runs no code of the app. The update can fail `check (php)` where input reaches such a sink on a path that no function of your app escapes: validate it there, and mark the function that makes it safe with `@psalm-taint-escape file`, `ssrf` or `header` and a comment on why. The security design of a new app, `docs/security.md`, names the analysis among its controls; an existing app can take the two rows of its threats from the template.
