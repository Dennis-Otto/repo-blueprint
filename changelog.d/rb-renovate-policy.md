### Features

- **One issue shows every update that waits or failed:** Renovate kept no dependency dashboard, so an update that waited for its week or for you, and one that failed, showed only in the log of the bot, as when the update of PHPUnit to 13 in paperless-sync failed to write its lock file and closed itself unseen. Every repository now gets the issue *Dependency dashboard*, with the label `dependencies`: the updates that wait and why, those that failed with their error, the vulnerabilities that OSV knows, and a checkbox for each that opens, retries or rebases it with the next run of the bot. Updates still come without a checkbox. The issue comes with the first run of Renovate after the update; nothing to do in your repository.
- **Updates of what your users run lead to a patch release:** Renovate committed only the dependencies of npm and Composer as `fix(deps)`, so the requirements in the manifest of a Home Assistant integration, the dependencies of a Python package in `pyproject.toml`, the actions in `action.yml` of a GitHub Action and the base images in the `Dockerfile` of a container came as `chore(deps)` and reached your users only with a release for another reason. They are `fix(deps)` now and lead to a patch release, while the updates of the tools of the checks stay `chore(deps)`; the dependencies of a Python package come in a group of their own, *the Python packages*. A rule in your `.github/renovate.json5` with a `semanticCommitType` of its own still wins.

### Changes

- **Renovate opens updates on the whole Monday:** its window was Monday from 00:00 to 06:59, Berlin time, and GitHub starts the scheduled runs of the bot only roughly and skips some, so in the week of 2026-10-05 a single run fell into it, and one more skipped run would have held every routine update back by a week. Routine updates and the refresh of the lock files now come on the whole Monday; a fix of a vulnerability still comes at once. The refresh of the lock files is built anew throughout Monday, so review it from Tuesday on, or again after it changed.
- **gitsign, Infection, krankerl and Nextcloud stay current:** the release workflow signs its tag with gitsign, the mutation tests of a Nextcloud app run Infection, and a Nextcloud app builds and signs its package with krankerl and Nextcloud, each downloaded at a pinned version and checked against its sha256. Renovate saw none of these pins, so Infection and Nextcloud were two patch releases behind. Now Renovate moves each of them a week after its release, and `pins.py` of the blueprint writes the sha256 of the new release beside the version, so that the update merges on its own and reaches your repository with the next release of the blueprint; your own Renovate leaves these pins alone. Decision 0029 says why.
