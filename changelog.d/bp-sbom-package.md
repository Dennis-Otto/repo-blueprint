### Bug fixes

- **The SBOMs of a release describe what it ships, by its name and version:** the SPDX and CycloneDX documents of every release described the folder of the repository, named `.` without a version, with every action of its workflows and every tool of its checks and its website: some 200 components, none of which a package holds. The scanners of your users reported advisories of MkDocs, Copier or an action against your release, and no SBOM said which release it belonged to. Now the build unpacks what the release ships, the zip of HACS, the wheel, the npm package or the signed Nextcloud app, and for an action, an image or a project without a package the files of its tag without those that only check, test and document it; syft describes what it finds there, the components that a package installs, with the name of the repository, the version of the release and its owner as the supplier at the root. The build stops before the release is published, and the release verification fails, when an SBOM doesn't name the release; its weekly run only notes an older release. syft comes from its release, checked by its sha256 and moved by Renovate like the other tools that the workflows download, in place of `anchore/sbom-action`, which downloaded an installer and ran it in the job that may write the release. The OpenVEX document names the release as Grype names the root of its SPDX SBOM, so `grype sbom:<repo>.spdx.json --vex <repo>.openvex.json` applies its statements. `SECURITY.md` shows that command, and checks each attestation of the release with `--signer-workflow`, so that one made by any other workflow of the repository fails. The weekly SBOM of the SBOM workflow still describes the whole repository with its tools, now by its name and commit. The update brings all of this.
