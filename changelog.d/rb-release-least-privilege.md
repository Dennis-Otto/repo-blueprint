### Bug fixes

- **The build of a release no longer holds the private key of the release app:** `build-release.yml` entered the environment `release` in every repository, and the release workflow passed it all of its secrets, while the build runs actions of others, such as those that write the SBOMs or set up PHP, Node and Python. The private key of the release app, which can change the settings and the workflows of every repository it is installed on, was in reach of each of them. Now only the build of a Nextcloud app, which signs the app with its key, enters the environment and gets the secrets; every other build holds only the token of its job, and zizmor accepts the passed secrets only at that one line of a Nextcloud app.
- **The release verification accepts only the provenance of a run for `main` on a runner of GitHub:** `verify-release.yml` checked which workflow signed the provenance of each asset, but not for which branch it ran nor on which machine, and for the image in GHCR not even the workflow. Every check now demands the workflow that builds the release, `--source-ref refs/heads/main` and `--deny-self-hosted-runners`, and so do the commands of `SECURITY.md` with which users verify a release and the check of the workflow *Chrome Web Store* before it uploads a zip. A release that anybody but the release workflow publishes, by hand or with a token, is verified at once instead of with the weekly run, and when that fails, the bot-health bot opens its issue, because GitHub would mail the failure only to whoever published the release.
- **A container image no longer claims SLSA Build Level 3:** the release workflow builds and attests the image in the job that pushes it, outside the isolated build, so `SECURITY.md` and the page of the kind now say that the image reaches SLSA Build Level 2, and its other assets Level 3. The README of a new container repository shows the strict command; an existing one changes its line `gh attestation verify oci://…` by hand to the one of its `SECURITY.md`.
