### Features

- **An optional second app, the settings app, writes the administration, so the release app can give it up:** the release app, which most workflows use, could also change every ruleset, environment and the actions that may run, only because the settings bot applied the settings with it; and the update pull request of a release that adds an action waited for `settings apply` from its branch, since the blueprint bot had no token that may widen the list of the allowed actions. Register a second GitHub App with only the permissions of the settings, install it, and set its Client ID as the variable `SETTINGS_APP_CLIENT_ID` and its private key as the secret `SETTINGS_APP_PRIVATE_KEY` of the environment `release`: the settings bot then applies the settings as this app, and the blueprint bot adds the patterns of a verified release to the allowed actions before it pushes the update, with a token that has only *Administration*, so the checks of the update start at once; the settings bot narrows the list after the merge. Afterwards, take *Administration*, *Pages*, *Variables*, *Environments* and *Secrets* from the release app. Without the settings app, everything works as before; with only one of the two set, both bots say what is missing and go on with the release app. `python3 .github/blueprint.py settings widen` does the widening on your machine. *Your own account* shows the set-up, and decision 0077 says why.
