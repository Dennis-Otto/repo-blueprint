### Features

- **A new record of a decision takes the number of its pull request, and the release writes the index:** two pull requests that each added a record took the same next free number and their rows in `docs/decisions/README.md` conflicted, so GitHub ran no checks and someone had to merge `main`, rename the record and push again. A new record is now named after the number of its pull request, or of the issue that the pull request fixes with `Fixes #…`, such as `1040-the-new-way.md`, which no other pull request can take. Pull requests leave the index alone: the release writes the row of each new record and the status of each record in the commit that writes `CHANGELOG.md`, and the website lists every record at any time. The step *Records of decisions* still fails on two records of one number and on a wrong row of the index, no longer on a gap between numbers or a missing row, and in the CI of a pull request it fails on a new record that carries neither number, with the number to take in its log; `blueprint.py decisions --complete` writes the index as the release does. The records you have keep their numbers ([decision 1033](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/1033-a-new-record-takes-the-number-of-its-pull-request.md)). In an existing repository, `docs/decisions/README.md` belongs to the project, so its second paragraph still says "the next free number" until you change it, as the template now says: copy the template to a file named after the number of your pull request or of the issue that it fixes, and leave the rows to the release. No command changes it, since the paragraph is your own prose that you may have reworded, and an old one breaks nothing: the step names the number to take. A pull request of yours that is open when the update arrives and adds a record renames it once, to its own number.
