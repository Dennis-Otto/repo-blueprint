### Features

- **The weekly mutation tests finish on large projects, show first what a test should catch, and open an issue when the score drops:** one job ran every mutant of a project, so an integration with about 9,000 mutants couldn't finish within the six hours of a job of GitHub, and the summary listed the first 30 survivors by name, mostly texts of help and log lines, among which those that change the logic hid. Now the job *plan* estimates the mutants of each function and splits the code into parts of about 3,000 mutants, at most eight, each a job of its own, and the job *report* puts them together into one score. The summary sorts every survivor by its change: first those that change the logic, an operator, a comparison, a number or a condition, by function and each with its change, then those that pass None or leave out an argument, then those that change only a text, with the *score of the logic* beside the score; `survivors.md` in the artifact *mutation*, which now stays for 90 days, has every change. When the score of the default branch falls by more than half a point below that of the run before, one issue *Mutation score dropped* opens with the functions that gained survivors of the logic, and it closes once a run is back. A run in which no mutant ran names the tests that failed without any mutant, such as one that can't pass in mutmut's copy of the repository, and `CONTRIBUTING.md` says how to keep mutmut away from a text with `# pragma: no mutate` and a test out of the copy with `@pytest.mark.mutation_unsafe`. The variable `MUTATION_PARTS` of a repository sets the number of parts in place of the estimate, and a project that limits `only_mutate` to stay within the time of one job can drop that limit now.
