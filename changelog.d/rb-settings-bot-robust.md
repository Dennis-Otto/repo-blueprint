### Bug fixes

- **The settings bot reports a change that GitHub refused, reads every page of a list, and runs when its code changes:** GitHub answers 404, not 403, to a token that lacks the permission for some changes, and `blueprint.py settings apply` took that answer for a change that was made; it now fails with exit code 2, names the part that GitHub refused and the permission that the release app may lack, as for a 403. Every request of the bots to GitHub tries once more after a gateway that timed out (502, 503, 504; not for a POST, which GitHub has often done all the same) or a rate limit, after the wait that GitHub asks for and at most two minutes of waits per run, and a rate limit is no longer called a missing permission. The labels, rulesets and secrets of environments are read from all their pages, not only the first 100 or 30, and a label that GitHub has in another case, such as `Bug` for `bug`, is renamed instead of failing as a label that exists already. `blueprint.py` now needs GitHub CLI 2.48 or later. The Settings workflow now also runs when an update of the blueprint changes its code, so that a release that changes how a setting is applied takes effect with the merge of its update instead of on the next Thursday, and no longer on a change of `.github/labels.toml`, which the Labels workflow applies: the two created the same new label at once, and one of them failed; should they still meet, the settings bot updates the label that the other created. The checklist names the gaps in the community profile in a step of their own, "Community profile complete (100 %)", instead of as missing secrets of the environments.
