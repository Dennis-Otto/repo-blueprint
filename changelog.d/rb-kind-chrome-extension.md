### Features

- **A new kind of project, a Chrome extension:** `copier copy --data project_type=chrome-extension` makes a Chrome extension of Manifest V3 in TypeScript, with the tools of Node, an example service worker with its tests, and `store/` with the listing and the reason of each permission for the Developer Dashboard. The step *Extension* of `scripts/check.sh` checks the manifest against what the Chrome Web Store refuses or holds up in its review: a permission or a host without its reason and its justification, a language without its listing, a name or a description over the limits of the store, or a version other than that of the release. It also builds the zip of the store, the same for the same commit, and the CI loads the extension into Chrome for Testing (decision 0085).
- **Every release of a Chrome extension reaches the Chrome Web Store by itself:** the isolated build of the release zips the extension from the signed tag and attests it. The new workflow *Chrome Web Store* then uploads exactly that zip, only with a valid provenance, and submits it for review. It runs every day as well: it delivers a release whose review had to wait, and fails with the reason and the fix on a rejection, a warning of Google, a review of more than seven days, or a submission that the dashboard lacks a justification for (`INVALID_ITEM_METADATA`). It signs in to Google with the OIDC token of GitHub through Workload Identity Federation, so no secret of the store is stored; `docs/releases.md` of the new repository has the one-time set-up, a script for the Cloud Shell, and `blueprint.py checklist` shows its two steps until their variables are set. An extension that a repository made as a Node package switches with `copier update --data project_type=chrome-extension`: it keeps its `extension/`, `store/` and `docs/releases.md`, and `blueprint.py settings apply` sets `PUBLISH_TO` and the environment `chrome-web-store`. Its prereleases come from the beta channel only, as its manifest takes only numbers.
