### Features

- **Every check that fails explains itself, also on a pull request from a fork:** a contributor whose pull request failed a check saw a red cross and the raw log of a tool. Now the new PR coach says what the check found, why that matters and how to fix it, with the commands to run and a link to read more: in the summary of the check, as its annotation, and after the checks in one comment on the pull request, which follows every push and says so once every check passes; a check that was cancelled, as one that ran out of time, hasn't passed. It works for pull requests from forks as well, whose own runs can't comment, and suggests a title that passes when the title is no Conventional Commit. `scripts/check.sh` explains the step that stopped it in the same words on your machine, and in the CI the problems of the text files, of Ruff and of actionlint show at their lines in the files of the pull request. The coach reads the checks from the API and runs no code of the pull request; text that a pull request controls appears only as code. The explanations of every check of the blueprint are in `.github/checks.toml`; explain the checks of your own project, such as end-to-end tests that you made required, in the new `.github/checks.project.toml`, and `python3 .github/blueprint.py coach verify` lists any without one. The comment follows the workflows of the checks that the blueprint sets up; to have it follow a workflow of your own, such as one of visual tests, name it in the answer `test_workflows` of `.copier-answers.yml`. A GitHub Action keeps its `.github/workflows/action-test.yml`, which the update leaves alone: to have its check *action* explain a failure as well, add the last step of the job `action` of the blueprint's copy to yours, the step *Explain the failure* with `if: failure()`, `CHECK: action` in its `env:` and `python3 .github/blueprint.py coach explain "$CHECK"` as its `run:`.

### Bug fixes

- **`scripts/check.sh` finds CRLF line endings on Windows too:** the grep of Git for Windows drops the carriage return at the end of each line, so the step *Text files* passed a file with CRLF line endings on Windows that it fails on Linux and macOS. It now fails there as well, so the checks on your machine are the same everywhere, and stricter than the CI for a file that Git would still commit with LF line endings, as `.gitattributes` asks. `sed -i 's/\r$//' FILE`, or an editor set up by `.editorconfig`, gives the file LF line endings again.
