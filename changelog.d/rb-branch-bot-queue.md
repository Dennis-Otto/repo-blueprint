### Performance

- **Pull requests that wait for auto-merge no longer run their checks for nothing:** `main` takes a pull request only when it is up to date with it, so only one of the waiting pull requests can merge next, yet after every merge the branch bot brought all of them up to date, and each ran every check again only to fall behind with the next merge; with n waiting pull requests, that was about n²/2 runs of the checks for the runners of your account. The branch bot now keeps a line, in the order in which auto-merge was turned on, and brings only the first one up to date that can merge; the others wait until it merges, so they still merge one after the other without a person, with about n runs of the checks. A pull request whose required check failed waits for a fix and leaves its place to the next one. Turning auto-merge on starts the bot at once, so a pull request that is behind is brought up to date within about a minute instead of waiting for the next merge or the half-hourly schedule, which GitHub often runs hours late; a required check that fails and turning auto-merge off start it too. A request that GitHub refuses for one pull request no longer stops the updates of the others and no longer labels a pull request without a conflict as `merge-conflict`: it is a warning about that pull request, and the run fails, so that the bot-health bot opens its issue. The summary of every run shows the line and why each pull request waits, and *Actions → Update branches* runs the bot by hand. Decision 0028 says why.
