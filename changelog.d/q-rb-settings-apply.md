### Bug fixes

- `settings apply` says why GitHub refused a change, in GitHub's own words, such as a ruleset whose bypass actor is a release app that the repository hasn't installed, with what to do about it. Each ruleset and each variable is applied by itself, so a refused one no longer keeps the others from being set, and a ruleset that the settings no longer want is deleted all the same: a review that `.github/repository.project.toml` dropped is no longer left required. The run names what happened to each and still fails.
- `REVIEWS_OF_MAIN` now says whether GitHub has *Reviews of main* after an apply, not what the file wanted where GitHub refused it, so the bots start the branch bot exactly where main requires reviews.
- A repository without the release app can say so: `RELEASE_APP = ""`, `RELEASE_AUTOMATION_CLIENT_ID = ""` and `RELEASE_AUTOMATION_APP_ID = ""` under `[variables]` in `.github/repository.project.toml`. An empty value means that the repository has no such variable, which an apply deletes instead of sending the empty value that GitHub refuses; no ruleset names the app, the environment `release` asks for no private key, and `settings check` is clean.
- `settings check` names a review of code owners that the default branch on GitHub has no `CODEOWNERS` file for, and the line of a drifted ruleset gives each key with what GitHub has and what the file wants, such as `GitHub has {"pull_request.required_approving_review_count": 2}, the configuration wants {"pull_request.required_approving_review_count": 1}`.
