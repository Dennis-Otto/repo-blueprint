# Architektur

Repo Blueprint ist ein Repository, das sein eigener erster Nutzer ist: Die Workflows, die ihn prüfen, veröffentlichen und aktualisieren, sind die Vorlagen der Workflows jedes Repositorys, das aus ihm entsteht, und jedes seiner Releases erreicht sie alle als Pull Request. Diese Seite zeigt, wie er aufgebaut ist und welchen Weg ein Release nimmt. [Die Automatisierung](https://dennis-otto.github.io/repo-blueprint/de/automation.html) beschreibt jeden Workflow, [das Sicherheitsdesign](security.md) (englisch), was der Blueprint schützt und wem er vertraut, die [Referenz](reference/questions.md) (englisch) jede Frage, Variable und jedes Secret, und [die Entscheidungen](decisions/README.md) (englisch), warum er so arbeitet.

## Wie der Blueprint funktioniert

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/how-the-blueprint-works.de.dark.svg">
  <img src="images/diagrams/how-the-blueprint-works.de.svg" alt="Wie der Blueprint funktioniert: Copier rendert ein neues Repository aus den Fragen in copier.yml und den Dateien in template/, die die Workflows aus .github/workflows/, die Manifeste aus stacks/ und blueprint.py aufnehmen. Renovate hält die Workflows und die Stacks aktuell.">
</picture>

- `copier.yml` enthält die Fragen. `template/` enthält die Dateien eines neuen Repositorys; ein Datei- oder Ordnername wie `[% if stack == 'php' %]composer.json[% endif %]` trägt seine Bedingung, und ein Name, der leer gerendert wird, entfällt. Die Trennzeichen `{= =}` und `[% %]` kommen in keinem Workflow, Skript oder Manifest vor; so bleiben `${{ }}` von GitHub Actions und `[[ ]]` von Bash und TOML unverändert.
- Die Workflows in `.github/workflows/` laufen in diesem Repository und sind zugleich die Vorlagen der Workflows jedes neuen Repositorys: actionlint prüft sie, und Renovate hält ihre Actions hier aktuell. Eine Zeile mit *Not in the blueprint itself* schaltet einen Job in diesem Repository ab und fehlt in neuen.
- `blueprint.py` startet das Werkzeug der Einstellungen als Code, der Checkliste und der Bots. Sein Code liegt in `blueprint/`, ein Modul für jede Aufgabe, mit einer eigenen `ruff.toml`, damit die Ruff-Einstellungen eines Projekts nicht für ihn gelten.
- `stacks/` enthält Manifeste und Lock-Dateien jeder Projektart, die Renovate aktuell hält; ein neues Projekt startet von ihnen.
- `tests/` prüft `blueprint.py` gegen ein simuliertes GitHub und rendert jede Projektart; der Variants-Workflow rendert jede einzelne und führt ihre eigenen Prüfungen mit den echten Werkzeugen aus. Außerdem bringt er ein Repository jeder Art vom letzten Release auf den Commit; das muss jede Datei des Blueprints so bekommen, wie ein neues Repository sie hat, und dieselben Prüfungen bestehen: in jedem Pull Request außer dem Release-Pull-Request, und jede Woche. Ebenso aktualisiert er eines mit den Antworten jedes Repositorys, das den Blueprint übernimmt, aus `tests/answers/`: ohne den Beispielcode (außer bei einem Repository, das der Blueprint neu erstellt hat, `MADE_NEW` in `tests/test_template.py`) und mit dessen Lizenz, Sprachen und Discussions; dessen Website und Lint müssen ebenfalls bestehen. Der Downstream-Workflow klont jedes dieser Repositories und aktualisiert es wie sein Blueprint-Bot, auf `main` und auf den Pull Request: Seine Zusammenfassung nennt die Dateien, deren Update der Pull Request ändert, und jeden Konflikt, bevor das Release sie dorthin bringt, und ein Konflikt in einer Datei, die keine Textseite ist, etwa einem Workflow, einem Skript oder einer Konfiguration, lässt ihn scheitern (`downstream.py`). Der Windows-Workflow führt `scripts/check.sh` außerdem unter Windows aus, in Git Bash wie auf dem Rechner eines Mitwirkenden, jede Woche und für jeden Pull Request, der den Code oder die Tests ändert. Der Workflow Next runner führt die Variants jede Woche auf dem Runner aus, auf den die Jobs als Nächstes umziehen.
- `docs/` macht diese Dokumentation zur Website des Blueprints: ihre Seiten binden die READMEs ein, und der Dashboard-Workflow veröffentlicht sie mit dem Dashboard unter `dashboard/`.
- `reference.py` schreibt die [Referenz](reference/questions.md) der Website aus `copier.yml`, den Workflows und den Einstellungen als Code der Vorlage, sodass jede Frage, Variable und jedes Secret dort beschrieben ist, wo man sie sucht, und aus dem Verzeichnis [`.github/fleet.toml`](https://github.com/Dennis-Otto/repo-blueprint/blob/main/.github/fleet.toml) die Vitrine der READMEs, den Abschnitt *Ein echtes Repository* jeder Art, die Reihenfolge des Rollouts und die Canaries der Variants; `tests/test_reference.py` scheitert, solange eine Seite von ihnen abweicht.

## Der Weg eines Releases

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/the-path-of-a-release.de.dark.svg">
  <img src="images/diagrams/the-path-of-a-release.de.svg" alt="Der Weg eines Releases des Blueprints: Ein Pull Request wird in main des Blueprints gemergt, und der Release-Workflow hält den Release-Pull-Request mit der nächsten Version. Sein Merge, durch den Maintainer oder von selbst, wenn er nur Updates enthält, veröffentlicht das Release mit einem signierten Tag und prüft es. Der Rollout-Workflow startet dann den Blueprint-Bot jedes Repositorys, das den Blueprint übernimmt. Jeder Bot prüft das Release, führt copier update aus und hält einen Update-Pull-Request als Release-App, damit die Prüfungen des Repositorys laufen. Ohne Konflikte merged er sich selbst, sobald sie bestehen; mit Konflikten oder mit BLUEPRINT_AUTOMERGE auf off wartet er auf den Maintainer. Das Dashboard zeigt das Release des Blueprints, auf dem jedes Repository steht.">
</picture>

1. **Ein Merge in `main`** des Blueprints startet den Release-Workflow, dessen release-please einen Release-Pull-Request mit der nächsten Version hält, bestimmt aus den Titeln der gemergten Pull Requests, und mit den Einträgen des Changelogs als Notizen.
2. **Das Release:** Der Maintainer merged den Release-Pull-Request, oder er merged sich selbst, sobald seine Prüfungen bestehen, wenn er nur Updates enthält: einmal am Tag, damit die Updates eines Tages ein Release ergeben, und sofort, wenn eines davon eine Schwachstelle behebt. Der Release-Workflow signiert seinen Tag mit gitsign, veröffentlicht das Release mit seinen SBOMs und seiner signierten Herkunft und prüft es so, wie es seine Nutzer können.
3. **Der Rollout**-Workflow startet den Blueprint-Bot jedes Repositorys der Release-App gleich nach dem Release, und der wöchentliche Lauf der Bots bleibt als Sicherheitsnetz, damit ein Fix jedes Repository in Minuten erreicht ([Entscheidungen 0052](decisions/0052-roll-out-every-release-at-once.md) und [0010](decisions/0010-roll-out-one-repository-at-a-time.md), englisch).
4. **Der Blueprint-Bot** jedes Repositorys prüft das Release, bevor er etwas ändert: Das Release muss unveränderlich sein, sein Tag muss auf einen Commit von `main` des Blueprints zeigen, und der Release-Workflow des Blueprints muss den Tag signiert haben ([Entscheidung 0020](decisions/0020-update-only-to-a-verified-release.md), englisch). Dann führt er `copier update` darauf aus und hält einen Pull Request auf dem Branch `blueprint/update`, als Release-App, damit die Prüfungen des Repositorys laufen.
5. **Die Prüfungen** des Repositorys testen das Update wie jeden Pull Request. Ohne Konflikte merged sich der Pull Request selbst, sobald jede Prüfung besteht; mit Konflikten oder mit [`BLUEPRINT_AUTOMERGE`](reference/variables.md#blueprint_automerge) auf `off` wartet er auf den Maintainer, wie die [Fehlerbehebung](troubleshooting.md#ein-update-des-blueprints-hat-konflikte) zeigt.
6. **Das Dashboard** zeigt das Release des Blueprints, auf dem jedes Repository steht, und den Update-Pull-Request in der Farbe seiner Prüfungen, unter [dennis-otto.github.io/repo-blueprint/dashboard](https://dennis-otto.github.io/repo-blueprint/dashboard/).
