# Fix-Bot und Selbstheilung

Was ein Repository selbst repariert: die Befunde, die ein Befehl beheben kann, Tests, die einmal scheitern, Prüfungen, die abbrechen, Releases und Bots, die fehlschlagen.

## Fix-Bot

Eine Prüfung, die scheitert, behebt, was ein Befehl beheben kann, etwa das Format des Codes, Leerzeichen am Zeilenende und Zeilenenden, die Regeln von markdownlint und die Seiten in einer Spalte: Der Bot committet die Behebungen als einen Commit auf einen Branch des Repositorys, auch einen von Renovate, schlägt sie an einem Pull Request aus einem Fork an ihren Zeilen vor, wo `/fix` eines Maintainers sie committet, und hält einen Pull Request mit den Behebungen von `main`, der sich selbst merged; `python3 .github/blueprint.py fix run` macht dieselben Behebungen auf deinem Rechner.

**Womit:** `autofix` in `.github/checks.toml`, `after-checks.yml`, `commands.yml`.

## Pull Requests reparieren sich selbst

Erst beheben, dann erklären: Was ein Befehl an einer gescheiterten Prüfung beheben kann, behebt der Pull Request selbst, auch ein Pull Request von Renovate, und `main` ebenso.

- **Die Prüfung behebt:** Jede Erklärung in `.github/checks.toml` sagt in `autofix`, welche Befehle beheben, was ihre Prüfung findet, oder warum kein Befehl das kann; ein Test des Blueprints scheitert an einer, die es nicht sagt. Scheitert eine Prüfung, führt ihr Job diese Befehle auf dem Head des Pull Requests aus, mit den Werkzeugen, die er schon installiert hat: die Textdateien, die Seiten in einer Spalte, die Version des Release-Bots, außer wo der Pull Request `.release-please-manifest.json` selbst geändert hat, das ein Mensch zurücksetzt, weil nur der Release-Bot es ändert ([Entscheidung 0069](../decisions/0069-a-lock-file-and-a-version-fix-themselves-only-where-their-tool-refuses-them.md)), Ruff, php-cs-fixer oder Biome, eine Lock-Datei von Composer oder npm, die ihr Werkzeug ablehnt, mit der kleinsten Änderung neu geschrieben, und eine Lock-Datei von pip-compile, die nicht mehr zu ihrer Quelle passt, neu kompiliert auf den Versionen, die sie festlegt ([Entscheidung 0103](../decisions/0103-a-lock-file-of-pip-compile-compiles-again-on-its-own-pins.md)), für `scripts/check.sh`, markdownlint für das Markdown. Er behält die Dateien, die sie geändert haben, als Artefakt.
- **Auch eine Prüfung des Projekts:** Der Bot liest die Behebungen jedes Workflows in der Liste `workflows:` von `after-checks.yml` auf `main`, etwa Docker E2E und was die Antwort `test_workflows` nennt, und keines anderen, egal wie ein Pull Request seine Läufe nennt ([Entscheidung 0107](../decisions/0107-the-fix-bot-reads-every-workflow-of-its-list.md)). Für eine eigene Prüfung nenne die Befehle in `autofix` in `.github/checks.project.toml` und kopiere die Schritte *Fix what a command can fix* und *Keep the fixes for the fix bot* von `ci.yml` ans Ende ihres Jobs, mit ihrem Namen in `CHECK` und einem eigenen Artefakt `fixes-<name>`, das in einem Matrix-Job auch `strategy.job-index` enthält, da jeder Zweig sein eigenes braucht; ihr Checkout braucht `fetch-depth: 2`. Der Bot wartet nur auf die Workflows, deren Dateien auf `main` ein solches Artefakt behalten, ein langer Lauf ohne eines hält also keine Behebung auf.

Läuft nach der Wartezeit noch einer, bekommt ein Branch keinen Commit: Den macht der Job nach dem Ende dieses Laufs.">

- **Auch eine Verschiebung eines Releases:** Was ein Release in einer Datei des Projekts ändern muss, etwa die Gruppe eines Labels, lässt den Schritt *Files of the project* am Pull Request des Updates scheitern, und der Bot committet es dort ([wie](updates.de.md#was-ein-release-in-einer-datei-des-projekts-ändert)).
- **Ein Commit auf einem Branch des Repositorys:** Sobald die Prüfungen des Commits, die beheben, fertig sind, committet der Fix-Bot alle ihre Behebungen als einen Commit auf den Branch, als die Release-App, mit ihrem Sign-off, und die Prüfungen laufen erneut; der Kommentar des PR-Coachs nennt die Dateien. Das klappt auch auf den Branches von Renovate und den anderen Bots, sodass ein Update eines Formatierers grün bleibt und sich selbst merged.
- **Eine Prüfung, die länger läuft als die Wartezeit:** Der Bot wartet bis zu einer Viertelstunde auf die Prüfungen eines Commits, die Behebungen behalten. Läuft dann noch eine, etwa lange End-to-End-Tests, committet er nichts auf einen Branch des Repositorys, denn ein Commit bräche diesen Lauf ab und verbrauchte einen seiner zwei Commits für einen Teil der Behebungen. Das Ende dieses Laufs startet den Bot erneut, wie auch immer er endete, und dieser Job macht den einen Commit mit jeder Behebung; jeder andere Job dieses Commits findet dann einen neuen Head und committet nichts. Darum startet der Job des Bots nach jedem Lauf einer Prüfung für den Head eines Pull Requests von einem Branch des Repositorys und endet nach wenigen Sekunden, wenn der Commit keine Behebung hat. Ein Vorschlag auf einem Fork und der Pull Request von `main` brechen keinen Lauf ab, sie nehmen also, was fertig ist ([Entscheidung 0112](../decisions/0112-the-fix-bot-leaves-a-commit-to-the-run-that-ends-last.md)).

- **Vorschläge an einem Fork:** Nach den Prüfungen schlägt der Bot die Behebungen an ihren Zeilen eines Pull Requests aus einem Fork vor, höchstens zehn in einem Review und keinen zweimal; **Commit suggestion** übernimmt einen. Eine Behebung, die kein Vorschlag zeigen kann, etwa Zeilenenden, nennt ihre Datei, und der PR-Coach den Befehl.
- **`/fix` an einem Pull Request:** Eine Person mit Schreibrecht im Repository kommentiert `/fix`, als erste Zeile eines Kommentars, und der Bot committet die Behebungen des Heads auf seinen Branch, als die Release-App, mit einem Augenpaar am Kommentar sofort und einem Kommentar mit dem, was er getan hat. Das geht auf einem Branch des Repositorys, auch einem mit dem Label `no-bot-fixes`, das nur die eigenen Commits des Bots stoppt, und auf einem Fork, dessen Autor Änderungen durch Maintainer erlaubt. Dort committet der Bot nur die Dateien, die der Pull Request ändert, und keine, die bestimmt, was ein Workflow ausführt, etwa eine Datei aus `.github/` oder `scripts/` oder `pyproject.toml`, deren Behebung ein Vorschlag für eine Person bleibt. Ob GitHub die Release-App auf den Branch eines Forks pushen lässt, ist nicht geklärt, deshalb ist eine Ablehnung kein Fehler: Der Fork bekommt die Vorschläge an ihren Zeilen, wie ohne den Befehl, und ebenso ein Fork, der keine Änderungen erlaubt. Der Bot wartet auf die Prüfungen des Heads, die Behebungen behalten, wie nach den Prüfungen; läuft eine nach einer Viertelstunde noch, committet er nichts, und `/fix` noch einmal nach ihrem Ende macht den Commit. Je Pull Request läuft ein Befehl zur Zeit, und ein `/fix`, während ein anderer wartet, ersetzt den wartenden. Wer kein Schreibrecht hat, bekommt diese Antwort, und der Code des Forks läuft nie mit dem Token: Der Job checkt nur `main` aus und nimmt die Behebungen der Prüfungen als Daten ([Entscheidung 0117](../decisions/0117-a-person-asks-for-the-fixes-of-a-fork-with-a-command.md)).

- **main repariert sich selbst:** Scheitert eine Prüfung von `main` mit Behebungen, hält sie ein Pull Request von `bot/self-heal`, der sich selbst merged, sobald jede Prüfung besteht; der Bot schließt ihn, sobald `main` keine mehr braucht, und ein Fehler des Bots hält ein Issue offen.
- **Auch was kein Commit ändert:** Jede Woche laufen Lint und die CI auch auf `main`, sodass sich eine neue Regel eines Werkzeugs über diesen Pull Request selbst repariert, statt den nächsten Pull Request einer Person scheitern zu lassen. Die Prüfungen laufen wie immer, und nur eine, die scheitert, führt ihre Behebungen aus; eine ruhige Woche kostet also je einen Lauf, öffnet nichts und startet keinen Job des Bots. Einen Zeitplan, den GitHub verpasst hat, startet Bot Health von Hand, was genauso zählt, und eine Prüfung, die ohne Befehl zum Beheben scheitert, hält ein Issue von Bot Health offen ([Entscheidung 0105](../decisions/0105-the-fixers-run-on-main-every-week.md)).
- **Der Titel und der Eintrag im Changelog, auf einem Branch des Repositorys:** Die Prüfung des Titels führt nichts eines Pull Requests aus, deshalb liest ein eigener Job den Pull Request über die API, sobald diese Prüfung gescheitert ist. Ein Titel, der seinen Typ selbst nennt und nur in der Form abweicht, etwa `Feat: add a dark mode` oder `feat(Settings) add a dark mode`, wird zu dem, den der PR-Coach vorschlägt. Der Typ und die Markierung für Breaking Changes entscheiden über die Version, deshalb bleiben ein Wort für einen Typ, etwa `Feature:`, und ein Titel, dessen Typ nur seine Wörter oder sein Branch hergeben könnten, Vorschläge. Ein `feat`, `fix` oder `perf` einer Person ohne Eintrag bekommt einen Entwurf aus diesem Titel, als eine neue Datei in `changelog.d/`, nach dem Branch benannt, unter der Überschrift seiner Art, einmal je Pull Request; der PR-Coach bittet dich, ihn zu lesen und an seiner Stelle zu sagen, was sich für die Nutzer ändert. Löschst du ihn, erklärt stattdessen die Prüfung. Ein Titel mit HTML, einer Erwähnung oder einem Link bekommt keinen Entwurf, und ein Pull Request aus einem Fork behält seinen Vorschlag und seine Erklärung ([Entscheidung 0110](../decisions/0110-the-fix-bot-corrects-the-form-of-a-title-and-drafts-one-entry.md)).

- **Sicher mit jedem Pull Request:** Der Bot führt nichts eines Pull Requests mit einem Token aus, das schreiben darf. Er nimmt die Behebungen als Daten, mit `blueprint.py` von `main`, und lässt nur Textdateien durch, die der Commit schon hat, unter einfachen Pfaden, außerhalb von `.git` und der Workflows; den Entwurf eines Eintrags, die einzige neue Datei, die er je hinzufügt, benennt und schreibt er selbst. Er committet höchstens zweimal hintereinander (einmal mehr für einen Check, der später endet), nie ein drittes Mal, und ein Pull Request mit dem Label `no-bot-fixes` bekommt keinen Commit.
- **Auf deinem Rechner:** `python3 .github/blueprint.py fix run` führt die Befehle jedes Schritts von `scripts/check.sh` aus, `python3 .github/blueprint.py fix text` behebt nur die Textdateien, und `python3 .github/blueprint.py fix version` schreibt die Version des Release-Bots dorthin zurück, wo eine Hand sie geändert hat; mit `--base origin/main` schreibt es keine, wo das Manifest von dem auf `main` abweicht, wie in der CI (vorher `git fetch origin main`; auf einem Fork nimm das Remote des Upstream-Repositorys, etwa `upstream/main`).

Der Fix-Bot ist in jeder Art dasselbe `after-checks.yml`, das nur die Liste der Workflows setzt, die er liest, und die Tests führen seine Schritte gegen ein nachgebautes GitHub aus.

## Wackelige Tests

Ein Testlauf, der fehlschlägt oder dessen Job sein Zeitlimit erreicht, führt seine fehlgeschlagenen Jobs einmal neu aus, außer dieselben Jobs sind schon für den Commit davor gescheitert; ein Job, der dann besteht, wird in einem Issue als wackelig gemeldet, mit dem Schritt, dem Test und dem Fehler, die gescheitert sind, und das Issue zählt, wie oft jeder Job und Test gewackelt hat.

**Womit:** `after-checks.yml`.

## Abgebrochene Prüfungen

Die schnellen Prüfungen laufen einmal für jeden Commit, sodass kein Lauf für einen anderen Commit sie abbricht; ein Lauf einer längeren vorgeschriebenen Prüfung für den neuesten Commit eines Pull Requests, den ein verspäteter Lauf für einen älteren Commit abgebrochen hat, startet von selbst neu, statt den Merge zu blockieren; ein neuerer Push auf `main` bricht die Tests und Scanner des Pushes davor ab, und ihr Lauf für den neuesten Commit von `main` startet ebenfalls neu, wenn ein verspäteter Lauf ihn abgebrochen hat. Ein Job, der sein Zeitlimit erreicht hat, wie es einem hinter Harden-Runner hängenden Job passieren kann, läuft für den neuesten Commit eines Pull Requests oder von `main` einmal neu.

**Womit:** `after-checks.yml`.

## Gescheiterte Releases

Das Release eines Merges, das scheitert, etwa am Push seines Tags, den GitHub für einen Moment ablehnt, führt seine fehlgeschlagenen Jobs von selbst einmal neu aus, dort, wo sie stehen geblieben sind. Ein zweiter Versuch übernimmt auch ein Release, das der erste als Entwurf hinterlassen hat, etwa wenn sein Job hängen blieb, nachdem er das Release angelegt hatte.

**Womit:** `after-checks.yml`.

## Pull Requests der Bots mit Konflikten

Der Screenshot-Bot, der Bilder-Bot des Blueprints und der Sync-Bot des Issue-Assistenten bauen den Branch ihres Pull Requests neu aus `main`, laufen aber nur nach einem Release, jede Woche oder jede Stunde. Hat einer ihrer Pull Requests Konflikte mit `main`, startet der Branch-Bot sofort den Workflow des Bots, statt eine Person zu bitten, `main` hineinzumergen, einmal für jeden Konflikt: Das Label `merge-conflict` zeigt, dass er es getan hat, bis GitHub den neuen Branch mergebar findet. Die beiden Bilder-Bots vermeiden die meisten Konflikte, bevor sie einen öffnen: Ein Rendern, das auf das davor gewartet hat, rendert `main` so, wie es dann ist, und hat `main` ein Bild oder eine Seite des Pull Requests geändert, während die Bilder gerendert wurden, etwa weil der Pull Request davor gemergt wurde, lässt der Bot seinen Branch, wie er ist, und rendert `main` neu. Der Diagramm-Bot und der Fix-Bot brauchen beides nicht: Jede Änderung von `main`, die mit ihrem Pull Request in Konflikt geraten kann, startet sie ohnehin.

**Womit:** `update-branches.yml`, `screenshot-bot.yml`, `docs-pictures.yml` und `sync-issue-assistant.yml` ([Entscheidung 0118](../decisions/0118-a-bot-whose-pull-request-conflicts-builds-it-anew-at-once.md)).

## Wenn eine Prüfung scheitert oder abbricht

Eine Prüfung, die ein Runner, eine Website oder GitHub für einen Moment scheitern lässt oder die ein Wettlauf zweier Läufe abbricht, braucht niemanden: Die Bots nach den Prüfungen führen sie einmal neu aus und lassen nur rot, was aus einem Grund scheitert.

- **Ein Download, der hängt, beginnt neu, bevor ein Bot nötig ist:** Jeder Download der Website ohne eigene Grenze, etwa einer des Social-Plugins, bekommt 10 Sekunden für die Verbindung und 30 für jeden nächsten Teil der Datei, und jeder Download beginnt zweimal neu. In den Variants weicht ein Setup von uv, das nicht binnen zwei Minuten endet, einem zweiten aus den Releases von uv auf GitHub, und ein Container, dessen Image nicht herunterzuladen war, startet neu. Nur was bei jedem Versuch scheitert, lässt seinen Schritt scheitern (Entscheidung 0061 der [Entscheidungen](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **Ein Build der Website, der auf sich selbst wartet, hängt nicht mehr:** Das Social-Plugin von Material zeichnet die Ebenen seiner Vorschaukarten in Threads, und eine Karte konnte ohne Ende auf eine Ebene warten, die eine andere Karte gerade startete. Die Hooks der Website lassen sie auf den Job selbst warten, sodass der Build endet; und ein Build, der nach vier Minuten noch läuft, schreibt in sein Log, wo jeder seiner Threads steht, bevor die fünf Minuten seines Schritts enden (Entscheidung 0089 der [Entscheidungen](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **Ein Release, das GitHub trotzdem öffentlich gemacht hat, zählt:** GitHub lässt einen Aufruf manchmal scheitern, nachdem es getan hat, worum er bat. Den Aufruf, der v1.11.1 öffentlich machte, beantwortete es mit HTTP 502 und machte das Release dennoch öffentlich; so scheiterte der Job, und der Rollout nach dem Versuch, der den Job neu ausführte, hielt das Release für eines, das schon vorher hinausgegangen war: Kein Repository bekam es, bis eine Person den Rollout startete. Jetzt liest der Job, der veröffentlicht, das Release nach einem gescheiterten Aufruf erneut und zählt es, sobald das Release so öffentlich ist, wie der Aufruf es wollte: kein Entwurf, eine Vorabversion, wie sein Tag es sagt, ein Release für alle das neueste und angekündigt, wenn das Repository Announcements hat. Sonst ruft er erneut auf, höchstens dreimal, 15 Sekunden auseinander, wie bei den Kategorien der Diskussionen, die er zuerst liest; erneut aufgerufen, ändert der Aufruf nichts, was schon getan ist, und GitHub verknüpft keine zweite Diskussion mit einem Release. Und der Rollout nimmt das Release, das öffentlich wurde, nachdem ein Job des Laufs, der veröffentlicht, begonnen hatte, in welchem Versuch auch immer, damit ein Lauf, den GitHub oder ein Bot neu ausführte, sein Release trotzdem in jedes Repository bringt ([#661](https://github.com/Dennis-Otto/repo-blueprint/issues/661)).
- **Ein Download übersteht einen Ausfall von GitHub:** Jedes Werkzeug, das ein Schritt des Blueprints aus einem Release auf GitHub lädt, etwa lychee, CodeQL, gitsign, krankerl, Infection oder syft, kommt über die API von GitHub mit dem Token des Jobs. Am 8. November 2026 liefen die Downloads von GitHub ohne Token stundenlang in Zeitüberschreitungen, und die Linkprüfung und CodeQL schlugen in jedem Repository fehl, während die API weiter funktionierte. `.github/download.sh` versucht es nach einem Fehler von GitHub erneut, fünfmal, im Abstand von 10, 20, 40 und 80 Sekunden, prüft den Download an seiner festgelegten sha256 oder an dem Digest, den GitHub davon führt, und wenn GitHub weiter scheitert, sagt seine Annotation, dass es ein Ausfall von GitHub ist und kein Problem der Änderung, mit dem Link zu [githubstatus.com](https://www.githubstatus.com). CodeQL analysiert mit der Version, die seine Action mitbringt und die der Runner meist schon hat, und auch der Bot für wackelige Tests fragt GitHub erneut, wenn es mit einem eigenen Fehler antwortet ([Entscheidung 0133](../decisions/0133-the-downloads-of-the-workflows-go-through-the-api.md)).
- **Einmal, nicht immer wieder:** Der Bot für wackelige Tests führt die fehlgeschlagenen Jobs des ersten Versuchs eines Testlaufs einmal neu aus, ebenso der Bot für gescheiterte Releases mit einem Release, das ein Merge gestartet hat; ein Release, das du schon neu ausführst, gehört dir, und der Bot lässt es in Ruhe; der Bot für abgebrochene Prüfungen startet einen Lauf höchstens zweimal. Ein Job, den GitHub an seinem Zeitlimit stoppt, endet abgebrochen, nicht fehlgeschlagen, und läuft ebenfalls einmal neu: ein Test durch den Bot für wackelige Tests, eine andere Prüfung für den neuesten Commit eines Pull Requests oder von `main` durch den Bot für abgebrochene Prüfungen und ein Bot durch den Bot-Health-Bot. Ein Lauf, den du oder ein neuerer Lauf abgebrochen hat, bleibt abgebrochen, auch wenn ein Job, der auf die anderen wartet, deshalb fehlgeschlagen ist.
- **Ein Job läuft nicht ohne seine Sperre:** Harden-Runner macht ohne seinen Agenten weiter, wenn er ihn nicht laden kann, wie beim Ausfall von GitHub am 8. November 2026, als drei Antworten 504 einen Job von paperless-sync, der Jobs neu starten darf, und den Branch-Bot des Blueprints mit dem Token der Release-App ganz ohne Sperre laufen ließen. Deshalb prüft ein Job, der sperrt, unmittelbar bevor er auf seine Hosts wartet, ob der Agent läuft: Auf einen, der noch startet, wartet er höchstens eine halbe Minute, und sonst stoppt er mit einer Annotation, die den Ausfall nennt, statt mit seinen Secrets und Tokens jeden Host zu erreichen. Ein Test läuft durch den Bot für wackelige Tests einmal neu, der ihn nicht als wackeligen Test zählt, ein Bot von `main` durch den Bot-Health-Bot, ein Release durch den Bot für gescheiterte Releases und die übrigen Prüfungen eines Pull Requests, etwa sein Titel, seine Signaturen oder CodeQL, durch *After the checks* ([Entscheidung 0134](../decisions/0134-a-job-stops-when-harden-runner-doesnt-block.md)).
- **Ein Job hinter Harden-Runner wartet auf seine Hosts:** Ein Job, der jeden Host sperrt, den er nicht braucht, fragt zuerst die, die er braucht, höchstens zwei Minuten lang, weil Harden-Runner auf manchen Runnern von GitHub [eine Adresse eines erlaubten Hosts sperrt](https://github.com/step-security/harden-runner/issues/708), bis das DNS sie vergessen hat. Er fragt jeden Host auf dem Port, den der Job erlaubt, über HTTP auf 80 und über HTTPS auf jedem anderen, und nur ein Host, den er nicht auflösen oder erreichen kann, gilt als gesperrt ([Entscheidung 0124](../decisions/0124-the-wait-asks-each-host-on-its-own-port-and-a-project-limits-its-render.md)). Harden-Runner v2.22.4 räumt GitHubs DNS-Experiment, die Ursache, aus dem Weg, und ein Job, der sudo behält, etwa das Rendern des Screenshot-Bots, sorgt selbst dafür ([Entscheidung 0123](../decisions/0123-harden-runner-v2-22-4-and-a-job-with-sudo-takes-githubs-dns-experiment-away.md)). So ein Job kann nach seinem letzten Schritt trotzdem bis zu seinem Zeitlimit hängen und läuft dann einmal neu ([Entscheidung 0088](../decisions/0088-jobs-that-block-wait-for-their-hosts-and-try-again-when-they-hang.md)).
- **Ein Fehler, der sich wiederholt, ist echt:** Wenn dieselben Jobs schon für den Commit davor auf demselben Branch gescheitert sind, nachdem sie einmal neu liefen, laufen sie nicht noch einmal, damit ein kaputter Test keinen Runner umsonst beschäftigt.
- **Das Issue der wackeligen Tests** bekommt für jeden Lauf, der beim Neustart bestanden hat, einen Kommentar mit einer Tabelle: jeden Job, der zuerst fehlgeschlagen ist, mit einem Link zu seinem Log, den Schritt, der gescheitert ist, die Tests, die pytest im Log nennt, und den ersten Fehler. Seine Beschreibung zählt, wie oft jeder Job und Test gewackelt hat, und verlinkt den Lauf, in dem er es zuletzt getan hat, den neuesten zuerst, sodass der Test, der am meisten wackelt, auffällt, ohne jeden Kommentar zu lesen. Der Bot liest jedes Log mit seinen Farben, mit jeder Version der GitHub CLI; ein Log, das GitHub nicht herausgibt, lässt die Zeile ohne ihre Tests, und eine Warnung des Laufs sagt, warum.
- **Tests, die pytest nicht ausführt,** etwa die Browsertests eines Docker E2E, nennen den gescheiterten Test ebenfalls, mit `uvx --from copier==9.19.1 copier update --defaults --vcs-ref=:current: --data "test_marker=Browser step:"`: Schreibt das Log eines solchen Jobs diesen Text vor den Namen jedes Tests oder Schritts, sobald er beginnt, nennt der Bot den, den das Log vor dem Fehlschlag zuletzt nennt, im gescheiterten Schritt des Jobs und im gescheiterten Worker, und nimmt die erste Exception danach als Fehler, wenn keine Annotation einen nennt.
- **Was das Issue von einem Pull Request zeigt:** Ein Name oder eine Zeile eines Logs steht dort als reiner Code, sodass ein Pull Request damit weder die Tabelle beenden noch jemanden erwähnen kann, und den Branch eines Forks, den er benennt, wie er will, nennt es nicht.
- **Die schnellen Prüfungen laufen einmal für jeden Commit:** Titel und Changelog, Dependency Review, Secret Scan, Bereichs-Labels und Website. Ein verspäteter Lauf für einen älteren Commit, etwa einer, den eine Änderung des Release-Pull-Requests startet, während release-please in ihn pusht, bricht sie für den neuesten Commit nicht mehr ab. Die Prüfungen, die Minuten dauern, Tests, Lint, CodeQL und die Varianten, brechen den Lauf für einen älteren Commit weiter ab; einen Wettlauf dort repariert der Bot für abgebrochene Prüfungen.
- **Ein Commit, den ein neuerer ersetzt hat, gibt seine Runner frei:** Der Bot für ersetzte Commits bricht die Läufe der Prüfungen eines Commits ab, den kein offener Pull Request als Head hat, und die eines gemergten Pull Requests, außer den Bereichs-Labels, die Labels schreiben, [ohne eigenen Runner](bots.de.md#ersetzte-commits).
- **Ein neuerer Push auf `main` bricht die Prüfungen des Pushes davor ab:** Die Tests, CodeQL, die Link-Prüfung, OSV-Scanner und die Prüfung der Workflow-Sicherheit von `main` sagen nur, wie es um `main` steht, und das sagt der Lauf des neueren Commits auch, also hören sie auf, wie in einem Pull Request, und überlassen ihre Runner den Läufen, auf die es ankommt. Die Website, das Release und die Bots, die committen oder GitHub ändern, beenden, was sie begonnen haben, und einen Lauf nach Zeitplan oder von Hand bricht kein Push ab. Hat ein verspäteter Lauf für einen älteren Commit den Lauf für den neuesten Commit von `main` abgebrochen, startet ihn der Bot für abgebrochene Prüfungen neu, sodass die Coverage von `main`, die Alerts des Code Scannings und der Fix-Bot immer seinen neuesten Commit sehen (Entscheidung 0076 der [Entscheidungen](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **Weitere Test-Workflows** eines Repositorys, etwa visuelle Tests, kommen mit `uvx --from copier==9.19.1 copier update --defaults --vcs-ref=:current: --data "test_workflows=Visual check, Screenshot bot"` zur CI und zu Docker E2E dazu, auch für den Fix-Bot, und der Bot für ersetzte Commits bricht ihre Läufe eines ersetzten Commits ab.
- **Die Link-Prüfung eines Pull Requests** liest die Dokumente, die er ändert, und alle Dokumente, wenn er die Regeln oder lychee selbst ändert oder eine Datei verschiebt oder löscht, auf die ein Dokument verlinken kann. lychee behält die Antworten der Websites einen Tag lang und fragt bei einem Link, der gescheitert ist, erneut nach, sodass eine Website, die für einen Moment nicht erreichbar ist, nur die Pull Requests scheitern lässt, die auf sie verlinken. Sie lässt nur das Changelog, die Texte der Lizenzen in `LICENSES/` und die Ordner der Abhängigkeiten und eines Builds aus, etwa `node_modules/` und `dist/`, nie ein Dokument, dessen Name ein solches Wort nur enthält, etwa `docs/decisions/0000-template.md`.

## Wenn ein Bot fehlschlägt

Ein Bot oder ein geplanter Workflow, der auf `main` fehlschlägt, führt seine fehlgeschlagenen Jobs einmal neu aus, wo ein zweiter Versuch bestehen kann, und hält sonst ein Issue pro Workflow offen, mit den fehlgeschlagenen Jobs, ihren Schritten und ihren ersten Fehlern, das der nächste bestandene Lauf schließt, sobald die fehlgeschlagenen Jobs in ihm wieder bestanden; jede Nacht ein Blick auf den letzten Lauf jedes Workflows, auch der des Projekts, der einen Workflow startet, dessen Zeitplan GitHub verpasst oder abgeschaltet hat, und um den Upload einer neuen Social Preview bittet; wo ein Renovate-Workflow läuft, ein Issue mit den Warnungen und Fehlern von Renovate.

**Womit:** `bot-health.yml`, `blueprint.py bot-health`.

GitHub schickt den Fehlschlag eines geplanten Laufs nur an den, der seinen Zeitplan zuletzt geändert hat, und den eines anderen Laufs an den, der ihn gestartet hat, in diesen Repositorys meist die Release-App: Ein roter Bot zeigte sich nur im Actions-Tab, so wie Findings, Mutation und Renovate tagelang fehlschlugen. Der Bot für den Zustand der Bots (`bot-health.yml`) macht aus jedem solchen Fehlschlag ein Issue und schließt es, sobald die fehlgeschlagenen Jobs wieder bestehen.

Ein erster Fehlschlag, den ein zweiter Versuch beheben kann, führt seine fehlgeschlagenen Jobs einmal neu aus. Ein Fehlschlag, der bleibt, öffnet ein Issue für den Workflow oder aktualisiert es, mit den fehlgeschlagenen Jobs, ihren Schritten und ihren ersten Fehlern. Ein Lauf, der besteht, schließt das Issue, sobald jeder Job, der fehlschlug, in ihm erneut lief und bestand, in jedem Zweig einer Matrix; ein Lauf, der einen solchen Job übersprang, oder einer ohne ihn lässt das Issue offen. Jede Nacht sieht sich der Bot den letzten Lauf jedes Workflows an, falls GitHub ein Ereignis verloren hat, überlässt aber einen Workflow, der ein eigenes Issue hält, diesem Issue. Er startet einen Workflow, dessen Zeitplan GitHub verpasst oder abgeschaltet hat: einen ohne Lauf seines Zeitplans oder von Hand seit der Zeit seines Zeitplans, gleich welche Pushes ihn seitdem ausgeführt haben.">
</picture>

- **Ein Issue pro Workflow,** mit einem Titel wie *Findings fails on main* und den Labels `bot-failure` und `maintenance`. Es nennt den letzten fehlgeschlagenen Lauf, seinen Versuch und seinen Auslöser und eine Tabelle der fehlgeschlagenen Jobs mit dem Schritt, der fehlschlug, und dem ersten Fehler eines jeden, aus den Annotationen des Laufs. Ein späterer Fehlschlag an derselben Stelle aktualisiert es nur, ohne Benachrichtigung; ein Fehlschlag in einem anderen Job oder Schritt fügt einen Kommentar hinzu. Der nächste Lauf, der besteht, schließt es mit einem Link auf diesen Lauf, sobald jeder Job, der fehlschlug, in ihm erneut lief und bestand: ein Job einer Matrix nach seinem Namen vor den Werten, etwa `render` für `render (en, 3/4)`, in jedem Zweig. Ein Lauf, der einen solchen Job übersprang, wie ein Push, den der Screenshots-Workflow nur plant, oder ein Lauf ohne ihn lässt das Issue offen, und die Zusammenfassung des Bots nennt den Job; der nächtliche Blick liest auch bis zu fünf frühere Läufe, die nach dem Fehlschlag bestanden, falls GitHub das Ende eines solchen verlor, der das Issue schließt. Ein Job außerhalb einer Matrix zählt nur mit seinem eigenen Namen. Schließ das Issue von Hand, wenn ein Job weg ist oder einen neuen Namen hat ([Entscheidung 0126](../decisions/0126-a-failure-issue-waits-for-the-jobs-that-failed.md)).
- **Ein zweiter Versuch nur, wo er bestehen kann:** Ein erster Fehlschlag führt seine fehlgeschlagenen Jobs einmal neu aus, wie es der Bot für wackelige Tests bei den Tests tut, außer ein anderer Bot hat das schon getan. Findings, das fehlschlägt, solange ein Alarm offen ist, Mutation, das Stunden braucht, um dasselbe noch einmal zu messen, und die Property-Tests und das Fuzzing, die an einer Eingabe fehlschlugen, die sie gefunden haben, werden sofort gemeldet. Ein Lauf, den GitHub nicht starten konnte, weil seine Workflow-Datei ungültig ist, ebenso.
- **Welche Läufe zählen:** die der Bots und geplanten Workflows, die `bot-health.yml` aufzählt, auf dem Standardbranch, von einem Zeitplan, einem Push, einem Start von Hand oder einem anderen Workflow, nie von einem Pull Request oder einem Fork, und die Prüfung eines Releases, das jemand von Hand oder mit einem Token veröffentlicht hat, die für seinen Tag läuft und ein eigenes Issue bekommt, das nur ein Lauf für diesen Tag schließt. Die Prüfungen, die in Pull Requests laufen, etwa die CI, die Website oder CodeQL, und die Workflows des Projekts zählen im nächtlichen Blick, der den letzten beendeten Lauf jedes Workflows auf dem Standardbranch nimmt, sodass keiner ihrer Läufe für einen Pull Request einen Lauf des Bots startet. Einem Lauf, den das Ende einer Prüfung eines Pull Requests startet, wie bei After the checks, gibt GitHub ebenfalls den Standardbranch, deshalb zählt der nächtliche Blick bei einem solchen Workflow nur dessen andere Läufe. Der Workflow Diagrams, Newest Node, Newest Python und Next runner halten je ein eigenes Issue, ebenso ein Workflow des Projekts, der es in einer Kommentarzeile `# bot-health: own-issue` sagt, etwa End-to-End-Tests, deren wöchentlicher Lauf gegen das kommende Release eigene Issues hält: Der nächtliche Blick öffnet und schließt für sie keines, nur das, das er vor dieser Zeile geöffnet hat, und startet weiterhin einen Zeitplan, den GitHub verpasst hat. Die Zeile ist für einen Workflow, der jeden Fehlschlag auf dem Standardbranch selbst meldet, auch den eines Pushs, denn der nächtliche Blick meldet dann keinen seiner Läufe. Lint läuft auf dem Standardbranch nur in seinem wöchentlichen Lauf, weil ein Pull Request diesen Branch nur erreicht, wenn er Lint besteht; ein Fehler von Lint an einem Commit, den der Branch verlassen hat, sagt also nichts mehr: Der nächtliche Blick öffnet dafür kein Issue und startet Lint von Hand, wenn dessen Issue offen ist, sodass ein Lauf, der besteht, es schließt.
- **Verpasste Zeitpläne:** GitHub führt einen Zeitplan zu Stoßzeiten verspätet aus, manchmal gar nicht, und schaltet die Zeitpläne eines Repositorys nach 60 Tagen ohne Aktivität ab. Jede Nacht startet ein Workflow von Hand, der seit der letzten Zeit seines Zeitplans, die sechs Stunden oder länger her ist, keinen Lauf seines Zeitplans oder von Hand hatte, höchstens vier pro Nacht, damit die Pull Requests ihre Runner behalten; ein Push seitdem zählt nicht, denn sein Lauf kann auslassen, was nur der Zeitplan tut, etwa die Tests des kommenden Releases; Findings, Issue lifecycle und der Issue assistant sync des Blueprints starten mit abgeschaltetem `dry_run`, wie ihr Zeitplan sie ausführt. Einen Zeitplan, den GitHub abgeschaltet hat, schaltet der Bot wieder ein.
- **Die Social Preview:** GitHub nimmt das Bild für die Karten von Links auf ein Repository nur aus einem Upload unter *Settings → General → Social preview*, den keine API bietet, sodass ein neues `.github/social-preview.png` bisher ungesehen blieb, bis jemandem die alte Karte auffiel. GitHub liefert den Upload Byte für Byte unter der `openGraphImageUrl` des Repositorys aus, von `repository-images.githubusercontent.com`, dem einzigen Host neben GitHubs API, den der nächtliche Blick erreichen darf. Jede Nacht vergleicht er den sha256 dieses Uploads mit dem committeten Bild und hält ein Issue, *Upload the new social preview*, mit den Labels `bot-failure` und `maintenance`, dem Bild und dem Link zu den Einstellungen offen, solange sie sich unterscheiden: Ein Bild, das sich wieder ändert, aktualisiert es ohne Benachrichtigung, und die Nacht nach dem Upload schließt es. Eine Seite, die noch das Standard-Panel ihrer Art zeigt, hat noch kein Bild zum Hochladen, da die Checkliste zuerst bittet, das Panel zu ersetzen, und ein Repository ohne das Bild bekommt kein Issue. Ein privates Repository bekommt auch keines, und der Blick lädt dort nichts herunter: GitHub zeigt die Social Preview nur für ein öffentliches Repository und nimmt in einem privaten nur dort einen neuen Upload, wo schon einmal einer hochgeladen wurde, sodass das Issue um ein Bild bäte, das niemand sieht. Ein Issue, das ein Repository behielt, als es privat wurde, schließt sich, und der Blick fragt wieder, sobald das Repository öffentlich ist. Lässt sich der Upload nicht lesen, schlägt der Blick mit dem Grund fehl, wie wenn er einen Workflow nicht ansehen kann ([Entscheidung 0132](../decisions/0132-the-bot-health-bot-asks-for-the-upload-of-a-new-social-preview.md)).
- **Die Probleme von Renovate:** Renovate, das im Blueprint für die Repositorys seines Eigentümers läuft und in einem Repository jedes anderen Eigentümers für dieses, protokolliert eine Lock-Datei, die es nicht lesen kann, als Warnung, ohne fehlzuschlagen. Der Renovate-Workflow hält ein Issue, *Renovate logs problems*, mit den Warnungen und Fehlern seines letzten Laufs, der welche hatte, nach Repository, und schließt es nach drei Läufen in Folge ohne eines. Ein öffentliches Issue nennt nur öffentliche Repositorys.
- Der Bot liest Läufe, Jobs und Annotationen und schreibt Issues mit dem `GITHUB_TOKEN` seines Jobs, und er checkt nur den Standardbranch aus, nie den Code eines Pull Requests. Ein Repository, dessen `.github/labels.toml`, die dem Projekt gehört, kein `bot-failure` hat, bekommt das Label vom Bot; trag es in die Datei ein, damit Farbe und Beschreibung an einem Ort bleiben.
