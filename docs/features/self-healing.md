# Fix bot and self-healing

What a repository fixes by itself: the findings that a command can fix, tests that fail once, checks that stop, releases and bots that fail.

## Fix bot

A check that fails fixes what a command can fix, such as the format of the code, trailing whitespace and line endings, the rules of markdownlint and the pages in one column: the bot commits the fixes onto a branch of the repository, also one of Renovate, as one commit, suggests them at their lines on a pull request from a fork, where `/fix` of a maintainer commits them, and keeps one pull request with the fixes of `main` that merges itself; `python3 .github/blueprint.py fix run` makes the same fixes on your machine.

**How:** `autofix` in `.github/checks.toml`, `after-checks.yml`, `commands.yml`.

## Pull requests fix themselves

Fix first, explain second: what a command can fix of a check that failed, the pull request fixes by itself, also a pull request of Renovate, and `main` too.

- **The check fixes:** each explanation of `.github/checks.toml` says in `autofix` which commands fix what its check finds, or why no command can; a test of the blueprint fails for one that doesn't say. When a check fails, its job runs those commands on the head of the pull request, with the tools that it installed already: the text files, the pages in one column, the version of the release bot, but not where the pull request changed `.release-please-manifest.json` itself, which a person sets back, as only the release bot changes it ([decision 0069](../decisions/0069-a-lock-file-and-a-version-fix-themselves-only-where-their-tool-refuses-them.md)), Ruff, php-cs-fixer or Biome, a lock file of Composer or npm that its tool refuses, locked again with the least change, and a lock file of pip-compile that no longer matches its source, compiled again on the versions that it pins ([decision 0103](../decisions/0103-a-lock-file-of-pip-compile-compiles-again-on-its-own-pins.md)), for `scripts/check.sh`, markdownlint for the Markdown. It keeps the files that they changed as an artifact.
- **A check of the project as well:** the bot reads the fixes of every workflow in the list `workflows:` of `after-checks.yml` of `main`, such as Docker E2E and what the answer `test_workflows` names, and of no other, whatever a pull request names its runs ([decision 0107](../decisions/0107-the-fix-bot-reads-every-workflow-of-its-list.md)). For a check of your own, name the commands in `autofix` in `.github/checks.project.toml`, and copy the steps *Fix what a command can fix* and *Keep the fixes for the fix bot* of `ci.yml` to the end of its job, with its name in `CHECK` and an artifact `fixes-<name>` of its own, which in a matrix job also holds `strategy.job-index`, since each leg needs its own; its checkout needs `fetch-depth: 2`. The bot waits only for the workflows whose files on `main` keep such an artifact, so a long run that keeps none holds up no fix.

- **A move of a release as well:** what a release needs changed in a file of the project, such as the group of a label, fails the step *Files of the project* on the pull request of the update, and the bot commits it there ([how](updates.md#what-a-release-moves-in-a-file-of-the-project)).
- **One commit on a branch of the repository:** once the checks of the commit that fix have ended, the fix bot commits all their fixes as one commit onto the branch, as the release app, with its sign-off, and the checks run again; the comment of the PR coach names the files. This works on the branches of Renovate and the other bots as well, so that an update of a formatter stays green and merges itself.
- **A check that outlasts the wait:** the bot waits up to a quarter of an hour for the checks of a commit that keep fixes. When one still runs then, such as long end-to-end tests, it commits nothing on a branch of the repository, since a commit would cancel that run and use up one of its two commits on a part of the fixes. The end of that run starts the bot again, however it ended, and that job makes the one commit with every fix; any other job of that commit then finds a new head and commits nothing. So the job of the bot starts after every run of a check for the head of a pull request from a branch of the repository, and ends after a few seconds when the commit has no fix. A suggestion on a fork and the pull request of `main` cancel no run, so they take what has ended ([decision 0112](../decisions/0112-the-fix-bot-leaves-a-commit-to-the-run-that-ends-last.md)).

- **Suggestions on a fork:** after the checks, the bot suggests the fixes at their lines of a pull request from a fork, ten at most in one review and none twice; **Commit suggestion** takes one. A fix that no suggestion shows, such as line endings, names its file, and the PR coach the command.
- **`/fix` on a pull request:** a person with write access to the repository comments `/fix`, as the first line of a comment, and the bot commits the fixes of the head onto its branch, as the release app, with a pair of eyes on the comment at once and one comment with what it did. That works on a branch of the repository, also one with the label `no-bot-fixes`, which stops only the bot's own commits, and on a fork whose author allows edits by maintainers. There the bot commits only the files that the pull request changes, and none that decides what a workflow runs, such as a file of `.github/` or `scripts/` or `pyproject.toml`, whose fix stays a suggestion for a person. Whether GitHub lets the release app push onto the branch of a fork isn't settled, so a refusal is no failure: the fork gets the suggestions at their lines, as without the command, and so does a fork that allows no edits. The bot waits for the checks of the head that keep fixes, as after the checks; while one still runs after a quarter of an hour, it commits nothing, and `/fix` once more after its end makes the commit. One command runs at a time for each pull request, and a `/fix` given while another one waits replaces the waiting one. Anybody without write access gets that answer, and the fork's code never runs with the token: the job checks out `main` alone and takes the fixes of the checks as data ([decision 0117](../decisions/0117-a-person-asks-for-the-fixes-of-a-fork-with-a-command.md)).

- **main heals itself:** when a check of `main` fails with fixes, one pull request from `bot/self-heal` holds them and merges itself once every check passes; the bot closes it once `main` needs none, and a failure of the bot keeps one issue open.
- **Also what no commit changes:** each week Lint and the CI run on `main` as well, so that a new rule of a tool repairs itself through that pull request instead of failing the next person's pull request. The checks run as ever, and only one that fails runs its fixers, so a quiet week takes one run of each, opens nothing and starts no job of the bot. A schedule that GitHub missed starts by hand, which counts the same, and a check that fails with no command to fix it keeps one issue of bot health open ([decision 0105](../decisions/0105-the-fixers-run-on-main-every-week.md)).
- **The title and the entry of the changelog, on a branch of the repository:** the check of the title runs nothing of a pull request, so a job of its own reads the pull request from the API once that check has failed. A title that names its own type and differs only in its form, such as `Feat: add a dark mode` or `feat(Settings) add a dark mode`, becomes the one that the PR coach suggests. The type and the breaking mark decide the version, so a word for a type, such as `Feature:`, and a title whose type only its words or its branch could give stay suggestions. A `feat`, `fix` or `perf` of a person without an entry gets a draft from that title, as one new file of `changelog.d/` named after the branch, below the heading of its kind, once for each pull request; the PR coach asks you to read it, and to say in its place what changes for users. Delete it, and the check explains instead. A title with HTML, a mention or a link gets no draft, and a pull request from a fork keeps its suggestion and its explanation ([decision 0110](../decisions/0110-the-fix-bot-corrects-the-form-of-a-title-and-drafts-one-entry.md)).

- **Safe with any pull request:** the bot runs nothing of a pull request with a token that can write. It takes the fixes as data, with `blueprint.py` of `main`, and lets through only text files that the commit has already, by plain paths, outside `.git` and the workflows; the draft of an entry, the one new file that it ever adds, it names and writes itself. It commits at most twice in a row (once more for a check that ends later), never a third time, and a pull request with the label `no-bot-fixes` gets no commit.
- **On your machine:** `python3 .github/blueprint.py fix run` runs the commands of every step of `scripts/check.sh`, `python3 .github/blueprint.py fix text` fixes the text files alone, and `python3 .github/blueprint.py fix version` writes the version of the release bot back where a hand changed it; with `--base origin/main`, after `git fetch origin main`, it writes none where the manifest differs from that of `main`, as in the CI (on a fork, use the remote of the upstream repository, such as `upstream/main`).

## Flaky tests

A test run that fails, or whose job runs out of time, runs its failed jobs once more, unless the same jobs broke for the commit before; a job that passes then is reported as flaky in one issue, with the step, the test and the error that failed, and the issue counts how often each job and test flaked.

**How:** `after-checks.yml`.

## Cancelled checks

The quick checks run once for each commit, so that no run for another commit cancels them; a run of a longer required check for the latest commit of a pull request that a late run for an older commit cancelled starts again by itself instead of blocking the merge; a newer push to `main` cancels the tests and scanners of the push before, and their run for the head of `main` starts again as well when a late run cancelled it. A job that ran out of time, as one that hangs behind Harden-Runner can, runs once more for the head of a pull request or of `main`.

**How:** `after-checks.yml`.

## Failed releases

The release of a merge that fails, as at a push of its tag that GitHub refuses for a moment, runs its failed jobs once more by itself, where they stopped. A second try also takes up a release that the first left as a draft, as when its job hung after it had created the release.

**How:** `after-checks.yml`.

## Pull requests of the bots that conflict

The screenshot bot, the picture bot of the blueprint and the sync bot of the issue assistant build the branch of their pull request anew from `main`, but run only after a release, every week or every hour. When one of their pull requests conflicts with `main`, the branch bot starts the bot's workflow at once instead of asking a person to merge `main`, once for each conflict: the label `merge-conflict` shows that it did, until GitHub finds the new branch mergeable. The two picture bots avoid most conflicts before they open one: a render that waited for the one before renders `main` as it is then, and when `main` changed a picture or a page of the pull request while the pictures rendered, as when the pull request before merged, the bot leaves its branch as it is and renders `main` anew. The diagram bot and the fix bot need neither: every change of `main` that can conflict with their pull request starts them anyway.

**How:** `update-branches.yml`, `screenshot-bot.yml`, `docs-pictures.yml` and `sync-issue-assistant.yml` ([decision 0118](../decisions/0118-a-bot-whose-pull-request-conflicts-builds-it-anew-at-once.md)).

## When a check fails or stops

A check that a runner, a site or GitHub fails for a moment, or that a race of two runs cancels, needs no person: the bots after the checks run it once more, and leave red only what fails for a reason.

- **A download that hangs starts again, before a bot is needed:** each download of the website that sets no time limit of its own, such as one of the social plugin, gets 10 seconds to connect and 30 for each next part of the file, and every download starts again twice. In the Variants, a setup of uv that doesn't end within two minutes gives way to a second one from the releases of uv on GitHub, and a container whose image failed to download starts again. Only what fails every attempt fails its step (decision 0061 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **A build of the website that waits for itself no longer hangs:** the social plugin of Material draws the layers of its preview cards in threads, and a card could wait without end for a layer that another card was just starting. The hooks of the website let it wait for the job itself, so the build ends; and a build still running after four minutes prints where each of its threads stands, before the five minutes of its step end (decision 0089 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **A release that GitHub made public all the same counts:** GitHub at times fails a call after it has done what was asked. It answered the call that made v1.11.1 public with an HTTP 502 and made the release public anyway, so the job failed, and the Rollout that followed the attempt that ran the job again took the release for one that had gone out before: no repository got it until a person started the Rollout. Now the job that publishes reads the release again after a call that failed, and counts it once the release is public as asked: no draft, a prerelease as its tag says, a release for everybody the latest one, and announced when the repository has Announcements. Otherwise it makes the call again, three times at most, 15 seconds apart, as it does with the categories of the discussions that it reads first; made again, the call changes nothing that is done already, and GitHub links no second discussion to a release. And the Rollout takes the release that went public after a job of the run that publishes started, in whichever attempt, so that a run that GitHub or a bot ran again still brings its release to every repository ([#661](https://github.com/Dennis-Otto/repo-blueprint/issues/661)).
- **A download survives an outage of GitHub:** every tool that a step of the blueprint downloads from a release on GitHub, such as lychee, gitleaks, CodeQL, gitsign, krankerl, Infection or syft, comes through GitHub's API with the token of the job. On 8 November 2026, GitHub's downloads without a token timed out for hours, and the link check and CodeQL failed in every repository, while the API kept working. `.github/download.sh` tries again after an error of GitHub, five times, 10, 20, 40 and 80 seconds apart, checks the download by its pinned sha256, or by the digest that GitHub keeps of it, and when GitHub keeps failing, its annotation says that it is an outage of GitHub, not a problem of the change, with the link to [githubstatus.com](https://www.githubstatus.com). CodeQL analyzes with the version that its action brings, which the runner usually has already, and the flaky-test bot asks GitHub again as well when it answers with an error of its own. The weekly SBOM runs the syft of a release too, rather than an action whose installer downloaded syft without a token, and the secret scan runs the gitleaks of a release, which Renovate keeps current, and writes the table of its findings itself, rather than an action that downloaded an old gitleaks without a token ([decision 0139](../decisions/0139-the-secret-scan-runs-gitleaks-of-its-release.md)). The setups of uv, Python and Node.js take the token of the job on their own, and mostly find their version in the tool cache of the runner; Harden-Runner and the setup of PHP still download their own tools from the page of a release without a way through the API, and setup-php falls back to its mirrors, and the decision says what each would need ([decision 0133](../decisions/0133-the-downloads-of-the-workflows-go-through-the-api.md)). The build of a Nextcloud app's release, which blocks those mirrors, signs the app on the PHP that the runner ships, as it is, so setup-php downloads nothing there.
- **Once, not again and again:** the flaky-test bot runs the failed jobs of the first attempt of a test run once more, and so does the bot for failed releases with a release that a merge started; a release that you already run again is yours, and the bot leaves it alone; the bot for cancelled checks starts a run twice at most. A job that GitHub stops at its time limit ends cancelled, not failed, and runs once more as well: a test by the flaky-test bot, another check for the head of a pull request or of `main` by the bot for cancelled checks, and a bot by the bot-health bot. A run that you or a newer run cancelled stays cancelled, even when a job that waits for the others failed because of it.
- **A job doesn't run without its block:** Harden-Runner goes on without its agent when it can't download it, as in GitHub's outage of 8 November 2026, when three answers 504 left a job of paperless-sync that may run jobs again, and the branch bot of the blueprint with the token of the release app, without any block. So right before it waits for its hosts, a job that blocks makes sure that the agent runs: it waits half a minute at most for one that is still starting, and otherwise stops with an annotation that names the outage, instead of reaching every host with its secrets and tokens. A test runs once more by the flaky-test bot, which counts it as no flaky test, a bot of `main` by the bot-health bot, a release by the bot for failed releases, and the other checks of a pull request, such as its title, its signatures or CodeQL, by *After the checks* ([decision 0134](../decisions/0134-a-job-stops-when-harden-runner-doesnt-block.md)). The bots of events, such as *Welcome* or the command `/fix`, also in a pull request of a fork, and the workflows with an issue of their own, such as *Newest Node*, run once more by the bot-health bot, which opens no issue for them, and a workflow of one try, such as *Mutation*, gets its second try too when Harden-Runner stopped each of its jobs that failed ([decision 0141](../decisions/0141-the-bot-health-bot-runs-every-bot-again-that-harden-runner-stopped.md)).
- **An outage of GitHub doesn't multiply:** on 9 November 2026, GitHub ended every run of every repository before its first job for five minutes, with *Internal server error*, and each of those runs started the bots that follow it, which GitHub ended the same way: over a hundred failed runs, each a mail. A bot that follows the end of a run now asks for its jobs first, and when GitHub couldn't start the run, as no job of it failed in a step, it reports nothing, runs nothing again and moves no line, with a notice: the bot-health bot opens no issue, the flaky-test bot, the bot for failed releases and the bot for stopped checks run nothing again while GitHub fails, and the branch bot keeps its line. The daily look of the bot-health bot runs such a run of `main` again once, and reports it only when GitHub couldn't start that try either. Every call of GitHub's API tries again after a 5xx or a call without an answer, three times, 10, 20 and 40 seconds apart, and a bot that GitHub keeps failing ends with the notice *GitHub is unavailable* instead of a failure: its next event or look catches up, and you have nothing to do. A refusal, such as a missing permission, still fails the bot, and a check still fails when GitHub fails. The runs that GitHub itself couldn't start still mail once each, as no workflow can keep GitHub from creating them ([decision 0136](../decisions/0136-an-outage-of-github-starts-no-bot-failure.md)).
- **A job behind Harden-Runner waits for its hosts:** a job that blocks every host that it doesn't need first asks those it needs, for two minutes at most, because on some of GitHub's runners Harden-Runner [blocks an address of a host that it allows](https://github.com/step-security/harden-runner/issues/708) until the DNS has forgotten it. It asks each host on the port that the job allows, by HTTP on 80 and by HTTPS on any other, and only a host that it can't resolve or reach counts as blocked ([decision 0124](../decisions/0124-the-wait-asks-each-host-on-its-own-port-and-a-project-limits-its-render.md)). Harden-Runner v2.22.4 takes GitHub's DNS experiment, the cause, out of its way, and a job that keeps sudo, such as the render of the screenshot bot, makes sure itself ([decision 0123](../decisions/0123-harden-runner-v2-22-4-and-a-job-with-sudo-takes-githubs-dns-experiment-away.md)). Such a job can still hang after its last step until its time limit, and then runs once more ([decision 0088](../decisions/0088-jobs-that-block-wait-for-their-hosts-and-try-again-when-they-hang.md)).
- **A failure that repeats is real:** when the same jobs broke for the commit before on the same branch, after they ran once more, the jobs don't run again, so that a broken test doesn't keep a runner busy for nothing.
- **The issue of flaky tests** gets a comment for each run that passed when it ran again, with a table: each job that failed at first, with a link to its log, the step that broke, the tests that pytest names in the log, and the first error. Its body counts how often each job and test flaked, and links the run in which it last did, the latest first, so the test that flakes most stands out without reading every comment. The bot reads each log with its colors, with every version of the GitHub CLI; a log that GitHub doesn't give leaves the row without its tests, and a warning of the run says why.
- **Tests that pytest doesn't run,** such as the browser tests of a Docker E2E, name the test that failed as well, with `uvx --from copier==9.19.1 copier update --defaults --vcs-ref=:current: --data "test_marker=Browser step:"`: when the log of such a job writes that text before the name of each test or step as it starts, the bot names the one that the log names last before the failure, in the step of the job and the worker that failed, and takes the first exception after it as the error when no annotation names one.
- **What the issue shows of a pull request:** a name or a line of a log is written as plain code, so a pull request can't end the table or mention anybody with it, and the branch of a fork, which it names as it likes, isn't named.
- **The quick checks run once for each commit:** the title and the changelog, the dependency review, the secret scan, the area labels and the website. A late run for an older commit, such as one that an edit of the release pull request starts while release-please pushes to it, no longer cancels them for the head. The checks that take minutes, the tests, Lint, CodeQL and the variants, still cancel the run for an older commit; the bot for cancelled checks repairs a race there.
- **A commit that a newer one replaced gives its runners back:** the bot for replaced commits cancels the runs of the checks of a commit that no open pull request has as its head, and of a pull request that merged, except the area labels, which write labels, [with no runner of its own](bots.md#runs-of-replaced-commits).
- **A newer push to `main` cancels the checks of the push before:** the tests, CodeQL, the link check, OSV-Scanner and the workflow security check of `main` only tell the state of `main`, which the run of the newer commit tells as well, so they stop, as in a pull request, and leave their runners to the runs that matter. The website, the release and the bots that commit or change GitHub end what they started, and no push cancels a run on a schedule or by hand. When a late run for an older commit cancelled the run for the head of `main`, the bot for cancelled checks starts it again, so that the coverage of `main`, the alerts of code scanning and the fix bot always see its newest commit (decision 0076 of the [decisions](https://github.com/Dennis-Otto/repo-blueprint/blob/main/docs/decisions/README.md)).
- **Other workflows of tests** that a repository has, such as visual tests, join the CI and Docker E2E with `uvx --from copier==9.19.1 copier update --defaults --vcs-ref=:current: --data "test_workflows=Visual check, Screenshot bot"`, for the fix bot as well, and the bot for replaced commits cancels their runs of a replaced commit.
- **The link check of a pull request** reads the documents that it changes, and every document when it changes the rules or lychee itself, or moves or deletes a file that a document may link to. lychee keeps the answers of the sites for a day and asks again for a link that failed, so that a site that is down for a moment fails only the pull requests that link to it. It leaves out only the changelog, the texts of the licenses in `LICENSES/` and the folders of the dependencies and of a build, such as `node_modules/` and `dist/`, never a document whose name merely holds such a word, such as `docs/decisions/0000-template.md`. Every document means those in `.github/` too, such as the template of pull requests, which the weekly run checks as well.

## When a bot fails

A bot or a scheduled workflow that fails on `main` runs its failed jobs once more where a second try can pass, and otherwise keeps one issue per workflow open, with the failed jobs, their steps and their first errors, which the next run that passes closes once the jobs that failed passed again in it; every night, a look at the latest run of every workflow, those of the project too, which starts a workflow whose schedule GitHub missed or switched off and asks for the upload of a new social preview; where a Renovate workflow runs, one issue with the warnings and errors of Renovate.

**How:** `bot-health.yml`, `blueprint.py bot-health`.

GitHub mails the failure of a scheduled run only to whoever last changed its schedule, and that of another run to whoever started it, in these repositories the release app for most runs: a red bot used to show only in the Actions tab, as when Findings, Mutation and Renovate failed for days. The bot-health bot (`bot-health.yml`) makes each such failure an issue, and closes it once the jobs that failed pass again.

A run that passes closes the issue once every job that failed ran again in it and passed, in every leg of a matrix; a run that skipped such a job, or one without it, leaves the issue open. Every night, the bot looks at the latest run of every workflow, in case GitHub lost an event, but leaves a workflow that keeps an issue of its own to that issue. - **One issue per workflow,** titled like *Findings fails on main*, with the labels `bot-failure` and `maintenance`. It names the latest failed run, its attempt and its trigger, and a table of the failed jobs with the step that failed and the first error of each, from the annotations of the run. A later failure in the same place only updates it, without a notification; a failure in another job or step adds a comment. The next run that passes closes it with a link to that run, once every job that failed ran again in it and passed: a job of a matrix by its name before the values, such as `render` for `render (en, 3/4)`, in every leg. A run that skipped such a job, as a push that the Screenshots workflow only plans, or a run without it leaves the issue open, and the summary of the bot names the job; the nightly look also reads up to five earlier runs that passed after the failure, in case GitHub lost the end of one that closes the issue. A job outside a matrix counts only by its own name. Close the issue by hand when a job is gone or has a new name ([decision 0126](../decisions/0126-a-failure-issue-waits-for-the-jobs-that-failed.md)).
- **A second try only where it can pass:** a first failure runs its failed jobs once more, as the flaky-test bot does for the tests, unless another bot already did. Findings, which fails while an alert is open, Mutation, which takes hours to measure the same again, and the property tests and the fuzzing, which failed on an input that they found, are reported at once. A run that GitHub couldn't start, because its workflow file is invalid, too.
- **Which runs count:** those of the bots and scheduled workflows that `bot-health.yml` lists, on the default branch, from a schedule, a push, a start by hand or another workflow, never from a pull request or a fork, and the verification of a release that someone published by hand or with a token, which runs for its tag and gets an issue of its own that only a run for that tag closes. The checks that run in pull requests, such as the CI, the website or CodeQL, and the workflows of the project count in the nightly look, which takes the latest finished run of every workflow on the default branch, so that none of their runs for a pull request starts a run of the bot. GitHub gives a run that the end of a check of a pull request starts, as it starts After the checks, the default branch too, so the nightly look counts only the other runs of such a workflow. The Diagrams workflow, Newest Node, Newest Python and the Next runner keep an issue of their own, and so does a workflow of the project that says so in a comment line `# bot-health: own-issue`, such as end-to-end tests whose weekly run against the coming release keeps issues of its own: the nightly look opens and closes none for them, only the one that it opened before the line came, and still starts a schedule that GitHub missed. These workflows and the bots of events, *Area labels*, *Commands*, *Dependabot maintenance* and *Welcome*, count only when Harden-Runner stopped a job of their first attempt, also in a pull request or a fork: then their failed jobs run once more, without an issue, as nothing else would run them again. The line is for a workflow that reports every failure on the default branch itself, those of a push included, because the nightly look reports none of its runs then. Lint runs on the default branch only in its weekly run, because a pull request reaches that branch only when it passes Lint, so a failure of Lint at a commit that the branch has left says nothing any more: the nightly look opens no issue for it, and starts Lint by hand when its issue is open, so that a run that passes closes it.
- **Missed schedules:** GitHub runs a schedule late at busy times, sometimes not at all, and switches the schedules of a repository off after 60 days without activity. Every night, a workflow without a run of its schedule or by hand since the latest time of its schedule, six hours ago or more, starts by hand, at most four a night so that the pull requests keep their runners; a push since doesn't count, because its run may leave out what only the schedule does, such as the tests of the coming release; Findings, Issue lifecycle and the Issue assistant sync of the blueprint start with `dry_run` off, as their schedule runs them. A schedule that GitHub switched off is switched on again.
- **The social preview:** GitHub takes the picture for the cards of links to a repository only from an upload under *Settings → General → Social preview*, which no API offers, so a new `.github/social-preview.png` used to stay unseen until someone noticed the old card. GitHub serves the upload byte for byte at the `openGraphImageUrl` of the repository, from `repository-images.githubusercontent.com`, the one host besides GitHub's API that the nightly look may reach. Every night it compares the sha256 of that upload with the committed picture and keeps one issue, *Upload the new social preview*, with the labels `manual-step` and `maintenance`, the picture and the link to the settings, open while they differ: a picture that changes again updates it without a notification, and the night after the upload closes it. A page that still shows the default panel of its kind has no picture to upload yet, since the checklist asks first to replace the panel, and a repository without the picture gets no issue. A private repository gets none either, and the look downloads nothing there: GitHub shows the social preview only for a public repository and takes a new upload in a private one only where someone uploaded one before, so the issue would ask for a picture that nobody sees. An issue that a repository kept when it turned private closes, and the look asks again once the repository is public. When the upload can't be read, the look fails with the reason, as when it can't look at a workflow ([decision 0132](../decisions/0132-the-bot-health-bot-asks-for-the-upload-of-a-new-social-preview.md)). The label `manual-step` says what the issue is: nothing fails, a step waits for a person. The bot creates it where a repository's own `.github/labels.toml` lacks it, and an issue that an earlier release opened with `bot-failure` keeps that label until the upload closes it ([decision 0141](../decisions/0140-a-step-that-waits-for-a-person-has-a-label-of-its-own.md)).
- **Renovate's problems:** Renovate, which runs in the blueprint for the repositories of its owner and in a repository of any other owner for that one, logs a lock file that it can't read as a warning, without failing. The Renovate workflow keeps one issue, *Renovate logs problems*, with the warnings and errors of its latest run that had any, by repository, and closes it after three runs in a row without one. A public issue names public repositories only.
- The bot reads runs, jobs and annotations and writes issues with the `GITHUB_TOKEN` of its job, and checks out only the default branch, never the code of a pull request. A repository whose `.github/labels.toml`, which belongs to the project, lacks `bot-failure` gets the label from the bot; add it to the file to keep its color and description in one place.
