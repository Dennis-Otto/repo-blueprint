# Website, Diagramme und Screenshots

Die Website der Dokumentation, und die Diagramme und Screenshots, die sich selbst aktuell halten.

## Website

Die Dokumentation aus `docs/` als Website mit Suche und hellem und dunklem Design, das dem System folgt, bis der Leser eines wählt, auf Englisch und, mit deutschen Seiten wie `index.de.md` neben den englischen, auf Deutsch: jeder Pull Request baut sie streng und prüft die gebauten Seiten: jeden Link und jeden Anker, auch die in HTML geschriebenen, mit lychee und ohne Netz, und was die Hooks der Website versprechen, etwa eine Sitemap in jedem Ordner mit Seiten und die 404-Seite in der Standardsprache, dass keine Seite mehr als 1.200 KB auf einmal lädt und dass jede Seite jedes Bild ihres Markdowns zeigt, die Teile der README eingeschlossen, mit `blueprint.py site-check`, und `scripts/check-site.sh` ergänzt die Prüfungen des Projekts; ebenso `scripts/check.sh`, sobald die Werkzeuge ihrer Vorschau installiert sind, unter Linux, macOS und Windows; jede Änderung an `main` veröffentlicht den Build dieses Checks auf GitHub Pages, mit dem, was ein Hook in `site/.well-known/` schreibt, und die Schriften und Skripte, die er herunterlädt, bleiben eine Woche im Cache, signiert seine Herkunft, die `gh attestation verify` prüft, und fragt die veröffentlichte Website nach der Startseite jeder Sprache; barrierefrei, mit dem Kontrast und den unterstrichenen Links, die WCAG 2.2 AA verlangt, was axe-core in beiden Designs prüft, in der Breite eines Desktops und eines Handys, wo auch eine Seite scheitert, die seitlich scrollt, auf den Seiten, die ein Pull Request ändert, und auf jeder Seite auf `main` und jede Woche, und eine neue schwere oder kritische Verletzung lässt die Prüfung scheitern, außer `.github/a11y-accepted.toml` akzeptiert sie mit ihrem Grund; schnell auf dem Handy, mit Bildern, die erst laden, wenn der Leser zu ihnen kommt, einem GIF mit einem MP4 daneben als dieses Video, im Design und in der Breite des GIFs, einem Bild für jedes Design, das nur in seinem Design lädt, einem Bild, das die README von `main` ihres eigenen Repositorys zeigt, etwa `https://github.com/OWNER/NAME/raw/main/screenshots/settings.png`, aus dem Checkout, sodass der Pull Request, der einen Screenshot hinzufügt, ihn auch auf seiner Website zeigt, und einem, das Git nicht verfolgt, das den Build scheitern lässt, den Diagrammen als ihre Bilder statt als Mermaid und einer festen Version von Mermaid für einen verbliebenen `mermaid`-Block; in der Sprache jeder Seite für die Suche und Suchmaschinen, mit einer Beschreibung und dem Datum ihrer neuesten Datei für jede Seite, den vollen Adressen ihrer Sprachen und ohne eine Seite ohne Übersetzung in Suchmaschinen; eine Karte für KI-Assistenten, `llms.txt`, wie [llmstxt.org](https://llmstxt.org/) sie verlangt, die die Hooks bei jedem Build aus dem Menü schreiben: Name und Beschreibung der Website, ein Abschnitt für jeden Teil des Menüs und jede Seite mit ihrer Beschreibung und ihrer Seite in jeder weiteren Sprache, nie eine Entscheidung, was `blueprint.py site-check` und lychee prüfen, und an ihrer Stelle eine `docs/llms.txt` des Projekts; die Badges bleiben auf GitHub; ein Header, der die Version des neuesten Releases zeigt, die die Hooks beim Build aus Git lesen, sodass keine Seite den Browser des Lesers die API von GitHub fragen lässt, was `blueprint.py site-check` prüft, und ein Footer mit Links zum Owner auf GitHub, zu seiner Website mit all seinen Projekten und zu GitHub Sponsors, wie `.github/FUNDING.yml` es nennt, in der Sprache der Seite, sofern `mkdocs.yml` nicht `extra.social` setzt; eine Seite *Automatisierung*, die die Hooks bei jedem Build aus `.github/workflows/` schreiben, auf Englisch und Deutsch: jeder Workflow zum Aufklappen, was ein Link oder die Suche von selbst tut, sodass die Seite auf dem Handy kurz bleibt, was `blueprint.py site-check` prüft, mit dem Kommentar an seinem Anfang und dem, was ihn startet, jeder Zeitplan in Worten, die Prüfungen, die `main` verlangt, und die Umgebungen und Secrets, die er nutzt, und an ihrer Stelle eine `docs/automation.md` des Projekts.

Weitere Sprachen funktionieren genauso, etwa `/de/`, `/nl/` und `/fr/`, sobald `mkdocs.yml` sie nennt: Eine Seite, die eine davon nicht übersetzt hat, bleibt eine Kopie der englischen Seite, die keine Versionen nennt, egal welche andere Sprache sie übersetzt hat; der Bericht eines Pull Requests verlinkt eine geänderte Seite unter ihrer Adresse, `nl/faq.html` für `docs/faq.nl.md`; und die Hinweise zu Rechtschreibung und Stil lassen eine Seite in einer Sprache aus, die sie nicht lesen können.

**Womit:** MkDocs mit dem Material-Theme, `mkdocs.yml`, `docs.yml`, `.github/mkdocs_blueprint.py`, `.github/a11y/`.

## Diagramme, die sich selbst reparieren

Jedes Diagramm als Bild, das alle sehen, auch in der GitHub-App, in den Stores und in E-Mails, die kein Mermaid zeichnen: eine Mermaid-Quelle in `docs/diagrams/`, gezeichnet als SVG für das helle und eines für das dunkle Design, die auch die Website zeigt, im Design, zu dem die Lesenden wechseln, sodass eine Seite mit Diagramm kein Mermaid lädt; die Prüfung *diagrams* zeichnet die Bilder in jedem Pull Request neu, der ein Diagramm ändert oder einen `mermaid`-Block hinzufügt, und der Diagramm-Bot committet Quellen und Bilder auf seinen Branch; auf `main` behebt ein Pull Request des Diagramm-Bots, was noch fehlt, und merged sich selbst; `bash scripts/diagrams.sh --extract` macht aus den `mermaid`-Blöcken vorhandenen Markdowns Quellen und ihre Bilder.

**Womit:** `scripts/diagrams.sh` mit mermaid-cli, `lint.yml`, `after-checks.yml`, `diagrams.yml`.

Die GitHub-App, HACS, der Nextcloud App Store, PyPI und die E-Mails von GitHub zeichnen kein Mermaid und zeigen einen `mermaid`-Block als Code. Darum ist jedes Diagramm ein Bild seiner Quelle, und die Bots halten das ohne einen Menschen so.

Nach dem Merge und jede Woche wird auch main gezeichnet: Ist ein Diagramm noch kein Bild seiner Quelle, behebt das ein Pull Request von bot/diagrams, der sich selbst merged. - **Ein Pull Request repariert sich selbst:** Fügt ein Pull Request von einem Branch des Repositorys einen `mermaid`-Block hinzu oder ändert er eine Quelle, führt die Prüfung *diagrams* `bash scripts/diagrams.sh --extract` aus, und der Diagramm-Bot committet die Quellen und Bilder, die dabei entstehen, als Release-App auf den Branch, mit einem Kommentar, der die geänderten Seiten nennt. Die Prüfungen dieses Commits bestehen. Ein Pull Request aus einem Fork bekommt die fehlschlagende Prüfung, deren Zusammenfassung die Dateien und den Befehl nennt.
- **`main` repariert sich selbst:** Nach jeder Änderung von `main`, die ein Diagramm betrifft oder einen `mermaid`-Block hinzufügt, und jede Woche zeichnet der Workflow Diagrams alle Diagramme von `main`. Fehlt etwas, etwa die Blöcke eines Repositorys direkt nach dem Update des Blueprints, hält er einen Pull Request vom Branch `bot/diagrams` mit der Korrektur, der sich selbst merged, sobald alle Prüfungen bestehen, und schließt ihn, wenn `main` anders repariert wurde. Ein fehlgeschlagener Lauf öffnet ein Issue, das der wöchentliche Lauf schließt, sobald der Bot wieder besteht.
- **Ein neuer Renderer zeichnet neu:** Renovate hält das Image von mermaid-cli in `scripts/diagrams.sh` aktuell; die Prüfung zeichnet die Bilder auf seinem Branch neu, und der Diagramm-Bot committet sie, sodass das Update weiterhin von selbst merged.
- **Nur Diagramme:** Der Bot führt keinen Code eines Pull Requests aus. Er committet nur Quellen in `docs/diagrams/`, SVG-Bilder in `docs/images/diagrams/` und Markdown-Seiten, mit einfachen Pfaden, auf genau den Commit, den die Prüfung gezeichnet hat, und nur für einen Branch des Repositorys.

## Screenshots, die sich selbst erneuern

Die Bilder des Projekts, die ein Bot nur erneuert, wenn sich ihre Pixel ändern: nach einer Änderung dessen, was sie zeigen, nach jedem Release und jede Woche führt der Screenshot-Bot `scripts/screenshots.sh` ohne Secrets aus und hält einen Pull Request mit den Bildern, die anders aussehen, der sich selbst merged; ein neues Repository beginnt mit einem Skript, das die Social Preview rendert und seine Website und, nach seiner Art, seine Integration in Home Assistant oder seine App in Nextcloud fotografiert, jedes in Docker und in beiden Themes.

**Womit:** `scripts/screenshots.sh`, `.github/screenshots-paths.txt`, `.github/screenshots.toml`, `screenshot-bot.yml`.

Die Bilder eines Projekts, in seiner README, auf seiner Website und in den Stores, zeigen es so, wie es war, als jemand sie zuletzt aufgenommen hat. Der Screenshot-Bot nimmt sie neu auf, sobald sich ändern kann, was sie zeigen, und ändert eine Datei nur, wenn sich ihre Pixel ändern.

Haben sich Pixel geändert, setzt der Job collect die Shards zusammen, und hat main keine dieser Dateien geändert, während sie gerendert wurden, hält ein Pull Request von bot/screenshots die neuen Bilder, die Dateien, die die Einstellungen nennen, und die Breite und Höhe, die die Seiten für die Bilder nennen, und merged sich selbst, sobald alle Prüfungen bestehen; sieht main aus wie gerendert, schließt der Bot ihn. Hat main inzwischen eine davon geändert, etwa weil der Pull Request davor gemergt wurde, oder hat der Pull Request später Konflikte mit main, rendert der Bot main neu: von selbst oder vom Branch-Bot gestartet. </picture>

- **Ein Skript schaltet ihn ein:** Jedes Repository hat den Workflow Screenshots (`screenshot-bot.yml`), der nichts rendert, solange das Projekt kein `scripts/screenshots.sh` hat. Das Skript rendert die Bilder an Ort und Stelle, wo auch immer die Dokumentation, die Stores oder die Social Preview sie hernehmen; ein neues Repository beginnt mit einem, das die Social Preview `.github/social-preview.png` rendert und fotografiert, was es macht, wie der nächste Punkt sagt. `.github/screenshots-paths.txt` listet die Dateien, deren Änderung die Bilder ändern kann, wie die Pfade eines Workflows. Beide gehören dem Projekt, ein Update des Blueprints lässt sie also in Ruhe.
- **Was ein neues Repository fotografiert:** die Startseite seiner Website, die das Skript mit den Werkzeugen in `.venv-docs` baut; eine Home-Assistant-Integration auch ihre Seite in einem Home Assistant in Docker, der mit `custom_components/` läuft und die Integration über ihren Config Flow eingerichtet hat, und eine Nextcloud-App die App in den Apps der Einstellungen einer Nextcloud in Docker, mit eingeschalteter App. Jedes Bild kommt als `docs/images/screenshots/<name>.png` im hellen Theme und `<name>.dark.png` im dunklen, für ein `<picture>`, aufgenommen vom Chromium des Images der Social Preview mit Playwright, mit Hashes gepinnt in `.github/screenshots-browser-requirements.txt`, das Renovate zusammen mit dem Image bewegt. Server und Browser teilen ein Docker-Netz ohne Weg nach draußen, die Uhr des Browsers steht still, sein Fenster ist 1280×800 groß, und die Buchstaben haben graue Kanten, sodass derselbe Code dieselben Pixel rendert; Renovate hält die Images von Home Assistant und Nextcloud im Skript aktuell, und ein Projekt fügt seine eigenen Bilder der Funktion `shoot()` hinzu.
- **Wann er rendert:** Nach einer Änderung von `main`, die eine Datei der Liste, das Skript, die Liste oder die Einstellungen betrifft, nach jedem Release, dessen Version ein Bild zeigen kann, und einmal pro Woche startet sein Plan einen Lauf von Hand, wie es der Branch-Bot und ein Mensch tun. Die Läufe von Hand rendern einer nach dem anderen, und einer, der wartet, macht einem neueren Platz, sodass ein Render, der gewartet hat, `main` so rendert, wie es dann ist. Er führt das Skript ohne Secrets aus, mit einem Token, das nur liest, mit Docker, mit der ganzen History, damit die Website das Datum jeder Seite wie veröffentlicht zeigt, und mit den Werkzeugen der Website in `.venv-docs`, wie `CONTRIBUTING.md` sie einrichtet, für ein Skript, das ihre Seiten fotografiert.
- **Shards, Dateien und Hosts:** `.github/screenshots.toml`, das dem Projekt gehört, kann drei Listen nennen ([Entscheidung 0120](../decisions/0120-the-screenshot-bot-renders-in-shards-takes-named-files-and-blocks-other-hosts.md)). `shards`, etwa `["en-1", "en-2", "de-1", "de-2"]`, rendern nebeneinander, jeder auf einem eigenen Runner mit seinem Namen in `SCREENSHOTS_SHARD`, alle denselben Commit; jeder rendert und löscht nur seine eigenen Bilder, und sobald jeder Shard bestanden hat, setzt der Job *collect* sie für den einen Pull Request zusammen, der jeden Shard nimmt oder keinen. `files`, etwa `["docs/demo/timeline.json"]`, sind die Dateien neben Bildern, die das Skript rendert, mit ihren genauen Pfaden aus einfachen Namen außerhalb von `.git` und `.github`, als Text in UTF-8, der als geändert zählt, wenn sich seine Bytes ändern: Daten, die nichts ausführt, etwa eine Aufnahme, die eine Seite abspielt, nie Code, ein Manifest oder eine Konfiguration. `hosts`, etwa `["ghcr.io:443"]`, sind die Hosts, die die Jobs, die rendern, außer denen ihrer eigenen Schritte erreichen dürfen: Mit ihnen blockiert Harden-Runner jeden anderen, sobald der Job GitHubs DNS-Experiment auf einem Runner, der es hat, aus seinem Weg geräumt hat ([Entscheidung 0123](../decisions/0123-harden-runner-v2-22-4-and-a-job-with-sudo-takes-githubs-dns-experiment-away.md)), ohne sie zeichnet er den Verkehr nur auf. Ohne die Datei rendert ein Job jedes Bild, und der Bot nimmt nur Bilder; ein Schlüssel, den der Bot nicht kennt, oder ein Wert, den er nicht nehmen kann, lässt den Lauf fehlschlagen, mit dem, was falsch ist.
- **Warten, Zeitlimit und Fehlschläge:** Drei weitere Schlüssel von `.github/screenshots.toml` helfen einem Rendern, das lange dauert ([Entscheidung 0124](../decisions/0124-the-wait-asks-each-host-on-its-own-port-and-a-project-limits-its-render.md)). `skip_wait`, etwa `["launchpad.net:443"]`, nimmt Hosts aus `hosts` aus dem Warten auf Harden-Runner heraus, bevor das Skript läuft: einen Host, der einen Runner oft warten lässt und den das Skript erst später braucht und selbst erneut versucht; die Jobs erlauben ihn weiter. `timeout_minutes`, etwa `21`, ist das Zeitlimit des Skripts in ganzen Minuten von 1 bis 45, und 45 ohne ihn, sodass ein hängendes Skript seinen Schritt scheitern lässt, bevor die Stunde des Jobs endet; das Skript läuft mit `exec`, sodass es das SIGINT, mit dem GitHub einen Schritt beendet, dem die Zeit ausgeht, selbst bekommt und seine Demo beenden und sagen kann, worauf es gewartet hat, binnen etwa zehn Sekunden: etwa 7,5 Sekunden nach dem SIGINT schickt der Runner ein SIGTERM und etwa 2,5 Sekunden später beendet er, was noch läuft. Ein Skript, das länger zum Aufräumen braucht oder ein Limit für jede Gruppe will, behält ein eigenes `timeout --kill-after`. `failure_folder`, etwa `"tests/e2e/artifacts"`, ist der Ordner, den ein fehlgeschlagener Shard für einen Menschen aufhebt, mit einem Pfad aus einfachen Namen außerhalb von `.git`, als Artefakt `failed-render-<shard>-attempt-<attempt>` für sieben Tage; der Pull Request nimmt ihn nie.
- **Nur Pixel zählen:** `blueprint.py screenshots keep` vergleicht jedes Bild, das das Skript geändert hat, mit dem von `main` nach seinen Pixeln, bei einer Animation Frame für Frame, und gibt jedem, das gleich aussieht, seine committete Datei zurück, sodass ein neuer Encoder, Browser oder Runner keine Datei ändert. Ein Frame, der den vorigen wiederholt, zählt einmal, die Zeit, die jeder Frame zeigt, gar nicht, und ein ganz durchsichtiges Pixel hat keine Farbe.
- **Ein Pull Request, der sich selbst merged:** Haben sich Pixel geändert, hält der Bot einen Pull Request von `bot/screenshots`, *docs: update the screenshots*, als Release-App, mit einer Tabelle der Bilder und dem Anteil der geänderten Pixel in jedem. Er merged sich selbst, sobald alle Prüfungen bestehen, der Bot hält ihn mit `main` aktuell und schließt ihn, wenn `main` ohne ihn aussieht wie gerendert. Hat `main` eines seiner Bilder oder eine seiner Seiten geändert, während sie gerendert wurden, etwa weil der Pull Request davor gemergt wurde, lässt der Bot seinen Branch, wie er ist, und rendert `main` neu, und hat der Pull Request später Konflikte mit `main`, startet der Branch-Bot den Bot, der ihn neu baut ([Entscheidung 0118](../decisions/0118-a-bot-whose-pull-request-conflicts-builds-it-anew-at-once.md)). Eine geänderte Social Preview bekommt die Erinnerung, sie unter **Settings → General → Social preview** hochzuladen. Ohne die Release-App warnt der Lauf und hebt die Bilder drei Tage als Artefakt auf.
- **Größen, die den Bildern folgen:** Eine Seite kann Breite und Höhe eines Bildes nennen, als `![Text](adresse){ width="660" height="788" }` in Markdown oder `<img src="adresse" width="660" height="788">` in HTML, damit sie beim Laden nicht springt. Kommt ein Bild in einer anderen Größe heraus, korrigiert der Bot diese Zahlen auf den Seiten oben im Repository und in `docs/` im selben Pull Request, damit eine Prüfung des Projekts besteht, die sie mit den Dateien vergleicht. Eine Seite, die das ganze Bild nannte, nennt das ganze neue; jede andere behält ihre Breite und bekommt die Höhe der neuen Form; eine schärfere Datei derselben Form ändert nichts. Eine Tabelle in der Beschreibung nennt jede Korrektur. Eine Breite allein, eine Größe in Prozent, eine Adresse eines anderen Repositorys und alles andere im Zweifel bleiben, wie sie sind, und die Prüfung, die die Größe nennt, erklärt sie.
- **Nichts als Bilder:** Der Job mit der Release-App führt nichts vom Skript aus. Er nimmt PNG-, JPEG-, GIF- und WebP-Dateien, deren Inhalt so beginnt wie ihre Art, und den Text der Dateien, die die Einstellungen seines eigenen Checkouts von `main` nennen, mit einfachen Pfaden, außerhalb von `.git` und der Workflows, und lässt jede andere Datei weg, die das Skript geändert hat, was die Beschreibung des Pull Requests nennt. Außer ihnen committet er nur die neuen Größen auf den Seiten: Das Markdown liest er aus seinem eigenen Checkout von `main`, der kein Bild enthält, und aus dem Kopf eines Bildes nimmt er nur die Zahlen, sodass nichts vom Skript eine Seite erreicht. Viele Bilder gehen in mehreren Commits. Ein fehlgeschlagener Lauf hält ein Issue des Bot-Health-Bots offen, bis ein Lauf wieder besteht.
- **Auf deinem Rechner:** `bash scripts/screenshots.sh`, dann `python3 .github/blueprint.py screenshots restore`, das jedem Bild, das gleich aussieht, seine committete Datei zurückgibt, die anderen auflistet und die Größen auf den Seiten korrigiert, wie es der Bot tut. Es vergleicht die Pixel mit Pillow, das `python3 -m pip install --require-hashes -r .github/screenshots-requirements.txt` installiert.
- **Auch die Bilder des Blueprints erneuern sich selbst:** Nach einem Release, das die Fragen, das Template, die Workflows oder das Dashboard geändert hat, wie `.github/docs-pictures/paths.txt` sie listet, und auf Wunsch führt der Workflow Docs pictures `scripts/docs-pictures.sh` aus, das `copier copy` aufnimmt und das Dashboard und, mit `.github/docs-pictures/github_pages.py`, Seiten von GitHub fotografiert, die sich nicht mehr ändern, wie sie ein Leser ohne Konto sieht: ein Update des Blueprints mit seinen Prüfungen, die Assets eines Releases und den Kommentar des PR-Coachs, in beiden Themes und mit einer Uhr lange nach ihnen, damit GitHub ihre Daten ausschreibt. Es hält auf dieselbe Weise einen Pull Request von `bot/pictures`, *docs: renew the pictures*.
