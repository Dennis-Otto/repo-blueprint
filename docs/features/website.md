# Website, diagrams and screenshots

The website of the documentation, and the diagrams and screenshots that keep themselves current.

## Website

The documentation in `docs/` as a website with search and a light and a dark theme, which follows the system until the reader picks one, in English and, with German pages such as `index.de.md` next to the English ones, in German: every pull request builds it strictly and checks the built pages: every link and anchor, also those written in HTML, with lychee and without the network, and what the hooks of the website promise, such as a sitemap in every folder of pages and the 404 page in the default language, that no page loads more than 1,200 KB at once, and that every page shows each picture of its Markdown, the parts of the README included, with `blueprint.py site-check`, and `scripts/check-site.sh` adds the checks of the project; so does `scripts/check.sh` once the tools of its preview are installed, on Linux, macOS and Windows; every change of `main` publishes the build of that check on GitHub Pages, with what a hook writes into `site/.well-known/`, with the fonts and scripts that it downloads kept in a cache for a week, signs its provenance, which `gh attestation verify` checks, and asks the published website for the home page of each language; accessible, with the contrast and the underlined links that WCAG 2.2 AA asks for, which axe-core checks in both themes, at the width of a desktop and of a phone, where a page that scrolls sideways fails too, with a page that leads to another address checked as it shows before it leaves, on the pages that a pull request changes and on every page on `main` and each week, and a new serious or critical violation fails the check unless `.github/a11y-accepted.toml` accepts it with its reason; quick on a phone, with pictures that load as the reader comes to them, a GIF with an MP4 beside it played as that video, in the theme and at the width of the GIF, a picture for each theme loaded only in its theme, a picture that the README shows from `main` of its own repository, such as `https://github.com/OWNER/NAME/raw/main/screenshots/settings.png`, served from the checkout, so that the pull request that adds a screenshot shows it on its website too, and one that git doesn't track fails the build, the diagrams as their pictures instead of Mermaid, and the release of Mermaid that draws a remaining `mermaid` block pinned; in the language of each page for the search and search engines, with a description and the date of its newest file for each page, the full addresses of its languages, and a page without a translation kept from search engines; a map for AI assistants, `llms.txt` as [llmstxt.org](https://llmstxt.org/) asks for it, which the hooks write from the menu at every build: the name and the description of the website, a section for each part of the menu, and each page with its description and its page in every further language, never a decision record, which `blueprint.py site-check` and lychee check, with a `docs/llms.txt` of the project in its place; the badges stay on GitHub; a header that shows the version of the latest release, which the hooks read from git at the build, so that no page has the reader's browser ask the API of GitHub, which `blueprint.py site-check` checks, and a footer with links to the owner on GitHub, to their website with all of their projects and to GitHub Sponsors, as `.github/FUNDING.yml` names it, in the language of the page, unless `mkdocs.yml` sets `extra.social`; a page *Automation*, which the hooks write from `.github/workflows/` at every build, in English and German: every workflow in a fold of its own, which a link or the search opens, so that the page stays short on a phone, which `blueprint.py site-check` checks, with the comment at its top and what starts it, each schedule in words, the checks that `main` requires, and the environments and secrets that it uses, and a `docs/automation.md` of the project in its place.

More languages work the same way, such as `/de/`, `/nl/` and `/fr/` once `mkdocs.yml` names them: a page that one of them hasn't translated stays a copy of the English page that names no versions, whichever other language translated it; the report of a pull request links a changed page at its address, `nl/faq.html` for `docs/faq.nl.md`; and the hints at the spelling and the style leave out a page in a language that they can't read.

**How:** MkDocs 1.6 with the Material theme, which Renovate holds below MkDocs 2 until every website moves to Zensical before the maintenance of Material ends on 5 May 2027, as [decision 0146](../decisions/0146-every-website-moves-to-zensical-before-the-maintenance-of-material-for-mkdocs-ends.md) plans it, `mkdocs.yml`, `docs.yml`, `.github/mkdocs_blueprint.py`, `.github/a11y/`.

## Diagrams that fix themselves

Every diagram as a picture that every reader sees, also in the GitHub app, the stores and e-mails, which draw no Mermaid: a Mermaid source in `docs/diagrams/`, drawn as an SVG for the light and one for the dark theme, which the website shows as well, in the theme that the reader switches to, so that a page with a diagram loads no Mermaid; the check *diagrams* draws the pictures anew in every pull request that changes a diagram or adds a `mermaid` block, and the diagram bot commits the sources and pictures onto its branch; on `main`, a pull request of the diagram bot fixes what is still missing and merges itself; `bash scripts/diagrams.sh --extract` turns the `mermaid` blocks of existing Markdown into sources and their pictures.

**How:** `scripts/diagrams.sh` with mermaid-cli, `lint.yml`, `after-checks.yml`, `diagrams.yml`.

The GitHub app, HACS, the Nextcloud App Store, PyPI and the e-mails of GitHub draw no Mermaid and show a `mermaid` block as code. So every diagram is a picture of its source, and the bots keep it that way without a person.

- **A pull request fixes itself:** when a pull request from a branch of the repository adds a `mermaid` block or changes a source, the check *diagrams* runs `bash scripts/diagrams.sh --extract`, and the diagram bot commits the sources and pictures it made onto the branch, as the release app, with a comment that names the pages it changed. The checks of that commit pass. A pull request from a fork gets the failing check, whose summary lists the files and the command.
- **`main` fixes itself:** after every change of `main` that touches a diagram or adds a `mermaid` block, and every week, the Diagrams workflow draws every diagram of `main`. When something is missing, such as the blocks of a repository right after the update of the blueprint, it keeps one pull request from the branch `bot/diagrams` with the fix, which merges itself once every check passes, and closes it when `main` is fixed otherwise. A failed run opens an issue, which the weekly run closes once the bot passes again.
- **A new renderer draws anew:** Renovate keeps the image of mermaid-cli in `scripts/diagrams.sh` current; the check draws the pictures again on its branch, and the diagram bot commits them, so the update still merges on its own.
- **Nothing but diagrams:** the bot runs no code of a pull request. It commits only sources in `docs/diagrams/`, SVG pictures in `docs/images/diagrams/` and pages of Markdown, by plain paths, onto the very commit that the check drew, and only for a branch of the repository.

## Screenshots that renew themselves

The pictures of the project, renewed by a bot only when their pixels change: after a change of what they show, after every release and every week, the screenshot bot runs `scripts/screenshots.sh` without secrets and keeps one pull request with the pictures that look different, which merges itself; a new repository starts with a script that renders the social preview and photographs its website and, by its kind, its integration in Home Assistant or its app in Nextcloud, each in Docker and in both themes.

**How:** `scripts/screenshots.sh`, `.github/screenshots-paths.txt`, `.github/screenshots.toml`, `screenshot-bot.yml`.

The pictures of a project, in its README, on its website and in the stores, show it as it was when someone last took them. The screenshot bot takes them again whenever what they show can have changed, and changes a file only when its pixels change.

- **A script turns it on:** every repository has the Screenshots workflow (`screenshot-bot.yml`), which renders nothing until the project has `scripts/screenshots.sh`. The script renders the pictures in place, wherever the documentation, the stores or the social preview take them from; a new repository starts with one that renders the social preview, `.github/social-preview.png`, and photographs what it makes, as the next point says. `.github/screenshots-paths.txt` lists the files whose change can change the pictures, as the paths of a workflow. Both belong to the project, so an update of the blueprint leaves them alone.
- **What a new repository photographs:** the home page of its website, which the script builds with the tools in `.venv-docs`; a Home Assistant integration also its page in a Home Assistant in Docker, which runs with `custom_components/` and the integration set up by its config flow, and a Nextcloud app the app in the apps of the settings of a Nextcloud in Docker, with the app enabled. Each picture comes as `docs/images/screenshots/<name>.png` in the light theme and `<name>.dark.png` in the dark one, for a `<picture>`, taken by the Chromium of the social preview's image with Playwright, hash-pinned in `.github/screenshots-browser-requirements.txt`, which Renovate moves together with the image. The server and the browser share a Docker network without a way out, the clock of the browser stands still, its window is 1280×800, and the letters have gray edges, so the same code renders the same pixels; Renovate keeps the images of Home Assistant and Nextcloud in the script current, and a project adds its own pictures to the function `shoot()`.
- **When it renders:** after a change of `main` that touches a file of the list, the script, the list or the settings, after every release, whose version a picture may show, and once a week, its plan starts a run by hand, as the branch bot and a person do. The runs by hand render one at a time, and one that waits gives way to a newer one, so a render that waited renders `main` as it is then. It runs the script without secrets, with a token that only reads, with Docker, with the whole history, so that the website shows the date of each page as published, and with the tools of the website in `.venv-docs`, as `CONTRIBUTING.md` sets them up, for a script that photographs its pages.
- **Shards, files and hosts:** `.github/screenshots.toml`, which belongs to the project, can name three lists ([decision 0120](../decisions/0120-the-screenshot-bot-renders-in-shards-takes-named-files-and-blocks-other-hosts.md)). `shards`, such as `["en-1", "en-2", "de-1", "de-2"]`, render side by side, each on a runner of its own with its name in `SCREENSHOTS_SHARD`, all of them the same commit; each renders and deletes only its own pictures, and once every shard passed, the job *collect* puts them together for the one pull request, which takes every shard or none. `files`, such as `["docs/demo/timeline.json"]`, are the files besides pictures that the script renders, by their exact paths of plain names outside `.git` and `.github`, as text in UTF-8 that counts as changed when its bytes change: data that nothing runs, such as a recording that a page plays, never code, a manifest or a configuration. `hosts`, such as `["ghcr.io:443"]`, are the hosts that the jobs that render may reach besides those of their own steps: with them, Harden-Runner blocks every other one, once the job has taken GitHub's DNS experiment out of its way on a runner that has it ([decision 0123](../decisions/0123-harden-runner-v2-22-4-and-a-job-with-sudo-takes-githubs-dns-experiment-away.md)), and the job stops when Harden-Runner has no agent that blocks ([decision 0134](../decisions/0134-a-job-stops-when-harden-runner-doesnt-block.md)); without them it only records the traffic. Without the file, one job renders every picture and the bot takes only pictures; a key that the bot doesn't know or a value that it can't take fails the run, with what is wrong.
- **Waiting, time limit and failures:** three more keys of `.github/screenshots.toml` help a render that takes long ([decision 0124](../decisions/0124-the-wait-asks-each-host-on-its-own-port-and-a-project-limits-its-render.md)). `skip_wait`, such as `["launchpad.net:443"]`, leaves hosts of `hosts` out of the wait for Harden-Runner before the script runs: a host that often keeps a runner waiting, which the script needs only later and tries again by itself; the jobs still allow it. `timeout_minutes`, such as `21`, is the time limit of the script, in whole minutes from 1 to 45, and 45 without it, so that a hung script fails its step before the hour of the job ends; the script runs with `exec`, so that it gets the SIGINT with which GitHub ends a step that runs out of time itself, and can stop its demo and say where it waited, within about ten seconds: about 7.5 seconds after the SIGINT the runner sends a SIGTERM, and about 2.5 seconds later it kills what still runs. A script that needs longer to clean up, or a limit for each group, keeps a `timeout --kill-after` of its own. `failure_folder`, such as `"tests/e2e/artifacts"`, is the folder that a failed shard keeps for a person to see, by a path of plain names outside `.git`, as the artifact `failed-render-<shard>-attempt-<attempt>` for seven days; the pull request never takes it.
- **Only pixels count:** `blueprint.py screenshots keep` compares each picture that the script changed with the one of `main` by its pixels, frame by frame for an animation, and gives each one that looks the same its committed file back, so a new encoder, browser or runner changes no file. A frame that repeats the one before counts once, the time that each frame shows not at all, and a fully transparent pixel has no color.
- **What changed, in red:** for each picture whose pixels changed while its size and frames stayed, PNG, JPEG, GIF and WebP alike, `keep` also draws a picture of the difference, as a PNG at `diff/<path>`, with `.png` added unless the path ends in it, such as `diff/docs/images/hero.webp.png`, and names it as `diff` in the entry of the picture in `report.json` ([decision 0131](../decisions/0131-keep-draws-the-difference-of-every-picture-with-frames-for-a-phone.md)). Each changed pixel is red over the new picture in its own colors behind a thin veil of its own average color, a fifth of each pixel, so that a dark page stays dark, a light one light and its text readable, for an animation of the pair of frames with the most changed pixels, and a red frame around each place of change keeps even a change of a single pixel in sight when a phone or Telegram shows the picture scaled down to about 1000 pixels wide: in such pixels, the frame is 4 wide and 6 away from its changes, and changes nearer to each other than about 48 share one. The artifact of the run holds them, which the description of the pull request and the summary of the run point to; the pull request commits nothing of `diff/`. A picture of another size or with other frames, a new or a deleted one, a video and a picture that Pillow can't read get none, and `keep` goes on. The visual checks of a repository can show these pictures instead of drawing their own.
- **Before and after, in one picture:** beside the difference, `keep` writes a comparison at `comparison/<path>`, named like `diff/`, and names it as `comparison` in the entry of the picture in `report.json`, with `frame`, the number of the frame that it shows, from 1, and `frames`, how many frames the picture has ([decision 0149](../decisions/0149-a-comparison-shows-the-place-of-a-change-before-and-after-of-one-frame.md)). It shows the place of the change before and after, of the same frame as the difference, in the colors of the pictures: cut to the box around every change with room around it and at least about a third of each side, so that one sees where on the page it is, at the size of the pictures, so that their text stays readable, and with the same red frame around each change on both sides. The two places stand side by side, or one above the other for a wide place, such as a line of text, whichever a phone held upright shows larger; the place before comes first, with a gray strip and a white arrow between them. The table of the pull request names the frame of an animation, such as *changed, most in frame 12 of 25*, and the pager sends the comparison to a phone; `comparison()` of `blueprint/screenshots.py` draws it for the visual checks of a repository.

Such a picture, of the dashboard of the repositories and of the same dashboard an hour later, after a workflow of one repository failed, as the code of `keep` draws it:

- **One pull request that merges itself:** when pixels changed, the bot keeps one pull request from `bot/screenshots`, *docs: update the screenshots*, as the release app, with a table of the pictures and the share of the pixels that changed in each. It merges itself once every check passes, the bot keeps it current with `main`, and closes it when `main` looks as rendered without it. When `main` changed one of its pictures or pages while they rendered, as when the pull request before merged, the bot leaves its branch as it is and renders `main` anew, and when the pull request conflicts with `main` later, the branch bot starts the bot, which builds it anew ([decision 0118](../decisions/0118-a-bot-whose-pull-request-conflicts-builds-it-anew-at-once.md)). A changed social preview gets a reminder to upload it under **Settings → General → Social preview**. Without the release app, the run warns and keeps the pictures as an artifact for three days.
- **Sizes that follow the pictures:** a page can name the width and the height of a picture, as `![Text](address){ width="660" height="788" }` in Markdown or `<img src="address" width="660" height="788">` in HTML, so that it doesn't shift while it loads. When a picture comes out at another size, the bot corrects those numbers on the pages at the top of the repository and in `docs/` in the same pull request, so that a check of the project that compares them with the files passes. A page that named the whole picture names the whole new one; any other keeps its width and gets the height of the new shape; a sharper file of the same shape changes nothing. A table in the description names each correction. A width alone, a size in percent, an address of another repository and anything else in doubt stay as they are, and the check that names the size explains them.
- **Nothing but pictures:** the job with the release app runs nothing of the script. It takes PNG, JPEG, GIF and WebP files whose content starts as their kind does, and the text of the files that the settings of its own checkout of `main` name, by plain paths, outside `.git` and the workflows, and leaves out every other file that the script changed, which the description of the pull request names. Besides them, it commits only the new sizes on the pages: it reads the Markdown from its own checkout of `main`, which holds no picture, and takes only the numbers from the header of a picture, so nothing of the script reaches a page. A large set of pictures goes in several commits. A failed run keeps an issue of the bot-health bot open until a run passes again.
- **On your machine:** `bash scripts/screenshots.sh`, then `python3 .github/blueprint.py screenshots restore`, which gives every picture that looks the same its committed file back, lists the others and corrects the sizes on the pages, as the bot does. It compares the pixels with Pillow, which `python3 -m pip install --require-hashes -r .github/screenshots-requirements.txt` installs.
- **The blueprint's own pictures renew themselves too:** after a release that changed the questions, the template, the workflows, the dashboard or the code that draws a difference, as `.github/docs-pictures/paths.txt` lists them, and on demand, the Docs pictures workflow runs `scripts/docs-pictures.sh`, which records `copier copy` and photographs the dashboard and, with `.github/docs-pictures/github_pages.py`, pages of GitHub that no longer change, as a reader without an account sees them: an update of the blueprint with its checks, the assets of a release and the comment of the PR coach, in both themes and with a clock long after them, so that GitHub writes their dates in full. With `.github/docs-pictures/difference_picture.py`, it also draws the picture of a difference above anew, with the code of `keep`, so that it shows what `keep` draws. It keeps one pull request from `bot/pictures`, *docs: renew the pictures*, in the same way. VHS records the terminal in real time, so each run gives the recording other frames and colors; the tape therefore also takes a picture of each screen on which it waits, and `.github/docs-pictures/recording.py` keeps the committed GIF and video while those pictures stay the same ([decision 0145](../decisions/0145-the-recording-of-copier-copy-renews-itself-only-when-a-screen-changes.md)).
