# Renovate removes an override of npm that an update made needless

- Status: accepted
- Date: 2026-11-23

## Context

An entry of `overrides` in `package.json` raises a package that a dependency asks for in a version with a vulnerability. homedarts-for-autodarts raises minimatch that way, because ESLint asked for minimatch `^10` and the fix of GHSA-g3hv-75wg-m249 is only in minimatch 11, and a test of the project fails once every package that needs minimatch takes the major version of the override itself, so that the override leaves with the update that makes it needless. That update came with Renovate's homedarts-for-autodarts#783, which moves ESLint to 10.15.0, which asks for `^11.0.5`: its check failed, and the pull request waited for a person ([#1112](https://github.com/Dennis-Otto/repo-blueprint/issues/1112)). paperless-sync has the same override in `scripts/eslint/package.json`, without such a test, and player-switch-for-autodarts a nested one below `addons-linter`.

No bot could repair it. On a pull request of a bot, `for_unread()` of `blueprint/fixes.py` leaves a fix of `package.json` and `package-lock.json` to a person, since both are in `WORKFLOW_FILES` of `blueprint/branches.py` ([decision 0142](0142-the-fix-bot-commits-nothing-that-runs-with-rights-where-nobody-reads-its-commit.md)), and Renovate runs only the commands that `allowedCommands` of `.github/renovate-global.json5` allows, the refresh of the lock files of pip-compile ([decision 0137](0137-the-refresh-of-the-lock-files-merges-by-itself-from-versions-a-week-old.md)) and the blueprint's own `pins.py`.

## Options

1. **A test that only warns, or an override that stays for good:** the override holds the package back from the updates of the tools that ask for it, and nobody notices.
2. **An `autofix` of the project for the fix bot:** the bot rightly leaves `package.json` to a person on a pull request of a bot; loosening that rule weakens a control.
3. **Turning off Renovate's update of the override, or `ignoreDeps`:** the override stays old for good.
4. **A script of one project in `allowedCommands`:** it runs in Renovate's checkout with the token, so it belongs in `blueprint.py`, reviewed once here and the same for every repository.
5. **A command of `blueprint.py` that Renovate runs after every update of npm, which removes an override only where npm doesn't need it, and the one more entry of `allowedCommands` that allows it.**

## Decision

Option 5:

- **The command:** `python3 .github/blueprint.py npm-overrides --fix` (in the blueprint `python3 blueprint.py npm-overrides --fix`) looks at every `package.json` that git keeps, in any folder and not only those that the update changed, that has `overrides` and a `package-lock.json` beside it. For each entry that names a version or a range, also one nested below the package that asks for it, it takes the entry out, with what that leaves empty, and runs `npm install --package-lock-only --ignore-scripts --no-audit --no-fund` in that folder, so that npm writes the lock file itself and runs no code of a package. An entry that names no version, such as `$eslint` or `npm:other@1`, stays without npm, and so does one that caps the package, with `<` or `<=` or a range such as `1.2.3 - 1.4.0`: it holds the package back from a version, such as a broken major one, which no lock file of today shows, so no comparison of two lock files can find it needless.
- **When a removal stays:** only when every copy of the package in the new lock file is at or above the floor of the override, the lowest version that it allows, such as 11.0.3 for `^11.0.3`, unless the old lock file held a copy at the same path and of the same version below the floor too, outside the reach of the override, as minimatch 3.1.5 below multimatch in player-switch-for-autodarts; and only when the new lock file brings no version of any package that the old one lacked, since Renovate gives npm `--before=` only on its own call, and a version younger than a week must not come into an update that merges by itself. Otherwise the command puts `package.json` and `package-lock.json` back byte for byte, also when npm fails.
- **A file it can't write back,** such as a `package.json` with a key twice or a lock file that isn't JSON, is left alone with a line that names it, and the command goes on with the others, so that one such file holds back no update of Renovate.
- **What it says:** each override that it removed and each one that it kept, with what npm takes without it; and a note `//` beside `overrides`, which may speak of the override that left, which it leaves as it is. Without `--fix` it names the overrides that npm no longer needs and fails, and changes nothing.
- **Renovate:** a rule of `.github/renovate-blueprint.json5` runs the command after every update of npm, in `executionMode: "branch"`, with `fileFilters` `**/package.json` and `**/package-lock.json`, and `installTools: { node: {}, python: {} }`: the image of Renovate 44.249.1 has `/usr/bin/node` without npm and a Python 3.12, and `install-tool` gives it the Node with npm and the Python of Containerbase, as `binarySource: "install"` lets it. Renovate runs each distinct task of the updates of a branch once, so a branch of the refresh of the lock files that holds npm and pip-compile runs `locks --refresh` and this command both. The Mend Renovate app runs no command of the blueprint, so there the rule is left out.
- **What the commit of the task takes:** every file that git shows as changed or new and that a `fileFilters` entry matches; Renovate matches each entry on its own, so a negation such as `!**/vendor/**` would match every other file. So a folder that a package manager fills in Renovate's checkout belongs in `.gitignore`, as its other files would come into the commit: Renovate's update of Composer installs into the `vendor/` beside each `composer.json` and leaves it for the next branch when it has nothing to commit ([#1138](https://github.com/Dennis-Otto/repo-blueprint/issues/1138)). The blueprint ignores `stacks/php/vendor/` in `stacks/php/.gitignore` and a Nextcloud app its `/vendor/`; a project that adds a `composer.json` in a subfolder, such as `vendor-bin/<tool>/composer.json`, ignores the `vendor/` beside it as well. The command itself reads only the files that git keeps.
- **The settings of the bot** allow `^python3 (?:\.github/)?blueprint\.py npm-overrides --fix$` besides the two commands of before, with its reason; it sits outside the lines of `pins.py`, which the settings of a repository that runs Renovate itself leave out, so that such a repository allows it too.

## Consequences

- An update of Renovate that makes an override needless removes it in its own commit, turns green and merges by itself; one that still needs it leaves both files as they were.
- The allowed command takes effect in every repository of the owner as soon as it merges, since they all run on the Renovate of the blueprint; the rule reaches a repository with the release and the blueprint bot's pull request there. Renovate then builds a branch such as homedarts-for-autodarts#783 anew, as it is behind `main`, and commits `package.json` without the override.
- Every update of npm takes a little longer, as Renovate installs Node and Python and npm writes the lock file once for each override; a repository without an override runs no npm.
- The command reads only the lock file that npm writes: a removal that npm resolves the same way but that a test of the project still refuses stays a failure for a person, and so does a stale note `//`, which the command only names.

## Amendment of 2026-11-24: an update commits only what Renovate and the command change

The task committed a `package.json` that Renovate never changed ([#1155](https://github.com/Dennis-Otto/repo-blueprint/issues/1155)). For an update that only moves the lock file, to a version in the range of `package.json`, Renovate 44.258.2 calls `npm install --package-lock-only --no-audit --ignore-scripts <name>@<version>`, and npm saves that version into `package.json` as `^<version>`, or adds the package to `dependencies`. Renovate sets the ranges in the root of the lock file, `packages[""]`, back to those of `package.json`, but only for keys that are there already (`lib/modules/manager/npm/post-update/npm.ts`), and before the task it writes only the package files that it changed itself (`execute-post-upgrade-commands.ts`). After the task it takes up every changed file of `git status` that `fileFilters` matches, so npm's `package.json` came into the commit beside a lock file whose root still had the old ranges: #1144 failed a test of the template that compares both, and player-switch-for-autodarts#319 merged green with `^4.14.1` in `package.json` and `^4.14.0` in the lock file. Before the task, Renovate had committed only the lock file of such an update.

`fileFilters` can't tell who wrote a file, and without `**/package.json` an override that leaves never reaches the commit. So the command learns which updates the branch has:

- **The data file:** the rule gives `postUpgradeTasks.dataFileTemplate`, a list of JSON with each update's `packageFile`, `depType`, `depName`, `packageName`, `currentValue`, `newValue` and `isLockfileUpdate`, written with the helpers `toObject` and `toJSON` of Renovate's templates, which leave out a field that an update lacks. In `executionMode: "branch"` Renovate compiles it with the configuration of the branch, which has its `upgrades`, writes it to a file of its own cache and names that file to each command in `RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE`, as its documentation and `execute-post-upgrade-commands.ts` of 44.258.2 say; the command itself stays as `allowedCommands` allows it. A data file that the command can't read fails the update.
- **Put back:** with `--fix`, before the overrides, each `package.json` that git keeps with a `package-lock.json` beside it, and whose updates in the data file all only move its lock file, goes back to what Git keeps in `HEAD`, as a checkout writes it: during the task, `HEAD` is the base branch, also when Renovate builds a branch anew. A `package.json` in which an update bumps or replaces a range keeps what Renovate wrote. A `package.json` without `overrides` counts too.
- **The root of each lock file matches its `package.json`:** after the overrides, the command compares `dependencies`, `devDependencies`, `optionalDependencies` and `peerDependencies` of each `package.json` with the root of its lock file, and where one differs, npm writes the lock file anew with the flags of before. That also covers a group in which one update bumps a range and another only moves the lock file, and a package that npm added to the `dependencies` of the root.
- **No new version:** the lock file that npm writes stays only when it brings no version that the lock file as Renovate wrote it lacked, as for an override that leaves; otherwise both files stay as they were before that call, the command names the versions and fails, and so does the update. Without `--fix`, the command names each lock file whose root differs and fails.

The reproduction of #1144 with npm 11.14.1, on the parent commit of its branch, wrote a `package.json` identical to the branch's, and a lock file identical but for its root; the command puts that `package.json` back without a call of npm, and the commit has only the lock file, as before the task. Renovate builds #1144 anew once the rule reaches `main`.
