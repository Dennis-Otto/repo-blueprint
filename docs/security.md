# Security design

What the blueprint protects, what it trusts and which risks remain. [SECURITY.md](https://github.com/Dennis-Otto/repo-blueprint/blob/main/SECURITY.md) says how to report a vulnerability and how to verify a release, and argues why the repositories and their releases are safe; this page covers the blueprint itself: the template, `blueprint.py` with its code in `blueprint/`, the bots that run from this repository and the dashboard.

## What you can expect

- Copying or updating a repository from the blueprint runs no code of the blueprint on your machine. The template has no tasks, migrations or Jinja extensions, so Copier renders it in its sandboxed Jinja environment and needs no `--trust`.
- `blueprint.py` never reads, prints or stores the value of a secret. It names the secrets that are missing and the `gh secret set` command that sets each one; you type the value into the prompt of the GitHub CLI.
- `blueprint.py settings apply` changes only the settings of the repository it is run in, and only those that `.github/repository.toml` names.
- A new release of the blueprint reaches a repository only as a pull request of the blueprint bot in that repository, which passes every check of the repository before it merges, or waits for the maintainer.
- The dashboard shows only what is public anyway: no finding of code scanning and no alert of Dependabot.

## What is protected

| Asset | Where it lives | Protection |
| --- | --- | --- |
| The template, which reaches every repository made from it | `template/`, `copier.yml` and the shared files of this repository | Pull requests with every required check, and the Variants workflow, which renders every kind of project and runs its checks with its real tools; a release that is not only dependency updates waits for the maintainer |
| The settings of every repository | `.github/repository.toml` of each repository | Applied only by `blueprint.py`, by an administrator or by the settings bot on `main`; the bot compares them every week, so that a weaker setting shows |
| The private key of the release app, which can write the administration of the repositories it is installed on | The secret `RELEASE_AUTOMATION_PRIVATE_KEY` of the environment `release` of each repository | Only workflows on `main` can use the environment; each job asks for a token with the permissions it needs, which expires after an hour |

## Trust boundaries

</picture>

1. **This repository → every repository made from it.** The blueprint bot of each repository runs `copier update` to the latest published release of the blueprint and opens a pull request there, every week and right after a release, when the Rollout workflow of this repository starts it, one repository after the other, with a token of the release app for that repository alone, which can only start workflows and read. Before the update, it verifies that the release workflow of the blueprint made the release: the release is immutable, its tag points at a commit of `main`, and the release workflow signed the tag. It refuses any other release, so a tag that someone else pushed reaches no repository. It commits the update with its own code from `main`, not with the code that the update brings, and never overwrites a commit of anyone else on its branch. The checks of that repository decide whether it merges; a conflict, which also turns its auto-merge off, or the repository variable `BLUEPRINT_AUTOMERGE` set to `off`, makes it wait for the maintainer.
2. **The template → Copier on your machine.** The template is data for Copier's sandboxed Jinja; the answers of the questions are checked by their validators.
3. **`blueprint.py` → GitHub.** It runs the GitHub CLI with the login of whoever starts it, or with the token of the settings bot, and treats every answer of GitHub as untrusted: an answer it can't read stops the run with an error, and so does a change that GitHub refused, also with a 404, which GitHub answers to a token without the permission for some changes.
4. **Renovate → every repository.** It runs from this repository a few times a day, as the release app, with a token that can write contents, pull requests and workflows but not the administration. Its updates are pull requests that pass the checks of each repository; the weekly refresh of the lock files waits for the maintainer. What fails reaches the issue *Renovate logs problems*.
5. **The dashboard → the public.** It reads public data of GitHub and publishes a static page on GitHub Pages, with the same data as JSON and the releases of every repository as an Atom feed; every value it shows is escaped.

## Threats and countermeasures

| Threat | Countermeasure | Evidence |
| --- | --- | --- |
| A harmful change of the template reaches every repository | Pull requests with every required check here; every kind rendered and checked with its real tools, also after an update from the latest release and with the answers of each repository that takes the blueprint; each of these repositories updated read-only before the merge, in the Downstream check, which is not required: its summary names every conflict, and it fails on one that the pull request brings into a file that is not a page, such as a workflow, a script or a configuration; a release that is not only dependency updates waits for the maintainer; in each repository, the update passes its own checks | the Variants and Downstream workflows, `tests/test_template.py`, `tests/test_downstream.py` |
| Copying or updating the blueprint runs code on the user's machine | No tasks, migrations or Jinja extensions in `copier.yml`, so Copier needs no `--trust` | `test_copying_runs_no_code_of_the_blueprint` in `tests/test_template.py`; the Variants workflow updates every kind without `--trust` |
| A rendered workflow loses its pins or runs with more permissions | Every action pinned to the commit hash of a version, never of a branch, which zizmor would report as soon as the branch moves on; the workflows of a new repository are the blueprint's own, which zizmor and actionlint audit | `test_every_action_is_pinned_to_a_commit`, `test_no_workflow_pins_an_action_to_a_branch`, `test_the_workflows_are_the_blueprints_own` |
| A pull request adds a vulnerability that CodeQL finds, or a weakness of a workflow that zizmor finds, and merges before anyone sees the alert | The rule *code scanning* of *Protect main*: a new alert of CodeQL of high or critical severity, or a new error, stops the merge, and so does every new alert of zizmor, which analyzes every pull request with the version that its action pins; an alert that `main` has already doesn't, and the Findings workflow stays the backstop for the other tools | `test_a_new_alert_of_code_scanning_stops_the_merge` in `tests/test_blueprint.py`, `test_a_new_alert_of_codeql_or_zizmor_stops_the_merge` and `test_zizmor_audits_a_pull_request_as_it_audits_main` in `tests/test_template.py`, decisions [0038](decisions/0038-new-alerts-and-unlisted-actions-stop-a-pull-request.md) and [0073](decisions/0073-zizmor-analyzes-every-pull-request-and-each-new-alert-stops-the-merge.md) |
| A workflow change or an update brings, unnoticed, an action that no one chose, in a `uses:` line or inside another action | Only the actions of GitHub and the patterns of `[actions.selected]` may run, as a setting of the repository; `settings check` follows every action that a workflow runs, also inside a composite action or a reusable workflow, and names each one that the list lacks, also a step that runs an image with `docker://`, which no pattern allows, and `settings apply` narrows the list only once every workflow can still start | `test_only_the_listed_actions_run` in `tests/test_template.py`, `test_an_action_that_an_action_runs_in_turn_needs_its_pattern` and `test_an_image_of_docker_stops_the_selected_actions` in `tests/test_blueprint.py` |
| A private key, a connection string or a password that no provider issued is committed | Secret scanning with its generic patterns, beside push protection for the secrets of its partners and the Gitleaks scan of every pull request | `test_generic_secret_patterns_are_switched_on` in `tests/test_blueprint.py` |
| A version published minutes ago, perhaps from a hijacked account, reaches every repository with the weekly refresh of the lock files, which moves every indirect dependency to its newest version without the week of waiting | The refresh waits for the maintainer instead of merging on its own, and Renovate builds it anew only in its weekly window, the whole Monday, so a review from Tuesday on is the diff that merges, while a review on Monday holds until the next run changes the refresh ([decision 0029](decisions/0029-a-dependency-dashboard-the-whole-monday-and-pins-with-their-checksum.md)); a cooldown of the package managers isn't possible for the refresh alone, as Renovate sets their environment for the whole repository and would hold back the fixes of vulnerabilities too ([decision 0012](decisions/0012-lock-refresh-waits-for-the-maintainer.md)) | `test_the_weekly_refresh_of_the_lock_files_waits_for_the_maintainer` in `tests/test_template.py` |

| An unexpected answer of GitHub makes `blueprint.py` apply wrong settings | Every answer is read strictly; anything else stops the run with an error before a change | `test_errors_of_github_stop_the_run`; coverage-guided fuzzing with Atheris in `fuzz/fuzz_blueprint.py` |
| The settings of a repository are weakened by hand | The settings bot compares them with the settings as code after every change and every week, and applies them | the Settings workflow of each repository |
| A release stands on a tag that the release workflow didn't sign: one that someone created first, at a commit of their own, or one that release-please created after the run of the merge was lost | Every run of the Release workflow, not only the one of the merge, signs the tag of a merged release pull request before the release is created on it, and release-please creates a release only in a run that signed its tag; a tag that exists already must be the release workflow's own, signed at the commit of the merge, and the isolated build checks that again before it builds or signs anything | `.github/sign-tag.sh`, `tests/test_sign_tag.py` |
| A rogue release tag: whoever can push a tag to the blueprint, with the token of a job that runs a third-party action or with a leaked token, creates the tag of a new version at a commit of their own, and every blueprint bot updates to it and merges its workflows | Only the release app may create a release tag (the ruleset *Release tag creation*, which the settings bot applies where the variable `RELEASE_AUTOMATION_APP_ID` names the app), and like everyone else it can't move or delete one. ## Residual risks

- The list of the allowed actions never restricts a local action (`uses: ./…`), also not one that a job clones while it runs: it catches a `uses:` line that slipped through and an action that another action runs in turn, not someone who changes a workflow on purpose. Review, actionlint and zizmor's audit stay the guard there.
- The list of the allowed actions names no image of Docker, and GitHub refuses a step that runs one with `docker://`: a workflow runs an image with `docker run` in a `run:` step instead, pinned by its digest, which Renovate moves, and `settings check` names every `docker://` step that a workflow or an action that it runs still has ([decision 0064](decisions/0064-an-image-of-docker-runs-with-docker-run.md)). A new action starts only once its pattern is on GitHub, so its pull request needs `settings apply` by a maintainer before its checks can run, as a renamed required check does. The check *lint* of every pull request follows every action that the workflows run, also in turn, and fails while the list in the files lacks one, so that no update of an action brings one that no one listed ([decision 0074](decisions/0074-every-pull-request-follows-the-actions-that-its-workflows-run-in-turn.md)).
- The maintainer's account and the private key of the release app are the keys to every repository made from the blueprint; whoever holds them can change all of them.
- A change that is wrong but passes every check reaches every repository with the next release of the blueprint. The maintainer's review of every release that is not only dependency updates is the last guard.
- Copier and the GitHub CLI run with the permissions of whoever starts them.
- A release of the issue assistant that its release workflow made reaches the blueprint with the pull request of the sync bot, which merges itself once every check passes, and every repository with the next release of the blueprint: the review of the release pull request of the issue assistant, and of every release of the blueprint that is not only dependency updates, is the guard.
- The release app may create release tags, so its private key could create one at a commit of someone else's choice. Only the release workflow on `main` can sign a tag as the blueprint bot demands, the bot also refuses a new tag that points at the signed tag of an older release, as the signature names that older version, and the release workflow builds no release on a tag that it didn't sign, so such a tag reaches no repository; it only blocks the version it names until the maintainer looks. A step of the release workflow itself can sign a tag as the workflow, but the bot takes no commit before the version a repository has, so no tag takes a repository back to an older blueprint; such a step could only name a later commit of `main` as a release, one that every check of `main` has passed. A repository whose settings name no `RELEASE_AUTOMATION_APP_ID` keeps the rules of the release tags without the rule of their creation.
- The checks of a Home Assistant integration run the current images of hassfest and HACS, not an image by digest, so that they validate against the rules of today, as the actions of both projects do. hassfest sees the checkout read-only, and HACS a token that can only read.
- The refresh of the lock files has no check of the age of the versions it brings yet: the maintainer's review of its diff, which shows every new version, is the guard. A refresh that Renovate builds anew in its next window needs a new review.
- `pins.py` pins the sha256 of a download as its release has it a week after it came out, so a release that someone replaced within that week is pinned as it is then; every later download is checked against that sha256. It runs in the container of Renovate, which holds the token of the release app, on the files of `main` with the version that Renovate moved: review a change of `pins.py` as one of a workflow.
- An action that a project pins to a branch follows that branch without the week of waiting and merges on its own, so a bad commit there reaches the workflows of that project within hours. Pin an action to a release where it has one; the workflows of the blueprint pin none to a branch.
- The fix bot commits what the checks of a branch of the repository fixed with the tools of that branch, also on a branch of Renovate whose pull request merges itself, so a tool of the checks that turned malicious could put a change of a text file into such a commit. Such a tool runs in every check and release that uses it already; the bot adds no permission to it, keeps out of `.git` and the workflows, and each of its commits shows in the pull request with its files.
